# 명세 밖 주장 직접 확인하기

원래 정답지 12개를 바꾸지 않는 수동 확인 안내다. 반복 계획·AI 호출 없이 필요한 항목만 확인한다.
버그 수정은 하지 않았으며 아래 순서는 제공된 사이트의 현재 증상을 보여 주는 절차다.

## 시작

이 폴더에서 PowerShell:

```powershell
.\start_local_review.ps1
```

`http://127.0.0.1:8765/signin.html`에서 test / testtesttest로 로그인한다.
비어 있는 별도 `manual/review.db`가 자동 생성된다. 실행 포트가 사용 중이면 `-Port 8766`처럼 바꾼다.
기존 앱의 DB나 8000 서버를 사용하지 않는다. 중지는 Ctrl+C다. 재시작하면 이 수동 확인 DB만 유지된다.
스크립트는 이번 검증에 사용한 기존 가상환경을 기본 사용한다. 다른 컴퓨터에서는 백엔드 의존성을 설치한 Python을 `-Python 'C:\path\python.exe'`로 지정한다.
원래 사이트 소스/포함 dist가 비교 자료 옆에 있어야 한다. ZIP만 다른 곳에 풀었다면 원래 `output/comparison` 위치로 되돌리거나 원본 폴더에서 실행한다.

### X1. 자기 메일이 두 장 보이는가?

1. 주소창으로 `/compose.html`에 직접 진입한다. New mail은 N2 때문에 404, Email 모달 Compose는 F2 때문에 실패한다.
2. To `test@adminator.test`, Cc `admin@adminator.test`, 구분할 제목과 본문으로 Send한다.
3. `/email.html` → Inbox에서 그 제목을 누른다.
4. 스레드 카운트 2와 같은 내용의 카드 두 장을 확인한다.
5. DevTools Network의 threadId 조회 응답을 보면 서로 다른 id·folderId(sent/inbox), 같은 messageId인지 비교할 수 있다. 인증 cookie/CSRF 값은 공유하지 않는다.

확인 포인트: UI의 중복 표시와 실제 두 번 배달을 혼동하지 않는다. 증상은 확인했지만 중복 제거/사본 구분을 어떤 방식으로 요구할지는 제품 판단이다.

### X2. 자기 메일 답장의 수신자는 무엇이어야 하는가?

1. X1 메일을 열고 Reply를 누른다. To가 비어 있는지 본다.
2. 취소하고 Reply all을 누른다. To는 비고 Cc에는 admin이 남는지 본다.
3. 작성 제목 New message와 Subject의 Re: 접두사를 구분한다. 제목만으로 답장 데이터 전체가 없다고 주장하지 않는다.

확인 포인트: `service.js` composeFrom()이 본인 주소를 걸러 낸다. 일반 타인 메일의 Reply는 다른 조건이다. 이 작성창으로 실제 전송을 시도하면 F2가 먼저 실패하므로 그 실패를 X2의 독립 배달 오류로 세지 않는다.

### X3. Cancel했는데도 오류가 남는가?

1. `/email.html` → Compose → 정상 수신자/제목/본문 → Send한다.
2. F2의 오류가 보이면 Cancel한다.
3. 대화상자는 닫혔는데 메인 화면에 취소 상태와 빨간 전송 오류가 함께 남는지 확인한다.
4. Refresh를 눌러 전역 오류가 지워지는지 대조한다.
5. 독립된 대조: `/compose.html`에서 To를 비우고 Send → 필수 입력 오류 → Cancel한다. 전역 오류는 남고 폼 오류만 지워지는지 본다.

확인 포인트: 5번으로 이 문제가 F2만의 결과가 아니라 취소 시 오류 상태 정리 누락임을 분리한다.

### X4. '1 results'가 실제 출력되는가?

1. 하나의 메일에만 important 라벨을 붙인다(메일 열기 → 체크 → Apply labels).
2. important 라벨로 필터링하거나 검색으로 정확히 한 통만 남긴다.
3. 목록 헤더가 `1 results`인지 확인한다.

확인 포인트: 단수/복수 문구 오류다. 숫자 자체가 틀렸다는 주장으로 확대하지 않는다. 라벨 dropdown이 All labels로 돌아가는 것은 기존 U2다.

### X5. 모바일 라벨이 정말 접근 불가능한가?

1. 브라우저 반응형 크기를 390×844로 맞추고 `/email.html`을 연다.
2. 폴더/라벨 패널에서 success가 처음에 잘리는지 본다.
3. 패널 **안에 포인터를 두고** 아래로 스크롤한다. 페이지 전체 스크롤과 구분한다.
4. success가 드러나고 선택 가능한지 확인한다. 이번 Chromium 확인에서는 정상 마우스휠로 드러나 클릭됐다.
5. 실제 터치 기기는 별도 확인한다. 이번 검토는 뷰포트 축소+마우스휠이며 실제 모바일 터치를 검증한 것은 아니다.

읽기 전용 DevTools 콘솔:

```javascript
const rail = document.querySelector('.mail-rail');
({ clientHeight: rail.clientHeight, scrollHeight: rail.scrollHeight,
   scrollTop: rail.scrollTop, overflowY: getComputedStyle(rail).overflowY });
```

확인 포인트: 스크롤 가능하다는 사실과 스크롤 발견성이 충분하다는 제품 판단은 다르다. 강제 클릭이나 CSS 변경으로 성공시켜 놓고 정상이라고 판정하지 않는다.

### X6. 검증 안내와 Drafts 문구 해석

- Email 모달의 빈 입력은 F2 오류와 같지만, 전용 Compose 빈 To는 `Enter at least one To recipient.`로 거부된다. 전체 앱에 입력 검증이 없다고 일반화하지 않는다.
- `Previously saved drafts are retained`는 기존 draft 데이터 보존이라는 README 계약과 함께 해석한다. 현 UI에 Drafts 메뉴가 없다는 것은 사실이나 그 문장이 데이터 손실의 증거는 아니다.

## 원보고서의 Mock 서버 오류 대조

일반 상태에서 `/email.html?mailMode=mock`가 정상 로드되는지 본다. 이번 검토에서는 성공했다.
진단 실험에서 로그인 후 PUT/POST/DELETE 등 쓰기만 차단하자 동일 Account server is unavailable 오류와 폴더 부재가 생겼다. Mock 조회도 마지막에 PUT 저장을 하므로 읽기 제한 정책의 영향일 수 있다.
이 차단 실험은 환경 원인 분리를 위한 별도 진단이지 실제 제품의 추가 결함 확정이 아니다.
