# 테스트 케이스 템플릿 — WebTestPilot 범위

원본의 사전조건, 입력값, 단계별 기대 결과, 경계값 설계 원칙을 현재 네 가지 검사 유형에 맞춰 정리했다.
아래 항목은 계획을 설계하는 기준이며, 실제 출력 필드는 [test_plan/2 계약](test-plan-v2.md)을 따른다.

## 공통 설계 템플릿

| 설계 항목 | 작성할 내용 | 현재 JSON에 반영하는 위치 |
|---|---|---|
| 검사 목표 | 어떤 기능 또는 사용자 문제를 확인하는가 | proposed_checks, title, family |
| 사전조건 | 시작 화면, 열려야 할 메뉴, 입력 상태, 필요한 준비 | 준비 동작은 steps, 해결할 수 없는 조건은 open_questions 또는 unplanned |
| 테스트 데이터 | 정상·비정상 입력의 구체적인 문자열과 관측된 조건 | fill.value, expected_source |
| 실행 단계 | 조작할 대상, 순서, 입력값과 이동 목적지 | steps의 허용 operation과 관측된 대상 |
| 중간·최종 기대 결과 | 각 중요 동작 이후 관찰할 변화, 마지막에 확인할 결과 | expected에 단계와 결과를 명확히 기술 |
| 근거 | 요구사항, 화면에 표시된 안내, 관측된 제약, 잠정적 추정 | expected_source |
| 남는 상태 | 변경된 입력·필터·장바구니 등이 다음 검사에 미치는 영향 | 다음 시나리오의 준비 동작 또는 미확인 조건 |

임의의 준비 계정, 서비스 기능, 서버 응답, selector를 만들어 빈 항목을 채우지 않는다.
준비 상태나 기대 결과를 확인할 수 없으면 질문 또는 미계획 사유로 남긴다.

## 1. 기능 검사

**설계 순서:** 관측된 기능 진입 → 구체적인 옵션·입력 적용 → 결과 데이터·상태 변화 확인.

정렬 기능이 실제 화면에 관측된 경우:

1. 필요한 정렬 메뉴를 연다.
2. 관측된 정렬 옵션을 선택한다. 최초 관측에 없는 후속 옵션은 target_description으로 기술한다.
3. 메뉴 선택 표시와 목록의 실제 순서가 선택한 기준과 일치하는지 관찰하도록 expected를 작성한다.

기능별로 다음과 같은 결과를 확인할 수 있다. 해당 기능과 기대 규칙이 관측되었을 때만 사용한다.

- 검색: 입력 수용과 함께 결과 목록 또는 결과 없음 안내가 변하는지.
- 필터: 선택 표시와 실제 표시 항목이 적용 조건에 맞는지.
- 수량 변경: 수량 표시와 연관된 표시 금액·항목 상태가 일치하는지.
- 항목 제거: 목록과 연관된 개수·합계 표시가 변경되는지.

목록의 일부만 수집되었으면 전체 데이터의 정확성이 검증된 것으로 기대 결과를 확대하지 않는다.

## 2. 입력 검증 검사

입력 필드의 type, required, minlength/maxlength, min/max 등 관측된 제약 또는 제공된 요구사항으로 입력 변형을 정한다.

| 관측된 조건 | 의미 있는 입력 변형 |
|---|---|
| 필수 입력 | 빈 값과 정상 값 |
| 이메일 등 형식 제한 | 잘못된 형식과 정상 형식 |
| 최소·최대 길이 | 실제 경계, 경계 바로 안쪽·바깥쪽 |
| 숫자 범위 | 실제 최소·최대, 범위 바깥 값 |

정상 입력도 확인해 검증이 항상 거부되는 문제를 구분한다.
오류 입력 후 수정하는 흐름이 중요하면 잘못된 값 제출 → 정상 값으로 수정 → 재제출까지 하나의 검사 목표로 계획할 수 있다.
이전 입력과 오류 상태가 다음 검사에 남는지 고려한다.
브라우저 기본 검증, 페이지 자체 안내, 실제 요청·응답은 각각 다른 관찰 근거다.
클라이언트의 invalid 상태나 이벤트 하나로 서버 처리 여부를 결론내리지 않는다.

## 3. 라우팅 검사

**설계 순서:** 관측된 이동 요소 확인 → 클릭 또는 허용된 URL로 navigate → URL과 도착 화면을 함께 확인.

- 일반 링크는 실제 href와 화면의 이름을 근거로 목적지를 정한다.
- SPA는 문서 전체 로딩 없이 URL과 내용이 바뀔 수 있다.
- 이동할 수 있어도 링크 이름과 무관한 화면에 도착하는지 확인한다.
- 로그인 후 목적지처럼 실제 요구사항이 없는 경로를 예시에서 가져오지 않는다.
- 권한이 필요한 이동이 차단되면 필요한 준비 조건을 기록한다.

뒤로 가기, 새로고침 등 현재 operation으로 제공되지 않는 동작을 임의의 실행 단계로 추가하지 않는다.

## 4. UI 검사

**설계 순서:** 확인할 화면 상태 준비 → 현재 viewport 이미지와 제공된 요소 정보를 관찰할 기준 작성.

- 메뉴·모달을 열어 조작 요소가 가려지거나 화면 밖으로 나가는지 확인한다.
- 오류를 유발하는 허용된 입력·동작 후 안내가 읽히는지 확인한다.
- 요소의 겹침·잘림이 정보 전달 또는 기능 조작에 미치는 영향을 구체화한다.
- DOM 존재, 표시 상태, 수집된 위치·크기 정보와 이미지를 구분해 사용한다.
- 디자인 기준이 없는 색상·폰트·간격의 선호를 오류 기준으로 만들지 않는다.
- DOM에 없는 브라우저 검증 안내도 고려한다. validationMessage만으로 화면 표시를 확정하지 않는다.

현재 화면 자체를 검사하는 ui 시나리오는 steps가 비어 있을 수 있다.
상태를 준비해야 하는 검사는 그 동작을 steps에 포함한다.
