# 두 웹 테스트 도구의 버그 발견 비교
기존 증거 대조·검수판 v4 · 2026-11-06 | 의도된 버그와 추가 버그를 구분해 계산

## 한눈에 보는 비교 결과

의도된 버그만 비교하는 경우와 확인된 추가 버그까지 비교하는 경우를 구분했습니다. 의도된 버그는 12개, 두 도구의 발견을 합쳐 실제로 확인한 추가 버그는 중복을 뺀 2개입니다.

| 계산 대상 | WebTestPilot | Dogfood |
| --- | --- | --- |
| 의도된 버그 12개만 | 6/12 = 50.00% | 8/12 = 66.67% |
| 의도된 버그 12개 + 확인된 추가 버그 2개 | (6+1)/14 = 50.00% | (8+2)/14 = 71.43% |

추가 버그 2개는 취소 뒤 오류 잔존과 단수·복수 문구 오류입니다. WebTestPilot은 그중 1개, Dogfood는 2개를 기록했습니다. 의도된 버그 중 WebTestPilot의 수신자 검사 문제는 일부 증상 기록을 포함합니다(2쪽).

이 문서에서 쓰는 표기

| 표기 | 뜻 |
| --- | --- |
| F | 기능 문제 |
| V | 입력값 검사 문제 |
| U | 화면 표시 문제 |
| N | 페이지 이동 문제 |
| p. | 원래 보고서의 페이지 번호. 예: Dogfood p.8 = Dogfood 보고서 8쪽 |

F·V·U·N과 뒤의 숫자는 email-page.txt에 있는 원래 버그 번호입니다. 본문에는 V7(수신자 형식·도메인 검증 누락)처럼 버그 이름을 함께 적었습니다.




계산식
의도된 버그 발견 비율 = 발견한 의도된 버그 / 전체 의도된 버그 × 100
추가 버그 포함 발견 비율 = (발견한 의도된 버그 + 발견한 추가 버그) / (전체 의도된 버그 + 확인된 추가 버그) × 100

같은 버그는 한 번만 셉니다. 두 도구 모두 같은 분모를 사용합니다. 두 번째 비율은 이번 비교에서 확인한 14개에 대한 발견 비율이며, 사이트에 존재할 수 있는 모든 버그를 발견했다는 뜻은 아닙니다.

## 의도된 버그 12개: 무엇을 찾고 놓쳤나

의도된 버그는 사용자가 제공한 email-page.txt의 12개 문제입니다. 모두 제공된 코드와 사이트에서 존재를 확인했습니다. 아래 표는 각 도구의 보고서에 해당 증상이 적혀 있는지와 확인 가능한 페이지를 보여줍니다.

| 의도된 버그 | WebTestPilot | Dogfood |
| --- | --- | --- |
| F1(상단 경로가 Inbox로 고정) | 발견<br>WebTestPilot p.2-3 | 발견<br>Dogfood p.15-16 |

| U2(선택한 폴더·라벨의 표시가 바뀌지 않음) | 기록 없음 | 발견<br>Dogfood p.15-16 |

| V6(가입하지 않은 내부 주소로도 발송 성공 처리) | 기록 없음 | 발견<br>Dogfood p.19-21 |
| V7(수신자 형식·도메인 검증 누락) | 일부 증상만 기록<br>WebTestPilot p.8 | 발견<br>Dogfood p.19-21 |

V7(수신자 형식·도메인 검증 누락)은 주의해서 읽어야 합니다. WebTestPilot은 잘못된 주소의 발송 시도까지 기록했지만 저장 성공까지 검증하지는 않았습니다. 이 비교에서는 그 구체적인 증상 기록을 발견으로 셌고, 실제 버그가 있다는 사실은 이번 검토로 확인했습니다. Dogfood는 외부 주소의 성공 처리를 확인했지만 모든 잘못된 형식을 시험한 것은 아닙니다.

## WebTestPilot: 무엇을 잘 찾았나

WebTestPilot은 상단 경로 표시 오류, 잘못된 링크, 다크 모드 글자색, 계정 메뉴 겹침을 명확한 발견 목록으로 제시했습니다. 특히 U3(계정 메뉴의 버튼 두 개가 겹침)은 이번 두 보고서 중 WebTestPilot만 기록했습니다.

| 보고서에 적힌 내용 | 실제 확인 결과 | 보고서 위치 |
| --- | --- | --- |
| Sent를 눌러도 상단에 Inbox가 남음 | F1(상단 경로가 Inbox로 고정)과 일치 | WebTestPilot p.2-3 |
| New mail을 누르면 없는 페이지로 이동 | N2(New mail이 없는 페이지로 이동)와 일치 | WebTestPilot p.3 |
| Email·Compose에서 다크 모드 글자가 안 읽힘 | U5(다크 모드에서도 글자가 검정색으로 남음) 하나의 버그 | WebTestPilot p.4-5 |
| 계정 메뉴의 Switch Account와 Logout 겹침 | U3(계정 메뉴의 버튼 두 개가 겹침)과 일치 | WebTestPilot p.6 |
| Compose 링크는 존재하지만 화면에는 보이지 않음 | U4(사이드바의 Compose가 보이지 않음)와 일치 | WebTestPilot p.8-9 |
| 잘못된 주소도 클라이언트 검사 없이 발송 시도 | V7(수신자 형식·도메인 검증 누락)의 일부 증상 | WebTestPilot p.8 |

왜 보고서 첫머리의 발견 5개와 계산 결과가 다른가?

WebTestPilot 보고서 첫머리의 5개 중 다크 모드 문제 2개는 같은 U5(다크 모드에서도 글자가 검정색으로 남음)이므로 1개로 셉니다. 여기에 WebTestPilot p.8-9에 적힌 U4(사이드바의 Compose가 보이지 않음), V7(수신자 형식·도메인 검증 누락)의 증상을 더하면 5 - 1 + 2 = 6개입니다. 뒤의 두 항목도 명세에 있는 의도된 버그입니다. 다만 수신자 검사는 발송 시도까지만 기록되어 저장 성공을 확인한 발견과 구별해야 합니다.

놓친 부분과 해석

F2(작성창 발송 실패), F3(계정 전환 실패), F4(자동 읽음 처리 누락), U2(폴더·라벨 선택 표시 누락), V6(미등록 내부 주소 발송 성공), V8(짧은 비밀번호 가입)는 발견 기록이 없습니다. 일부 작성창 검사는 시작 조건을 준비하지 못했고, 쓰기 차단 때문에 저장 결과를 확인하는 검사에도 제약이 있었습니다. 이는 보고서의 실행 조건을 설명하는 사실이지, 모든 미발견의 원인을 입증한 것은 아닙니다.

실제 화면: WebTestPilot만 기록한 U3(계정 메뉴 버튼 겹침). Switch Account와 Logout이 같은 영역에 겹쳐 표시됩니다.

## Dogfood: 무엇을 더 찾았나

Dogfood는 화면·이동 문제뿐 아니라 메일을 실제로 보내 보면서 F2(작성창 발송 실패), V6(미등록 내부 주소 발송 성공), V7(수신자 형식·도메인 검증 누락)을 기록했습니다. U2(폴더·라벨 선택 표시 누락)도 WebTestPilot보다 구체적으로 설명했습니다.

| Dogfood가 기록한 문제 | 실제 확인 결과 | 보고서 위치 |
| --- | --- | --- |
| Email 화면의 작성창에서 발송 실패 | F2(작성창 발송 실패). 전용 compose.html은 발송 가능 | Dogfood p.2-4 |
| New mail이 없는 페이지로 이동 | N2(New mail이 없는 페이지로 이동)와 일치 | Dogfood p.4-5 |
| 빈 입력에도 “다시 시도” 오류만 표시 | 현상은 실제. F2(작성창 발송 실패)가 입력 검사보다 먼저 실패하므로 별도 의도된 버그로 더 세지 않음 | Dogfood p.6-7 |
| 다크 모드 글자가 거의 보이지 않음 | U5(다크 모드에서도 글자가 검정색으로 남음)와 일치 | Dogfood p.8-10 |
| 사이드바 Compose가 안 보임 | U4(사이드바의 Compose가 보이지 않음)와 일치 | Dogfood p.10-11 |
| 자기 메일 두 장 표시·답장 받는 사람 빈칸 | 현상은 확인. 기대 동작을 정해야 하므로 버그 확정은 보류 | Dogfood p.11-14 |
| Cancel 후 이전 오류가 남음 | 추가로 발견된 버그로 확인 | Dogfood p.14-15 |

| 모바일에서 success 라벨이 잘림 | 처음 잘림은 실제. 패널 안을 스크롤하면 보이고 클릭 가능 | Dogfood p.17-18 |
| 미가입 내부 주소·외부 주소 발송 성공 | V6(미등록 내부 주소 발송 성공), V7(수신자 형식·도메인 검증 누락) | Dogfood p.19-21 |

Dogfood가 붙인 문제 제목은 10개지만 의도된 버그 10개를 찾은 것은 아닙니다. 같은 원인 설명과 추가 발견이 섞여 있습니다. 경로·라벨 문제는 서로 다른 의도된 버그 2개를, 미가입·외부 수신자 문제도 서로 다른 2개를 포함합니다. 두 번 세지 않도록 정리하면 의도된 버그는 8개입니다.

실제 화면: 두 도구 모두 발견한 U5(다크 모드 글자색 오류). 어두운 배경 위에 어두운 글자가 남아 읽기 어렵습니다.

## 추가로 발견된 버그

다음 두 문제는 email-page.txt의 의도된 버그 12개에는 없지만, 두 도구의 보고서와 실제 사이트·코드를 대조해 확인했습니다. 첫 번째 계산(의도된 버그만)에는 넣지 않고, 두 번째 계산(추가 버그 포함)의 분모에는 두 문제를 모두 넣습니다. 분자에는 각 도구가 발견한 문제만 넣습니다.

| 추가로 발견된 버그 | 누가 기록했나 | 확인한 사실 |
| --- | --- | --- |
| 작성 취소 뒤 이전 오류가 남음 | WebTestPilot p.9<br>Dogfood p.14-15 | 취소 후 이전 오류가 남음. WebTestPilot: Enter a subject. / Dogfood: Message could not be sent.<br>영향: 취소 뒤에도 실패가 계속되는 것으로 오해할 수 있음 |
| 결과가 1개인데 “1 results”라고 표시 | Dogfood p.15-16 | 숫자 1에는 단수 result가 맞지만 항상 복수형 results 출력<br>영향: 기능 영향은 작은 문구 오류 |

작성 취소 뒤 이전 오류가 남는 문제

Email 화면에서 발송 오류를 낸 뒤 Cancel을 누르면 작성창은 닫히지만 오류가 화면에 남습니다. 전용 compose.html에서도 필수 입력 오류를 낸 뒤 Cancel하면 같은 문제가 생겼습니다. 따라서 의도된 발송 실패만의 결과가 아니라 취소할 때 오류를 지우지 않는 문제로 확인했습니다.

실제 사이트 화면: 취소했다는 안내 바로 아래에 이전 전송 오류가 남아 있습니다.

직접 확인: 작성창에서 Send로 오류 발생 → Cancel → 화면에 오류가 남는지 확인 → Refresh로 오류가 지워지는지 비교합니다. 전용 compose.html에서 받는 사람을 비운 채 같은 과정을 해 보면 발송 실패 버그의 영향을 분리할 수 있습니다.

“1 results” 문구 문제

한 통만 검색되도록 검색어 또는 라벨을 적용하면 확인할 수 있습니다. 결과의 숫자가 틀린 것은 아니고, 단수·복수 문구가 맞지 않는 문제입니다. 기능에 미치는 영향은 작습니다.

## 버그라고 단정하지 않은 현상

실제로 보이는 현상이라도 기대 동작이 불분명하거나 다른 원인이 있으면 “추가로 발견된 버그”로 확정하지 않았습니다.

| 보고된 현상 | 이번에 확인한 것 | 판단 |
| --- | --- | --- |
| 자기에게 보낸 메일이 같은 대화에 두 장 표시됨<br>Dogfood p.11-13 | 보낸 사본과 받은 사본이 각각 존재하며 화면에 둘 다 표시됨 | 두 번 배달됐다는 증거는 아님. 한 번만 보여야 할지 사본을 구분할지 제품 요구 확인 필요 |
| 자기 메일의 Reply / Reply all에서 To가 비어 있음<br>Dogfood p.12-14 | Reply all에서 To는 비고 Cc는 유지됨. Re: 제목·인용 본문도 유지됨. Reply의 Cc 유지까지 확인한 것은 아님 | 자기 메일 답장 기본 수신자를 정해야 함. 모든 답장이 고장났다고 확대하지 않음 |
| 모바일에서 success 라벨이 안 보임<br>Dogfood p.17-18 | 처음에는 잘리지만 패널 내부를 스크롤하면 보이고 선택 가능 | 발견하기 어려운 사용성 문제는 남음. 영구적으로 접근할 수 없는 버그라고 단정하지 않음 |
| Mock 모드에서 서버 오류·폴더 미표시<br>WebTestPilot p.8 | 일반 접속은 정상. 로그인 뒤 쓰기를 차단하면 같은 오류 발생 | 테스트의 쓰기 차단 영향으로 설명 가능. 독립 앱 버그로 더 세지 않음 |
| 취소 안내가 과거 임시저장을 언급함<br>Dogfood p.14-15 | 현재 임시보관함 메뉴는 없지만 과거 데이터 보존은 사이트 설명에 명시됨 | 안내가 혼란스러울 수는 있음. 데이터 손실이나 거짓 안내로 확정하지 않음 |

“Mock 모드”는 실제 수신자에게 메일을 배달하지 않는 샘플 메일함입니다. 이 비교에서 정상 여부를 설명하기 위해 필요한 경우에만 이 이름을 사용했습니다. 모바일 확인은 작은 화면 크기의 브라우저에서 수행했으며 실제 휴대폰 터치 동작은 검사하지 않았습니다.
