# 이메일 사이트 버그 보고서 비교·검증

검토일: 2026-11-06 (Asia/Seoul)  
비교 대상: WebTestPilot `report.pdf`(2026-11-03, 10쪽) / Dogfood `report.ko.pdf`(2026-11-04, 21쪽)  
정답 기준: `email-page.txt`의 12개 ID. F=기능, U=UI, V=입력 검증, N=이동·라우팅.

## 1. 핵심 결과

요청하신 지표는 `보고서에서 발견한 명세 버그의 고유 ID 수 / 명세 버그 12개`다. 통계 용어로는 precision/accuracy보다 **명세 결함 발견률(recall)**에 가깝다. 명세 밖 추가 결함은 분자·분모에 넣지 않았다.

| 집계 범위 | WebTestPilot | Dogfood |
|---|---:|---:|
| 보고서 전체: 본문 + 부록에 구체적으로 적힌 증상, 이번 검토로 사실 확인 | **6/12 = 50.00%** | **8/12 = 66.67%** |
| 정식 발견만: WebTestPilot 발견 1~5 / Dogfood ISSUE-001~010 | **4/12 = 33.33%** | **8/12 = 66.67%** |

두 범위를 함께 제시하는 이유는 WebTestPilot이 부록 C에 버그 단서를 적고도 본문 결함으로 승격하지 않은 경우가 있기 때문이다. 전체 보고서 비교에서는 그 내용을 버리지 않되, 도구 자체가 성공·저장까지 검증했다고 확대하지 않는다. 특히 WebTestPilot의 V7은 **클라이언트 주소 검증 누락·전송 시도라는 부분 관찰**이고, 실제 성공·Sent 저장은 이번 소스/로컬 검토가 보완했다. 이 보완 없이 도구의 확정 실적으로 읽으려면 정식 발견 지표를 사용해야 한다.

Dogfood의 ISSUE-008은 F1과 U2를 함께, ISSUE-010은 V6과 V7을 함께 기술한다. 한 이슈가 서로 다른 명세 ID의 구체적 증상을 각각 포함하므로 각각 대응했다. 반대로 WebTestPilot의 발견 3·4는 같은 U5의 서로 다른 페이지 증상이므로 1개 ID로 중복 제거했다.

이 한 번의 실행에서 Dogfood의 전체 보고서 발견률이 16.67%p 높지만 도구 일반 성능의 우열을 뜻하지 않는다. 쓰기 권한·시간·시나리오·테스트 데이터·날짜가 다르다.

## 2. 실제 사이트와 정답 기준 확인

정식 발견 5건의 중심 증상은 모두 실제 코드와 일치한다. 다만 고유 명세 버그는 4개다. 이 5건 기준의 유효 관찰과 전체 명세 발견률을 혼동하지 않는다.

부록의 추가 관찰 검토:

- U4 숨은 Compose와 V7 클라이언트 검증 누락은 실재하므로 전체 보고서 지표에는 포함한다. V7의 저장 성공까지 W가 입증했다는 뜻은 아니다.
- Cancel 후 오류 잔존은 명세 밖 추가 결함 X3으로 확인했다.
- Logout의 href='#'만으로 동작 결함을 주장할 수 없다. `auth/ui.js`의 [data-auth-logout] 클릭 핸들러가 preventDefault 후 client.logout()을 호출한다. 실제 로그아웃은 금지 범위여서 실행하지 않았다.
- Mock 모드 서버 오류는 무차단 상태에서 재현되지 않았다. 로그인 후 쓰기 차단만 적용하면 mock 조회 과정의 PUT /api/mock-mailbox가 막혀 동일 오류와 폴더 0개가 재현됐다. MockEmailApi.execute()가 읽기 뒤에도 상태를 저장하는 구조 때문이다. 원 실행의 네트워크 원자료가 없으므로 같은 원인으로 단정할 수는 없지만, 독립 앱 버그로 가산할 근거는 부족하다.
- New mail의 404 메모는 N2 중복이다. 다크 모드 메모는 U5 중복이다. 메뉴가 다른 버튼을 덮는다는 메모는 U3의 파생 영향이며 별도 명세 ID가 아니다.

## 6. 명세 밖 추가 항목과 사용자 재확인 절차

아래 X ID는 이번 비교를 위한 식별자이며 원래 정답지에 추가된 번호가 아니다. 모두 12개 분모에서 제외한다. 완전한 재현 조건과 결과는 `추가항목_재확인.md`, 실제 관찰은 `evidence/observations.json`을 함께 본다.

### X1. 자기 발송 메일의 중복 스레드 표시 — 증상 확인, 표시 결함 후보

출처: Dogfood ISSUE-006, 11~13쪽. 전용 Compose에서 To=test@adminator.test, Cc=admin@adminator.test로 한 통 전송하고 test의 Inbox에서 연다. `2 message(s) in this thread`와 같은 내용의 카드 2개가 나타난다. API에서는 **서로 다른 id와 folderId(sent/inbox), 같은 messageId**임을 확인했다. 이는 두 번 네트워크 배달됐다는 증거가 아니다. `backend/mail.py`가 정상적으로 두 물리 사본을 만들고 thread 조회가 두 폴더를 함께 읽으며 UI가 messageId별 중복 제거/사본 구분 표시를 하지 않는 구조다. 동일 메시지를 한 번만 보여야 하는지 또는 보냄/받음 구분이 필요한지는 제품 기대를 정해야 한다. 증거: X_self_thread_F4.png.

### X2. 자기 메일의 Reply/Reply all에서 To가 비어 있음 — 증상 확인, 기능·UX 후보

출처: ISSUE-006, 12~14쪽. X1의 메일을 연 뒤 Reply all을 누른다. To='', Cc='admin@adminator.test', 제목은 New message다. `service.js` composeFrom()의 dedupe가 자신의 주소를 항상 제외하므로 생긴다. 수신자 없는 작성 상태는 실제지만 자기 메일 답장의 기본 수신자를 어떻게 정할지는 추가 요구가 필요하다. 일반 타인 메일 답장 전체가 실패한다는 주장이나 F2와 별도의 배달 실패를 이 실험만으로 확정하지 않는다. 모달 송신은 이미 F2가 가린다. 증거: X_self_reply_all.png.

### X3. Cancel 뒤 취소된 작성 오류가 메인 화면에 남음 — 추가 결함 확인

출처: W 부록 C 9쪽, Dogfood ISSUE-007 14~15쪽. Email 모달에서 Send 실패 후 Cancel한다. dialog는 닫혔지만 'Composition cancelled…' 상태와 'Message could not be sent…' 전역 alert가 함께 남았다. 전용 Compose에서 빈 To를 정상 거절시킨 뒤 Cancel해도 전역 'Enter at least one To recipient.'가 남는다. 따라서 F2만의 파생 결과가 아니라 **작성 취소 시 오류 상태 초기화 누락**이다. `closeCompose()`와 cancel-compose는 전역 error('')를 호출하지 않는다. Refresh는 run()의 초기화로 오류를 지운다. 증거: X_cancel_stale_error.png, X_standalone_cancel.png.

### X4. 단일 결과에도 '1 results' — 추가 문구 결함 확인

출처: Dogfood ISSUE-008, 15~16쪽. 메일 한 통만 매칭되는 폴더/필터에서 제목을 확인한다. `ui.js`가 항상 `${page.total} results`를 출력하므로 1일 때도 복수형이다. 결과 개수가 틀렸다는 뜻은 아니며, 기능 영향이 낮은 문구 결함이다. U2의 상태 표시 누락과 분리되지만 별도 분모에는 넣지 않는다. 증거: U2_X_singular.png, F1_U2_sent.png.

### X5. 모바일 success 라벨 잘림 — 현상 확인, 접근 불가 결함은 미확정

출처: ISSUE-009, 17~18쪽. 뷰포트 390×844에서 rail clientHeight=259, scrollHeight=306, overflow-y=auto. 처음에는 success 일부가 rail 밖이었다. rail 위에서 정상 마우스휠을 사용하자 scrollTop=47, success가 영역 안으로 들어오고 클릭도 완료됐다. 강제 클릭이나 CSS 수정은 하지 않았다. 스크롤 가능성을 알아채기 어렵다는 UX 우려는 남지만 DOM에서 삭제/영구 접근 불가한 결함으로 세면 과장이다. 실제 터치 장치의 제스처는 검사하지 않았다. 증거: X_mobile_before_scroll.png, X_mobile_after_scroll.png.

### X6. 모달 입력 검증 안내 / 임시저장 안내 문구 — 별도 해석 항목

ISSUE-003의 입력별 안내가 없다는 관찰은 확인됐지만 F2가 검증 함수 호출 이전에 모든 입력을 거부한다. 같은 값을 전용 Compose에 넣으면 To·제목·본문 필수 검사가 동작하므로 앱 전체에 검증이 없다고 일반화할 수 없다. ISSUE-007의 'Previously saved drafts are retained'는 현 UI에서 Drafts 접근 기능이 없다는 사실과 과거 DB를 보존한다는 사실을 함께 적어야 한다. 현재 데이터의 손실이나 임시저장 기능 존재를 뜻하지 않는다.

## 7. 실험 방법과 한계

- 2026-11-06, Chromium 153.0.8010.12, 1440×900와 390×844 뷰포트, ko-KR, 새 비인증 컨텍스트에서 test 로그인, 제공 dist 사용. Google Fonts 등 외부 요청은 차단했다. 실제 휴대폰 터치 검사는 아님.
- `evidence/observations.json`의 21개 체크는 서로 다른 관찰 시점이다. 21개 버그 또는 21개 독립 시험 성공을 뜻하지 않는다. 추가 `write_block_control.json`은 정책 영향 진단 실험이다.
- 소스 수정·버그 수정·제품 빌드 교체·기존 DB 변경은 하지 않았다. 실험 서버는 종료했다. 기존 8000 포트 서버에는 접속하지 않았고 임의의 비어 있는 로컬 포트를 사용했다.
- 두 원보고서의 최초 네트워크/trace/원본 실행 JSON은 제공되지 않았다. PDF에 포함된 텍스트·이미지와 전달된 코드, 이번 로컬 관찰을 대조한 것이다. 원 도구의 모든 내부 판정 과정을 역검증한 것은 아니다.
- W 실행: 6분, 추정 $1.02, 쓰기 차단, 테스트 계정 로그인, 일부 시작 조건 실패. D 실행: 16분, $2.52, 119턴, 메일 발송 허용, 로그아웃·계정 설정 변경 금지. 이 값은 원보고서 기재값이며 이번에 재측정하지 않았다.
- D가 '읽음 상태 정상'이라고 쓴 것은 수동 Mark read 관찰과 양립한다. F4의 자동 열람 처리를 검증한 근거가 아니므로 F4 발견으로 인정하지 않았다.
- 다크 테마 기본값은 저장된 dash26-theme 또는 OS 선호를 따른다. 모든 사용자에게 다크가 기본이라는 표현은 일반화하지 않는다.

## 8. 완성 후 실제 화면 재점검

사용자 추가 요청에 따라 별도 격리 DB에서 실제 사이트를 다시 열고 데스크톱·390×844 화면 11개를 직접 시각 검토했다. `evidence/final_visual/visual_observations.json`과 PNG가 최종 대조 기록이다. API 응답만 보고 대체한 점검이 아니다.

- 메뉴 겹침, 다크 모드 기본 글자 가독성, 숨은 Compose, 모달 송신 오류, Cancel 뒤 alert, 자기 메일 두 카드, 빈 To, 모바일 내부 스크롤을 실제 화면과 다시 대조했다. 발견률은 변경되지 않았다.
- Sent를 클릭한 자리에 포인터가 남으면 `.mail-folder:hover` 배경이 보인다. 포인터를 계정 메뉴로 옮긴 화면에서는 사라진다. 따라서 Dogfood의 “Sent가 강조됨”을 관찰 오류라고 단정하지 않고 hover와 지속 선택 표시를 구분하도록 문구를 보정했다.
- Reply all은 To가 비어 있지만 Subject의 Re:와 인용 본문은 유지된다. 작성 대화상자 제목 New message만으로 답장 문맥 전체가 없다고 주장하지 않는다.
- 최종 모바일 확인에서도 success가 스크롤 후 드러나 정상 클릭됐다(scrollTop=46px). 초기 확인의 47px는 당시 상태의 측정값이며 고정된 제품 규격이 아니다. 실제 터치 제스처는 미검증이다.
- 이번 서버도 종료했으며 원본 소스·기존 DB·원보고서는 변경하지 않았다.
