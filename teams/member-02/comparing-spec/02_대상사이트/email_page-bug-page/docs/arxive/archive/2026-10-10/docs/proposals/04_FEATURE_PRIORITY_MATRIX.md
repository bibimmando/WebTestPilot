## 평가 기준

| 기준 | 가중치 | 1점 / 3점 / 5점 |

종합점수=`(30U+25F+15E+15L+15X)/5`. High≥85, Medium70–84, Low<70. E는 높을수록 쉽고 별도 난이도 Low/Medium/High는 변경 범위의 정성 판단이다. 신기능이 필요한 근거가 없으면 사용자 활용도·적합성을 낮게 본다. 테스트 자동화·버그 인젝션·Oracle은 **가중치0**, 우선순위 결정 기준으로 사용하지 않는다.

점수는 서비스 가설에 기반한 상대 판단이며 사용 빈도 측정값이 아니다. 개발 요청 시 실제 사용자 목적을 확인해 조정한다. W02/W16이 높은 것은 화면이 이미 있는데 이동/메뉴의 단절을 크게 줄이기 때문이다. W03/W04는 큰 작업이지만 일상 업무의 연결 가치가 크다. W12/W14는 새 도메인 수요가 확인되지 않아 후순위다.

## 점수와 개발 순서 구분

W01/W02/W16은 기존 정보와 화면을 서비스 중심으로 연결하는 첫 묶음이다. W03은 전용 task 구조가 필요해 다음 단계지만 장기 핵심이다. W05/W11은 현재 서비스를 실제로 쓰기 위한 설정/주소/최신성 문제를 해결한다. W09는 이미 있는 Calendar view/RSVP를 유지하면서 관련성과 공유/충돌 안내를 보강한다.

W04는 Task와 자원 링크를 모두 준비한 뒤 구현한다. W06/W07은 저장소를 복제하지 않는 발견/대기 뷰다. W08은 현재 차트가 있기 때문에 '차트를 추가'하는 것이 아닌 정확한 업무 지표를 준비하는 후속 과제다. W15는 기본 홈이 안정된 뒤 개인화한다. W12 요청·W14 장소는 사용 목적이 확정되지 않으면 구현하지 않아도 된다.

## 부가 품질 참고

미래 구현의 기본 확인은 사용자가 약속한 정보를 찾고 저장/이동할 수 있는지, 자기 자료가 다른 계정에 보이지 않는지, 모바일에서 작업할 수 있는지다. 기존 테스트 자동화는 이 서비스 계약을 검증하는 수단으로 활용한다. 실습 레코드·재현 작업대·고의 버그 화면을 서비스 도메인으로 제안하지 않는다.
