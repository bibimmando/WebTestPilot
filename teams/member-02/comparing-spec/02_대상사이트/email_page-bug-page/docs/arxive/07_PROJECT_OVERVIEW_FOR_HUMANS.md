# 사람이 읽는 프로젝트 현황

2026-10-12 수정·회귀 완료 기준. Adminator 화면을 바탕으로 만든 로그인 가능한 내부 협업 웹앱이다. 계정 추가·빠른 전환, 개인 할 일·설정, 업무 Home, 내부 이메일과 고정 Label, 공유 일정, 공유/1:1 채팅, 사람·업무 검색, 확인 목록과 기본 리포트가 구현되어 있다.

화면은 HTML·JavaScript·SCSS, 서버는 FastAPI, 저장소는 기본 SQLite다. 개인 메일·할 일·설정과 공유 자료를 구분한다. 새 공유 일정과 공유 채팅방은 로그인한 모든 사용자가 접근하는 현재 정책을 유지한다.

**최초 QA 14건을 모두 수정했다.** 초안의 경쟁 덮어쓰기와 일정 재시도 중복을 방지하고, 수신 메일 분류·Label 검증·테마·설정 장애 복구·모바일 화면·호환 메뉴·오류 응답·대량 조회·빌드와 기존 회귀 테스트를 보강했다. 기존 DB의 계정과 업무 자료는 모두 보존한 채 열과 테이블만 추가했다.

실제 검증에서 프론트 171개, 서버 100개, 브라우저 회귀 13종, 정적 검사와 production 빌드가 통과했다. PC·390px 모바일, 24개 페이지, 계정 전환·초안 충돌·일정 응답 유실·설정 복구·메일 Label을 포함한다. 메일·일정의 응답량과 화면 준비 시간도 줄었다. 상세 범위와 한계는 [09 회귀 결과](09_POST_FIX_REGRESSION_REPORT.md)에 있다.

**다음 개발과 격리된 기능 테스트에 사용할 수 있다.** 운영 환경, 큰 자료에서의 장시간 부하, 실제 휴대전화·접근성, 다중 서버 검증은 다음 단계다. 일정의 많은 화면 요소와 주기적 조회, JSON 기반 검색·집계가 주요 성능 개선 후보다.

외부 메일·실제 내부 첨부, 사용자 정의 Label, 다중 버그 ON/OFF 플랫폼은 아직 없으며 이번 범위에서도 추가하지 않았다. 현재 의도적으로 삽입된 제품 버그는 없고 Mock 오류 기능은 검사용 도구다.

후속 Codex는 이 요약 대신 **[06 상세 기술 맥락](06_CODEX_DEVELOPMENT_CONTEXT.md)**과 **[08 작업 인계](08_WORK_SESSION_HANDOFF.md)**를 우선 참조한다. 수정 내용은 [08 수정 보고](08_QA_REMEDIATION_REPORT.md), 최초 검수 기록은01~05에 보존되어 있다.

# 사람이 읽는 프로젝트 현황

2026-10-12 검수 기준. 현재 프로젝트는 Adminator 화면을 기반으로 만든 **로그인 가능한 내부 협업 웹앱**이다. 테스트 사이트라는 목적 설명도 있지만, 여러 버그를 켜고 끄는 테스트 플랫폼은 아직 없다.

구현된 주요 기능은 계정 추가·빠른 전환, 개인 할 일과 설정, 업무 Home, 내부 이메일과 고정 Label, 공유 일정, 공유/1:1 채팅, 사람 검색, 업무 검색, 확인 목록과 기본 리포트다. 메일은 등록된 내부 계정끼리 전달한다. 외부 메일 발송과 실제 내부 첨부, 사용자 정의 Label 생성은 구현되지 않았다.

화면은 HTML·JavaScript·SCSS, 서버는 FastAPI, 저장소는 기본 SQLite다. 메일·할 일·설정은 계정별 자료이며 새 공유 일정과 공유 채팅방은 로그인한 모든 사용자가 접근하는 현재 정책을 갖는다.

이번에 프론트 단위 테스트 **135개**, 서버 테스트 **62개**, 정적 검사와 별도 빌드가 통과했다. 인증·계정 전환·Label 회귀·메일·일정/채팅·업무 연결의 브라우저 검증도 수행했다. 오래된 브라우저 테스트 2개는 현재 화면과 맞지 않아 실패했다.

발견 사항은 **Critical 0 / High 2 / Medium 7 / Low 5**다. 먼저 해결할 것은 초안의 조용한 덮어쓰기, 일정 재시도 중복, 발신 Label의 수신본 복사, Label 입력 계약, 오래된 회귀 테스트다. 최근 수정한 Label 필터 해제·메일함 이동·개수 표시·계정 초기화는 이번 회귀에서 통과했다.

**다음 개발과 격리된 기능 테스트에는 사용할 수 있지만 운영 준비 완료로 보기는 어렵다.** 데이터 정합성과 검증 기반을 보강한 뒤 자료량·운영TLS·다중 서버·실기기 검증을 진행하는 것이 좋다. 다중 버그 토글 플랫폼이 목적이라면 별도 범위와 격리·복원 설계가 필요하다. 이번 작업은 보고서만 작성했으며 기능 코드를 고치지 않았다.
