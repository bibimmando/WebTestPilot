## 왜 다시 고쳤나

이전 전체 검사에서 고유 버그 발견은 1종에서 2종으로 늘었지만, 검사 계획이 실행까지 도달하지 못하거나 실제 의도와 다른 요소를 누르는 문제가 있었습니다. 판정 모델만 바꿔서는 해결되지 않습니다.

확인한 문제는 다음과 같습니다.

| 문제 | 공통 원인 | 이번 변경 |
|---|---|---|
| 보이는 링크인데 계획이 거절됨 | URL 검증이 축약 관찰의 `links.url`만 읽고 `controls.href`를 놓침 | 관찰한 링크·제어 요소·검증된 최신 요소의 URL을 합쳐 같은 출처만 허용 |
| 한 시나리오 오류로 전체 계획 실패 | 시나리오 의미 검증을 계획 전체에 일괄 적용 | 시나리오를 원자적으로 검증하고 유효한 선행 시나리오와 최초 UI 관찰을 보존 |
| 링크 대신 알림 닫기를 눌러도 계획 완료 | operation/value만 확인하고 대상 의미는 확인하지 않음 | 실행 전에 고정 대상과 최신 관찰의 대상을 비교하고 실제 dispatch 직전에도 다시 확인 |
| DOM 변경 후 키가 바뀌면 대상을 잃음 | 축약 관찰에서 href·현재 검증 요소가 빠짐 | 스냅샷의 검증된 제어 요소를 별도 보충 관찰에 포함 |
| 이름 없는 아이콘 버튼을 식별하기 어려움 | role/name만으로 식별 불가 | 기존 전처리 WeakMap의 문서별 실제 노드 참조를 제한적으로 사용 |
| 알림·배지만 있고 실제 내용 증거 부족 | 기능 판정에 목록·수량·화면이 충분히 전달되지 않음 | 범용 DOM 상태 보충과 완료 시나리오의 실제 마지막 화면 첨부 |
| URL마다 공통 폼 검사 반복 | Runtime마다 실행 기록 초기화 | 명시적인 캠페인 파일을 통해 별도 실행 사이에서 기록 공유 |

## 변경된 파이프라인

```text
현재 페이지 관찰 + 검증된 요소 + 제한된 DOM 상태
 → 계획 AI: 제안·고정 기대값·행동·미관찰 대상의 식별 조건
 → 전체 구조·제안 대응 검증
 → 시나리오별 의미 검증, 거절 및 의존성 보류 기록
 → 고정 대상 바인딩 저장
 → 실행 AI가 최신 요소 선택
 → 역할·이름/주소 또는 동일 실제 노드 확인
 → 실제 dispatch 직전 스냅샷에서 재확인
 → Playwright MCP 행동
 → 전후 DOM·텍스트·네트워크 등 증거 + 완료 시 마지막 실제 화면
 → 독립 판정 AI
 → 후보는 동일 시작 조건에서 추가 1회 재현·재판정
 → 판정과 실제 증거 위치를 캠페인 기록에 연결
```

버튼을 정확히 눌렀는데 앱의 수량이 그대로인 경우에는 실행 성공 뒤 앱 판정으로 넘깁니다. 다른 버튼을 고른 경우에는 행동을 보내지 않고 실행 오류로 기록합니다. 실행 오류 자체를 앱 버그라고 확정하지 않습니다.

## 계획 검증의 범위

- 계획 생성 도구의 navigate URL 목록을 관찰한 동일 출처 URL로 제한합니다. 서버 경로나 상품명은 코드에 넣지 않습니다.
- 모델이 이 목록을 무시해도 의미 검증에서 해당 시나리오를 거절합니다. URL 제한을 우회해서 실행하지 않습니다.
- 하나의 시나리오 내부 일부 단계만 잘라 실행하지 않습니다. 기대값과 단계의 의미가 달라지는 것을 막습니다.
- 유효한 선행 시나리오는 보존합니다. 행동 없는 UI 검사는 최초 상태에서 실행하도록 앞으로 배치합니다.
- 거절된 시나리오 뒤의 행동 시나리오는 독립성을 증명할 계약이 없으므로 보수적으로 보류합니다. **임의의 의존성 그래프를 자동 복구하는 구현은 아닙니다.**
- JSON 구조, 중복 ID, 제안 누락 같은 응답 전체 오류는 기존의 제한된 1회 수정 요청을 유지합니다.
- 한 상태 변화의 성공이 다음 행동의 전제라면 시나리오를 나누도록 계획 지침을 보강했습니다. 아직 조건 분기나 단계별 assert 실행 언어를 추가한 것은 아닙니다.

## 대상 검증의 범위

`execution_bindings.json`에 계획 시점의 대상 식별 조건을 저장합니다. 기존에 관찰한 요소는 프로그램이 식별 조건을 만들고, 나중에 나타날 요소는 계획 AI가 `target_identity`의 role과 name 또는 href를 작성합니다. 이 필드는 계획 도구 내부 확장이며, 내보내는 `test_plan/2` 단계에는 넣지 않습니다.

일반 버튼은 역할·이름이 맞는 현재 후보가 하나여야 합니다. 링크는 역할과 관찰한 목적지 주소를 비교합니다. 헤더와 푸터에 같은 목적지 링크가 여러 개면 해당 목적지로 가는 동등한 링크를 허용하며, 후보 수를 기록합니다. 이름만 같은 버튼 여러 개를 임의로 선택하지 않습니다.

이름과 주소가 없는 기존 요소는 전처리의 `observed_ref`가 같은 실제 DOM 노드일 때만 연결합니다. 이 값은 WeakMap과 문서별 식별자로 생성되므로 CSS 위치가 같아도 다른 노드나 새 문서의 요소를 같은 대상으로 취급하지 않습니다. 새 노드로 교체된 이름 없는 요소는 재식별을 보류합니다. 이 참조는 같은 노드라는 사실만 보장하고, 아이콘의 업무 의미가 맞다는 보장은 아닙니다.

실행 AI의 선택 검증과 별개로 runtime이 행동 직전 생성한 스냅샷에서도 다시 확인합니다. 검증 실패는 `flow.json`의 `target_audit`, 모델 교정 응답 또는 행동 오류에 남습니다. 실행 완료 커서는 성공한 계획 행동에만 증가합니다.

## 증거 수집과 한계

`snapshots/<snapshot_id>.json`의 `dom_state`와 판정 입력의 `supplement.dom_state`에 다음을 담습니다.

| 데이터 | 의미 |
|---|---|
| candidates | main 또는 body 안에서 관찰한 article·li·tr·listitem·row 등의 후보와 텍스트·하위 링크 |
| links | 같은 범위에서 관찰한 링크 주소·텍스트·이미지 포함 여부 |
| numeric_and_status | 숫자 입력·spinbutton·output·상태 메시지·숫자가 있는 버튼/링크 |
| scope·url·snapshot_id | 관찰 범위·주소·연결된 스냅샷 |
| omitted·completeness | 개수 제한, 문자열 잘림, iframe·shadow DOM·가상 목록의 한계 |

읽기만 수행하는 일반 DOM 수집입니다. 전용 API, DB, 사이트 내부 버그 목록은 호출하지 않습니다. 수집 실패나 도중 페이지 이동은 unavailable로 남깁니다. 최대 후보 80개, 링크 120개, 숫자·상태 100개, 문자열 240자입니다.

**DOM 후보 개수는 업무상 상품 개수가 아닙니다.** 중첩된 목록이나 표, 숨겨진 데이터, 가상 스크롤, iframe 등이 있습니다. 후보가 0개라는 이유만으로 항목 누락을 확정하지 않도록 판정 지침에 명시했습니다.

완료된 기능 검사에도 실제 마지막 뷰포트 이미지를 첨부합니다. 기능 이미지 수집 실패는 해당 이미지의 누락으로 남고 자동으로 앱 오류가 되지 않습니다. UI 검사는 기존처럼 실제 이미지가 필수입니다. 이미지가 인용된 후보를 재현할 때에는 원본·재현 화면을 모두 제공하고 URL·뷰포트·스크롤 일치 조건을 확인합니다. 화면 밖 항목이나 임의의 전체 사이트 상태까지 증명하지는 않습니다.

## 캠페인 기록

새 CLI 옵션 `--campaign-state <파일>`을 같은 요구사항·출처·쓰기 권한의 여러 URL 실행에 재사용합니다. 명시하지 않으면 기존처럼 Runtime 안에서만 공유합니다.

실행 완료, 정책 차단 없음, 수용된 passed/candidate 판정이 모두 있어야 공통 폼 기록에 등록합니다. 실행 실패·불명확한 결과·inconclusive는 등록하지 않습니다. 저장 항목에는 run/flow/finding ID와 증거 폴더가 있습니다.

동일 폼 필드·제약·초깃값과 동일 행동·입력값을 비교하므로 기대값의 문장 표현만 바뀌었다고 실행을 반복하지 않습니다. 보류된 새 기대값을 passed로 처리하지 않고 unplanned/deferred로 표시합니다. 다른 기대값을 이전 판정으로 자동 대체하는 기능은 아닙니다.

출처·요구사항·쓰기 권한이 다르면 같은 파일 사용을 거절합니다. 잠금 파일로 동시 수정을 거절하고 임시 파일 교체로 저장합니다. 프로세스가 비정상 종료되어 `.lock`이 남으면 실행 중인 프로세스가 없는지 확인한 뒤 정리해야 합니다. 이 기능은 순차 실행용입니다.

서로 다른 사용자 상태·인증 역할·배포 버전·검사 설정에는 별도 캠페인 파일을 사용해야 합니다. 이를 전부 자동으로 판별하는 캐시 무효화 기능은 없습니다. 전역 캠페인 기록이 사이트 전체의 모든 기능 검사 완료를 의미하지도 않습니다.

## 검증 명령

프로젝트 루트 PowerShell에서 실행합니다. 테스트는 구현 파일과 분리된 기존 test 디렉토리를 사용합니다.

```powershell
$env:PYTHONUTF8 = '1'
$env:PYTHONPATH = (Resolve-Path 'external/WebTestPilot-integration/teams/member-01').Path
.\.venv\Scripts\python.exe -m unittest discover -s external/WebTestPilot-integration/teams/member-01/integration/test -t external/WebTestPilot-integration/teams/member-01 -v
.\.venv\Scripts\python.exe -m unittest discover -s src/ai_inspection -t . -v
.\.venv\Scripts\python.exe -m integration.test_staged
.\.venv\Scripts\python.exe -m integration.test_executor
.\.venv\Scripts\python.exe -m integration.test_regressions
.\.venv\Scripts\python.exe -m integration.test.generate_quality_demo --output tmp/reliability_demo_new
```

마지막 명령은 새 출력 폴더를 사용합니다. 일반/이름 없는 버튼의 정상·고장 동작, 가짜 담기 성공, 잘못된 대상 선택, UI 이미지 재현을 별도 localhost 예제에서 실제 MCP로 검증합니다. 모델은 고정 응답이므로 이 결과를 실제 AI 탐지율이라고 부르지 않습니다. 실제 Sonnet 결과는 별도 실행 결과 문서에 기록합니다.

## 실제 검사와 해석

Sonnet 집중 검사는 기존 CLI·Playwright MCP 파이프라인으로만 수행합니다. 이전 누락을 보고 선정한 일반 기능 검사이므로 블라인드 벤치마크가 아닙니다. 모델 입력에는 정상 요구사항·관찰 증거·검사 우선순위만 넣고, 주입 버그 ID·정답·GT를 넣지 않습니다.

전체 사이트 재검사가 아니므로 이전 전체 탐지율 2/17을 새 수치로 덮어쓰지 않습니다. 이번 목적은 계획→실행 대상→증거→판정→재현의 연결이 실제로 개선됐는지 확인하는 것입니다. 최종 결과·미해결 항목·사용량은 아래 연결된 결과 문서를 기준으로 확인합니다.
