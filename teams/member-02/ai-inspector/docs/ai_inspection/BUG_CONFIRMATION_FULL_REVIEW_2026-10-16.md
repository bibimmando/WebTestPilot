## 어떻게 점검했나

- 이전 전체 검사와 같은 29개 URL 집합 및 정상 요구사항을 사용했습니다. 두 후보는 재현 예산이 부족해 별도의 단일 시나리오 후속 검사로 확인했습니다.
- 29개 URL을 모두 시도했고 후속 2건을 포함해 flow 31개·시나리오 89개를 기록했습니다. 본 검사는 약 24분 21초였고 후속 검사는 이 시간 안에 함께 진행했습니다.
- 최초 후보 12건 중 추가 재현 완료로 confirmed가 된 기록은 9건이며, 버그 ID로 중복 제거하고 조건별 대조한 결과가 6종입니다. 시나리오 판정은 passed 46건·candidate 12건·inconclusive 26건·finding 등록 거절 2건·수용 판정 없음 3건입니다.
- flow 25개는 completed, 4개는 execution_incomplete, 1개는 재현 중 취소, 1개는 판정 응답 형식 오류입니다. 29개 URL을 방문했다는 것이 모두 정상 검증됐다는 뜻은 아닙니다.
- 기존 integration CLI → Playwright MCP → 전후 증거 → 판정 AI → 추가 1회 재현·재판정 경로만 사용했습니다.
- 모델은 계획·실행·판정·재현 모두 Sonnet 5.5입니다. 검사 모델에는 주입 버그 ID·정답·GT를 전달하지 않았습니다.
- GT 목록과 판정 결과의 ID 대조는 검사와 분리된 사후 평가입니다. 알려진 테스트 사이트의 후속 점검이므로 블라인드 실험은 아닙니다.
- 로그인·암호 입력·가입 성공·계정 변경·주문 생성·서버 초기화는 실행하지 않았습니다. 네트워크는 읽기 전용이며 브라우저 시작 상태만 복원했습니다.
- 실행 소스는 검사 중 수정하지 않았습니다. 모델이 무작위로 고르는 시나리오와 후속 집중 검사가 포함되므로 단순한 동일 조건 A/B 수치로 해석하지 않습니다.

## 확정의 의미와 증거 제한

여기서 확정은 프로그램의 `candidate → 추가 재현 reproduced → confirmed` 기록이 있고 17개 버그 ID의 증상과 대응된다는 뜻입니다. 모든 원인·모든 조건의 검증 완료를 의미하지 않습니다.

F1은 저장 개수와 실제 목록 DOM·텍스트 내용의 불일치가 반복됐습니다. 마지막 이미지는 푸터만 보여 목록 본문의 시각적 확인은 못했으며, 모델이 언급한 지연 로딩·수집 누락 가능성도 원문에 남겼습니다. DOM 후보 개수만으로 전체 업무 항목 수를 단정하지 않습니다.

이번 F2 일부 흐름은 장바구니 URL로 직접 navigate한 방식이라 전체 로드에 따른 상태 유실 가능성에 대한 단서가 있습니다. 이전 독립 검사에서는 관찰한 장바구니 링크를 직접 클릭해 같은 현상을 재현했습니다. 이 차이를 지우지 않고 기록했습니다.

F3은 장바구니 이동 전 증가 버튼 단계에서 이미 수량 1→1이 관찰되어 전체 로드의 한계와 구분됩니다. 저장 DOM의 plus 아이콘·활성 상태와 최초·재현의 실제 MCP 대상 및 전후 스냅샷을 대조했습니다.
