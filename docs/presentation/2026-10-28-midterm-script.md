# WebTestPilot 중간발표 발표문

팀 404 · 2026-10-28 · 발표 약 8분 (슬라이드 20장 + 예비 1장)

제목 옆 (약 N초)는 소리 내어 읽을 때의 추정 시간이다.

## 1. 표지 (약 5초)

안녕하세요, 팀 404입니다. 저희 프로젝트 WebTestPilot의 중간 결과를 발표하겠습니다.

## 2. 목차 (약 10초)

발표는 네 부분입니다. 시작과 목표, 검사 범위와 동작 방식, 진행 현황, 그리고 중간 결과와 향후 계획 순으로 말씀드리겠습니다.

## 3. 동기 (약 25초)

웹 서비스 테스트는 생각보다 반복적입니다. 사이트마다 테스트를 새로 만들고, 기능이 바뀔 때마다 다시 고쳐야 합니다. 크롤러로 자동화하면 깨진 링크나 오류 페이지는 찾지만, 로그인하고, 팝업을 열고, 값을 넣고, 버튼을 눌렀을 때 화면이 맞게 바뀌는지처럼 사용자와 상호작용해야 드러나는 버그는 확인하기 어렵습니다. 그래서 사용자처럼 화면을 조작하며 버그를 찾는 AI 테스터를 만들자는 데서 출발했습니다.

## 4. 부딪힌 벽 (약 30초)

그런데 막상 AI에게 테스트를 맡겨 보니, AI가 버그라고 말하는 것이 두 종류로 나뉘었습니다. 왼쪽은 누가 봐도 틀린 것입니다. "2개 저장됨"이라고 써 놓고 카드는 1개거나, 수량 + 버튼을 눌러도 숫자가 그대로인 경우처럼 화면이 스스로 모순되면 AI도 자신 있게 오류라고 말할 수 있습니다. 오른쪽은 다릅니다. 비밀번호 6자리로 가입이 된다, 이게 버그일까요? 서비스가 6자로 정했다면 정상입니다. 품절 상품을 담을 수 있는 것도 예약 구매라면 정상입니다. 정답이 화면이 아니라 개발자의 머릿속에 있어서, AI 혼자서는 정할 수 없었습니다.

## 5. 구체화한 목표 (약 25초)

그래서 목표를 구체화했습니다. 모든 것을 판정하는 도구가 아니라, 사람이 판단할 재료를 빠르게 모아 주는 보조 도구입니다. 확실한 오류는 다시 실행해 재현까지 확인한 뒤 버그 후보로 올리고, 의도를 알아야 하는 것은 억지로 판정하지 않고 보류나 질문으로 사람에게 넘깁니다. 결과는 재현 절차와 증거, 판정하지 못한 항목까지 담은 보고서로 전달합니다.

## 6. 왜 이 네 가지 버그인가 (약 30초)

왜 이 네 가지 버그인지 말씀드리겠습니다. 현업 멘토링에서 실제 QA에서 자주 걸리고 사용자가 바로 겪는 버그로 기능, 입력 검증, 이동, UI를 짚어 주셨고, 이는 국제 품질 표준 ISO 25010의 기능 적합성, 사용자 오류 방지, 화면 품질과도 대응됩니다. 실제 버그 연구에서도 10년 전에는 가장 흔한 영향이 기능 일부 손실로 46%였고, 지금도 UI 버그가 약 12%, AI가 만든 웹 앱은 클릭에 실제로 반응하는 비율이 10에서 55%에 그쳤습니다. 겉보기만으로는 알 수 없고 직접 눌러 봐야 하는 이유입니다. 자세한 수치는 마지막 장에 정리해 두었습니다.

## 7. 검증하는 네 가지 버그 (약 30초)

검증하는 네 영역의 예시입니다. 기능은 눌러도 반응 없는 버튼이나 개수 문구와 실제 항목 수가 다른 경우, 입력 검증은 걸러지지 않는 잘못된 입력, 이동은 엉뚱한 곳으로 가는 링크, UI는 겹치거나 잘린 화면입니다. 모두 사이트 이름이 들어가지 않은, 어느 웹에서나 지켜야 할 공통 규칙 17개로 검사하고, 규칙에 없는 이상은 버그로 단정하지 않고 관찰로 남깁니다. 기능과 이동은 실제 사이트에서 확인했고, 입력 검증과 UI는 일부 구현된 상태로 더 발전시켜야 합니다.

## 8. 파이프라인 (약 30초)

전체 흐름입니다. URL을 받으면 코드가 사이트를 돌며 페이지를 종류별로 묶고, AI가 종류마다 한 번 탐색해 무엇을 확인할지 계획을 세웁니다. 계획은 고정된 테스트로 바뀌어 같은 종류의 여러 페이지에서 실행되고, 코드가 기대값과 실제값을 비교합니다. 어긋난 것만 AI가 원인을 분류하고, 다시 실행해 재현되면 보고서에 올립니다. AI는 탐색과 계획, 분류, 화면 판정, 제목만 맡고, 누르고 비교하고 등급을 매기는 일은 코드가 합니다. 서버에 쓰는 요청은 기본으로 막습니다.

## 9. 한 건이 만들어지는 과정 (약 40초)

한 건이 만들어지는 과정을 수량 + 버튼으로 보여 드리겠습니다. 1번은 AI가 쓴 계획으로, 코드가 아니라 데이터입니다. 무엇을 누르고 어떤 값을 읽어 무엇과 비교할지만 적혀 있습니다. 2번 테스트 코드는 AI가 아니라 29줄짜리 변환 코드가 찍어 낸 것이라 번호만 있고, 실행할 때 공통 실행 코드가 이 번호로 계획을 찾아 Playwright로 누르고 비교합니다. 그래서 AI 없이도 같은 테스트를 다시 돌릴 수 있습니다. 3번 기록을 보면 5초 동안 41번 다시 읽어도 수량이 1 그대로였고, 이렇게 어긋난 것만 4번에서 AI가 분류해 버그 후보가 됐습니다.

## 10. 진행 현황 (약 30초)

지금까지는 URL 하나로 보고서까지 끝까지 돌아가는 프로토타입을 먼저 완성하는 데 집중했습니다. 그래서 일곱 단계는 모두 동작하고, 로그인, 쓰기 차단, 모바일 화면, 확신 등급, AI 원인 분류, 재현 확인, PDF 보고서까지 갖췄습니다. 대신 오른쪽의 입력 검증 보강, 쓰기 허용 실행, 판정 못 함 줄이기 같은 부분은 뒤로 미뤄 두었고, 이제 이 뼈대 위에서 하나씩 발전시켜 나가겠습니다. 그럼 중간 결과를 보여 드리겠습니다.

## 11. 결과 요약 (약 25초)

저희 팀이 버그를 심어 만든 테스트 페이지 세 곳, 쇼핑몰, 관리 대시보드, 커뮤니티를 URL과 테스트 계정만 주고 한 번씩 검사했습니다. 쇼핑몰은 21분, 약 5달러, 관리 대시보드는 27분, 약 8달러, 페이지가 많은 커뮤니티는 39분, 약 11달러가 들었고, 버그 후보는 모두 다시 실행해 재현을 확인했습니다. 심어 둔 버그와의 대조는 아직 하지 않은, 채점 전 결과입니다.

## 12. Maison · 쇼핑몰 (약 25초)

쇼핑몰입니다. 파란 카드가 확신 높음으로, 2개 저장됐다면서 카드는 하나뿐인, 화면 값끼리 모순된 경우입니다. 앞에서 본 수량 버튼은 상품 페이지 세 곳에서 똑같았고, 필터 해제와 위시리스트 문제, 모바일 화면 결함 두 건도 나왔습니다.

## 13. Adminator · 관리 대시보드 (약 25초)

관리 대시보드에서는 Calendar 링크가 실제로는 채팅 화면을 가리켰고, 비교한 다른 에이전트도 같은 문제를 찾았습니다. 작업을 추가하거나 저장해도 목록에 반영되지 않았는데, 막힌 서버 요청이 없어서 쓰기 차단 때문은 아닙니다. 달력 Week 버튼과 모바일 알림 목록 잘림도 나왔습니다.

## 14. Agora · 커뮤니티 (약 25초)

커뮤니티 사이트에서는 입력 검증 문제가 나왔습니다. 제목을 300자로 제한한다고 표시하면서 301자가 그대로 들어갔고, 차단 이유와 커뮤니티 소개도 제한을 넘었습니다. 제출은 하지 않고 입력란과 카운터만 확인한 결과입니다.

## 15. 보고서 ① 첫 쪽 (약 20초)

결과는 이런 보고서로 나옵니다. 첫 쪽에서 버그, 화면 결함, 보류, 판정 못 함, 통과한 검사의 수와 주요 발견을 한눈에 봅니다. 제목은 AI가 쓰지만 숫자나 인용이 기록과 다르면 코드가 돌려보냅니다. 오른쪽은 앞에서 본 수량 사례의 상세입니다.

## 16. 보고서 ② 재현 절차 (약 20초)

발견 상세는 이렇게 생겼습니다. 확신 높음이었던 위시리스트 사례입니다. 시작 주소부터 다섯 단계로 따라 할 수 있는 재현 방법이 있고, 어떤 일반 규칙에 어긋나는지, 기대값과 실제값, 다시 실행해 재현됐는지가 붙습니다. 오른쪽은 실행 중에 찍은 증거 화면으로, 2개 저장됐다는 문구 아래 카드가 한 장뿐입니다.

## 17. 보고서 ③ 판정하지 못한 것 (약 25초)

보고서는 판정하지 못한 것도 숨기지 않습니다. 왼쪽은 판단 보류로, 의도를 알아야 하는 것은 사유별로 묶고, 위시리스트에서 장바구니로 옮기면 목록에서 빠져야 하는지처럼 사람에게 질문을 남깁니다. 오른쪽은 판정하지 못한 항목으로, 앞 단계가 실패해 뒤 검사를 못 한 것이 22건으로 가장 많았고, 사유와 건수를 그대로 보여 줍니다.

## 18. 다른 에이전트와 비교 (약 25초)

비교 대상은 GitHub 스타 약 4만 5천 개의 공개 AI 브라우저 에이전트, agent-browser의 dogfood 기능입니다. 같은 탐색 모델로 돌렸을 때 지적 건수와 비용은 dogfood가 유리했고, Calendar 링크나 수량 버튼처럼 둘 다 찾은 것도 있습니다. 저희는 동작 결함을 기대값과 실제값, 자동 재현으로 증명하고, dogfood는 문구와 사용성까지 넓게 지적합니다. 커뮤니티 사이트의 탐색 효율이 다음 과제이고, 채점 전이라 정확도 우열은 말하지 않겠습니다.

## 19. 한계와 향후 계획 (약 40초)

한계와 계획입니다. 첫째 비용입니다. Agora 실행에서 비용의 93%가 탐색과 계획이었고, 계획이 거부되면 전체를 다시 쓰는 구조 때문이었습니다. 시나리오 단위로 제출하고 화면 정보를 줄여 낮추겠습니다. 둘째, 입력 검증과 화면 판정입니다. 브라우저가 띄우는 검증 말풍선은 화면 글자에 없어 못 읽고, 서버 쪽 검증은 실제 제출이 필요한데 쓰기를 막아 두었습니다. 입력칸의 유효성 상태를 직접 읽고, 데이터 초기화와 함께 제출까지 하는 실행을 붙이겠습니다. 셋째, 판정 못 한 항목과 사용자 의도입니다. 앞 단계 실패는 실행 안정화로 줄이고, 의도나 시작 조건이 필요한 것은 계획 단계에서 사용자에게 바로 물어 그 답을 기대값으로 쓰겠습니다. 이후 정확도를 측정하고, 12월에 처음 보는 앱으로 최종 평가를 하겠습니다.

## 21. (예비) 근거 수치 상세

예비 슬라이드입니다. 발표 중에는 넘기지 않고, 근거에 대한 질문이 나오면 보여 드립니다. 연구마다 분류 기준이 다르기 때문에, 비율끼리 더하거나 직접 비교하지는 않습니다. 이동과 라우팅은 직접 대응하는 수치가 없어서, 멘토링과 ISO 25010의 기능 정확성을 근거로 들었습니다.
