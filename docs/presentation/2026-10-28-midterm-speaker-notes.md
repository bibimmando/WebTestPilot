# 중간발표 발표자 참고 (2026-10-28)

발표 중에 읽지 않는다. 질문이 나오면 답하는 데 쓴다.

## 1. 서버에 쓰는 요청을 왜 막나

**막는 것**
- 허용한 사이트 주소 안에서도 GET·HEAD 같은 읽기 요청만 통과시킨다. 주문·결제·글쓰기·저장처럼 서버 상태를 바꾸는 요청(POST·PUT·PATCH·DELETE 등)은 브라우저 단계에서 끊는다(`qa/src/browser.ts` `guardContext`).
- 허용한 주소 밖으로는 나가지 않는다. 다른 사이트의 이미지·글꼴·스타일시트를 읽는 요청만 예외로 허용한다. 예외를 두지 않으면 화면이 덜 그려져서, 앱 결함이 아닌 것을 결함으로 판정하게 된다.
- 로그아웃처럼 앱 설정에 적은 금지 주소는 누르기 전에 거절한다. 리다이렉트로 그 주소에 가는 경우도 막는다.
- 실시간 연결(WebSocket)은 읽기와 쓰기를 구분할 수 없어서 쓰기를 허용한 실행에서만 연결한다.

**이유**
1. **공유 서버 보호.** 테스트 사이트는 팀원과 다른 실행이 함께 쓰는 서버다. 한 번 실행할 때마다 주문·글이 쌓이면 다른 사람의 결과와 다음 실행의 시작 상태가 달라진다.
2. **되돌릴 수 없는 동작 방지.** 결제, 메일 발송, 데이터 삭제는 실수로 한 번만 일어나도 되돌리기 어렵다. 실제 서비스에 쓰게 될 때를 생각하면 기본값은 막는 쪽이 안전하다.
3. **재현성.** 같은 계획을 다시 돌렸을 때 같은 결과가 나오려면 시작 상태가 같아야 한다. 쓰기를 막으면 초기화 없이도 같은 상태에서 다시 시작할 수 있다.
4. **우리가 만든 실패와 앱 결함 구분.** 쓰기를 막은 뒤에 화면이 이상하면, 앱 탓인지 우리가 요청을 막아서인지 알 수 없다. 그래서 막은 쓰기 요청을 기록해 두고, 그 뒤의 실패는 "쓰기 차단으로 확인 불가"로 따로 분류한다. 버그로 세지 않는다. 예를 들어 Adminator의 작업 저장 문제는 그 단계에서 막힌 요청이 없었기 때문에 쓰기 차단 때문이 아니라고 말할 수 있었다.

**앞으로**
- 쓰기는 "앱 설정에 데이터 초기화 방법이 등록되어 있고, 사용자가 허용했을 때"만 켠다. 코드에는 이미 `allowWrites`와 초기화 설정 자리가 있다. 남은 일은 실제 사이트에서 초기화와 함께 돌려 보는 것이다(~11/14).

## 2. 입력 검증과 UI는 무엇이 되고, 무엇이 남았나

### 입력 검증 (일부 구현)
**되는 것**
- 공통 규칙 3개: 잘못된 입력은 받아들여지지 않고 안내가 나온다, 필수 입력을 비우면 제출되지 않는다, 수량은 1보다 작아질 수 없다.
- 화면에 보이는 글자로 판단할 수 있는 경우. 예를 들어 Agora에서 "301/300" 카운터를 읽어 글자 수 제한 위반을 찾았다.

**안 되는 것과 이유**
1. **브라우저 기본 검증 말풍선을 못 읽는다.** `required`나 `type=email` 같은 브라우저 검증 안내는 화면 글자(DOM 텍스트)에 없는 말풍선이라 지금 방식으로는 읽히지 않는다.
2. **서버 쪽 검증은 확인할 수 없다.** 잘못된 값을 서버가 거절하는지 보려면 실제로 제출해야 하는데, 제출은 쓰기라서 막혀 있다.
3. **계획이 약하다.** AI가 입력 검증 시나리오를 다른 영역보다 적게 세운다.

**발전 방향**
1. 입력칸의 유효성 상태(`validity`, `validationMessage`)를 브라우저에서 직접 읽어 말풍선 내용까지 비교한다.
2. 데이터 초기화와 함께 쓰기를 허용한 실행에서 실제 제출 후 서버 응답(오류 안내, 저장 여부)까지 확인한다.
3. 입력 폼이 있는 페이지에서는 입력 검증 시나리오를 반드시 세우도록 계획 검사를 보강한다.

### UI (일부 구현)
**되는 것**
- AI 없이 코드로 하는 품질 점검: 다른 요소에 가려진 버튼, 이름 없는 아이콘 버튼, 화면 밖으로 넘친 내용.
- AI 화면 판정: 계획에 적은 조건(예: 모바일에서 글자가 잘리지 않는다)을 스크린샷으로 판정하고, 다시 찍어 같은 결함이 보여야 확정한다. 세 사이트에서 화면 결함 3건이 나왔다.

**한계**
1. 화면 판정은 AI가 스크린샷을 보는 것이라 확신 등급이 낮고, 같은 화면도 판정이 흔들릴 수 있다.
2. 외부 이미지·글꼴이 막히면 화면이 덜 그려져 결함으로 오판할 수 있었다. 지금은 읽기 전용 정적 자원은 허용하도록 고쳤다.
3. 겹침·잘림은 측정 화면 크기에 따라 달라서 기준 크기(데스크톱·모바일 390px)를 정해 두고 본다.

**발전 방향**
1. 코드 점검 결과와 AI 판정이 같은 요소를 가리킬 때만 확신을 올린다.
2. 화면 크기를 몇 개 더 늘린다.
3. 화면 판정 결과도 사람 채점으로 오탐을 잰다.

## 3. 그 밖의 예상 질문

- **판정 못 함은 왜 생기나** (Maison 10/26 보고서, 35건)
  | 사유 | 건수 |
  |---|---|
  | 앞 단계 실패로 실행 안 됨 | 22 |
  | 자동화 실패로 분류 | 6 |
  | AI가 판단 불가 | 3 |
  | 시작 조건 준비 실패 | 3 |
  | 쓰기 차단 | 1 |

  대부분은 실행 안정화로 줄일 문제다. 사용자에게 의도와 시작 조건을 묻는 기능은 "시작 조건 준비 실패"와 "판단 보류"를 줄이는 쪽이다.
- **비교 대상이 적절한가.** agent-browser(Vercel Labs)는 GitHub 스타 약 4.5만 개(2026-10-27 확인)의 AI 브라우저 자동화 도구이고, dogfood는 그 안의 탐색형 QA 기능이다.
- **Playwright 공식 에이전트(planner·generator·healer)와는 비교했나.** 시도는 했지만 저희 환경에서 끝까지 돌리지 못해 비교 결과가 없다. 구조는 "계획 → 테스트 생성 → 실행"으로 비슷하다. 차이는 두 가지다. Playwright는 테스트 코드를 AI가 쓰고 healer가 실패한 테스트를 고쳐 통과시킨다. 저희는 코드를 틀로 찍어 내고, 실패는 고치지 않고 분류한다. 결과를 보고 기대값을 바꾸지 않기 위해서다.
- **11장 테스트 사이트.** 세 곳 모두 팀이 버그를 심어 만든 테스트용 사이트다. 심은 버그와의 대조(채점)는 발표 뒤에 사람이 따로 한다. 정답을 보면서 개발하면 결과가 사이트에 맞춰지기 때문이다.
