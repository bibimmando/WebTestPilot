# 1차 의견 — Claude

대상: [docs/design/V2_ARCHITECTURE.md](../../design/V2_ARCHITECTURE.md) 3.1. 근거: 첫 유료 실측, 10/12 Maison 결과 분석(개발용 버그 17개 유형별 탐지 결과).

## A. 성능: 이대로면 무엇을 잡고 무엇을 놓치는가

### A1. 가장 큰 위험 — "관찰한 값"을 기대값으로 쓰면 버그를 정답으로 굳힌다 (높음)

탐색 에이전트는 현재 앱(버그가 있을 수 있는)을 보고 계획을 만든다. 기대값 출처가 `observed`이면 **지금 화면의 값이 곧 기대값**이 된다. 결함 버전에서 탐색하면 결함 동작을 정상으로 고정한다. 첫 실측에서도 "증가 버튼을 눌러도 1"을 본 모델이 그 상태를 기대값으로 쓰지 않은 것은 우연이다(대상을 고정할 수 없어서였다).

- 제안: `observed`는 **대상 식별·시작 조건·회귀용**으로만 쓰고, 검사 대상 기능의 기대값 근거로는 쓰지 못하게 한다. 기대값 근거는 요구사항·화면 제약·**일반 웹 규범**(예: "필터를 해제하면 처음 목록으로 돌아온다", "증가 버튼은 값을 1 늘린다")만 허용. 일반 규범은 AI 추정이므로 결과는 "검토 대상"으로 가지만 탐지는 된다.
- 결함 버전과 정상 버전을 따로 탐색하는 평가(Q47)에서 이 문제가 바로 드러날 것이다.

### A2. 검사 표현력(oracle)이 버그 유형을 못 따라간다 (높음)

10/12 분석의 17개 유형을 현재 설계(M7까지 완성 가정)의 검사 표현으로 대조했다.

| 유형 | 예 | 필요한 검사 | 설계 3.1 |
|---|---|---|---|
| 상태 간 비교 | F4 필터 해제 후 목록 수가 처음과 같아야 함 | 이전 시점 값과 비교 | `expected_from`은 "다른 대상"만, "같은 대상의 이전 시점"은 없음 |
| 목록 전체 조건 | 카테고리 필터 후 모든 카드가 그 카테고리 | 각 항목에 대한 조건(all/each) | 없음 |
| 관계 | N1 카드 이름 = 도착 상세 제목 | 다른 대상 값과 비교 | M2 `expected_from` |
| 페이지 계산값 | N3 이동 후 scrollY=0, U1 scrollWidth>innerWidth | 스크롤·크기 같은 계산된 사실 읽기 | 없음 (`visual` AI 판단으로만) |
| 겹침·잘림·포커스·스타일 | U2·U3·U4·U5 | 요소 위치·CSS·focus 상태 | `visual`(이미지 AI)만 — 비싸고 불안정 |
| 쓰기 흐름 | F1·F2 wishlist·cart, V1·V3 주문 | 쓰기 허용 + 초기화 + 교차 페이지 | M5 |
| 경계값 | V5 정확히 8자 비밀번호 | 7/8/9 입력 비교 | 탐색 AI에 맡김, 근거는 화면 제약 |
| 로그인 흐름 | N4 로그인 후 원래 경로 | 로그인 + URL 읽기 | M5 + `read: url` |

- 제안: `read`에 **프로그램이 계산하는 사실**을 추가한다: `url`, `scroll`, `overflow`(scrollWidth vs viewport), `box`(위치·크기), `overlap(T#)`, `focused`, `style(속성)`, `items`(그룹의 각 항목 값 목록). 비교에 `previous(검사 ID)`(이전 시점 값), `all/any`(목록 조건), 수 비교(`<`, `>`, `≠`)를 추가. UI 문제의 대부분은 이미지 AI 판단 없이 이 사실들로 잡힌다. 이미지 판단은 마지막 수단.
- 이게 없으면 M7까지 완성해도 Maison 기준으로 기능·이동 일부(F3·N1·F4 정도)와 화면 넘침(U1)만 잡을 것으로 본다. Playwright Agents 10/12 결과(7/17)보다 낮을 수 있다.

### A3. 콘솔·네트워크 오류를 버리고 있다 (중간)

JS 오류, 4xx/5xx 응답은 기대값 없이도 잡히는 싼 신호다. 지금은 수집도 판정도 안 한다. 증거와 "검토 대상"으로라도 넣어야 한다.

## B. 구현 난이도

### B1. 범위 대비 일정 (높음)

남은 7주에 M1~M9. 특히 M3(사이트 탐색), M5(로그인·초기화·쓰기·승인), M6(보고서·PDF), M7(웹 화면)은 각각 큰 작업이다. 6명 중 지금 v2를 아는 사람은 사실상 없고(나와 Codex가 만들었다), `integration/`을 쓰던 팀이 TypeScript로 넘어와야 한다.

- 제안: M6·M7(보고서·웹 화면)은 엔진과 계약(`report.json`)만 먼저 고정하면 다른 팀원이 병렬로 만들 수 있다. 계약을 M3 전에 고정하자.
- 제안: C3(전처리기 재작성)는 이미 일어난 일이다. 팀 확인 때 "되돌릴지"가 아니라 "Python 담당자가 어떤 모듈을 맡을지"를 정해야 한다.

### B2. 자체 대상 식별 규칙이 복잡하고 깨지기 쉽다 (중간)

접근성 snapshot 텍스트를 우리가 파싱해 Target을 만든다. 오늘 `[cursor=pointer]` 한 줄 형태로 대부분이 깨졌다. Playwright 버전이 바뀌면 또 깨질 수 있다. 그룹 안 순서·동적 영역까지 넣으면 규칙이 더 늘어난다.

- 제안: 파싱 대신 Playwright의 `getByRef(ref).normalize()`가 만든 locator를 **후보**로 쓰고, 우리 규칙은 "검증"(유일성·같은 요소·값 의존 여부)만 한다. 0단계에서 문자열 조작 문제로 버렸지만, 문자열을 고치지 않고 그대로 쓰되 값 의존이면 거부하는 방식이면 단순해진다. 실험이 필요하다.

### B3. 두 단계(탐색 후 고정 실행) 구조의 비용 (낮음)

탐색 중에 이미 행동하고 다시 실행하므로 브라우저 시간이 두 배다. 비용은 모델 호출이 지배하므로 문제는 작다. 다만 탐색 중에 본 이상(A1의 "증가 안 됨")은 실행 전에 이미 증거가 있다 — `observations`를 검토 대상으로 바로 보고하면 실행 단계에서 못 잡아도 놓치지 않는다.

## C. 우선순위 제안

1. A1 기대값 근거 규칙 (작음, 성능에 가장 큼) → M1에 포함
2. A2 계산된 사실 읽기·이전 시점 비교·목록 조건 (중간) → M2를 키우고 시각 AI 판정(M4)을 줄임
3. B1 `report.json` 계약 조기 고정과 병렬 개발 → M3 전
4. A3 콘솔·네트워크 신호 (작음) → M4
5. B2 locator 후보 방식 실험 (작음) → M1~M2 사이
