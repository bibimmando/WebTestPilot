**사용자 승인 후 설계 문서 3.2에 반영했다 (2026-10-15).**

## 결론

구조(탐색 → 고정 계획 → 결정적 실행 → 재계산 대조 → 분류 → 재현)는 유지한다. 바꿔야 할 것은 **검사를 더 많이 추가하는 것보다, 기대값이 어디서 왔는지와 언제 관측했는지를 계약으로 묶는 것**이다. 이게 없으면 결함 버전을 탐색할 때 결함 동작을 정답으로 고정해 놓치게 된다.

## 합의한 단순화

- **적응 실행(4a)을 M4에서 뺀다.** 대신 계획·시도·완료·미실행·실행 여부 불명확을 원인별로 집계한다(작음). 행동 실행 실패율과 요구사항 검사 범위를 따로 보고하고, 평균 아래 숨은 특정 흐름의 반복 실패도 본다. 20% 기준은 재검토 신호로만 유지.
- **대상 식별:** Playwright `normalize()`가 만든 locator를 후보로 쓰는 실험은 작게 해 본다. 단, locator 코드 문자열을 실행하지 않는다는 기존 계약은 유지.

## 성능·일정 추정 (확인된 수치가 아님)

- Maison 개발 버그 17개 유형 기준, 설계 3.1을 M7까지 완성하면 한 번의 새 탐색에서 증거가 맞는 후보 **5~9개**, 위 변경을 넣으면 **7~11개** (Codex 추정). 10/12 Playwright Agents의 최초 실행 매칭 7개와는 지표가 달라 직접 비교하지 않는다. 독립 앱 성능으로 환산할 수 없다.
- 쓰기·로그인·초기화가 필요한 유형(F1·F2·V1~V5·N4)은 M5가 없으면 불가, 있어도 조건부.
- 난이도: M2·M3·M4·M5·M8·M9 상, M1·M6·M7 중. 11/19 안정화 기준선까지 실제로는 약 5주. 늦어지면 서버 배포 → 조건부 비교(Playwright Agents·agent-browser) → 시각 판정 순으로 줄인다.
