# Maison 의존을 줄이기 위한 일반화 평가 계획

작성일: 2026-10-13, 한국 시간. 이 문서는 평가 설계안이며 새로운 앱의 검사나 유료 AI 실행 결과가 아니다. 제품 소스는 수정하지 않았다.

## 1. 이전 제안에 추가해야 할 조건

Maison의 시나리오를 고정하고 Playwright로 반복 실행하는 것은 재현성·회귀 검사에 유용하다. 이것만으로 처음 보는 앱에서 기능을 찾아 시나리오를 만들고 검증하는 능력을 입증하지는 못한다. 두 능력을 별도로 평가해야 한다.

여기서 과적합은 모델의 추가 학습뿐 아니라 코드·프롬프트·압축 정책을 Maison 사례에 맞춰 반복 조정하는 과정에서도 생길 수 있다. “수량”을 특정 span에서 읽거나 “상품” 링크를 특정 URL 경로로만 인식하면 다른 앱에서는 실패할 수 있다.

현재 Maison 결과는 개발·회귀 기준으로 유지한다. 새 평가에서 기존 계획·selector·상품명·정답표를 전달하지 않고 공통 엔진으로 첫 검사를 수행할 수 있어야 일반화의 근거가 된다.

## 2. 평가를 세 종류로 분리

| 종류 | 입력과 방법 | 확인하는 능력 | 한계 |
| --- | --- | --- | --- |
| 고정 회귀 | 검토한 계획·기대·초기 상태를 그대로 실행 | 행동·대기·증거·비교의 재현성 | 처음 보는 기능의 탐색 능력은 평가하지 않음 |
| 구조 변형 | 같은 사용자 기능을 다른 DOM·데이터·표현으로 구현 | 대상 식별·관측 압축이 표면 구조에 의존하는지 | 같은 앱을 바꾸는 것만으로 새 앱 일반화가 입증되지는 않음 |
| 미사용 앱 평가 | 개발 중 쓰지 않은 독립 앱에서 새 계획 생성부터 실행 | 기능 발견·계획·실행·판정의 전달 가능성 | 지원 범위와 표본 수 안에서만 해석 |

세 종류의 결과는 합산한 단일 통과율로 보고하지 않는다. 저장 테스트를 다시 실행한 성공을 새 앱 탐색 성공으로 세지 않는다.

웹 에이전트 연구에서도 같은 사이트의 새 작업, 처음 보는 사이트, 처음 보는 도메인을 나누어 평가한다. 이 구분을 프로젝트의 개발·검증 분리에 적용한다. 모델의 사전학습에서 해당 사이트를 본 적이 없다는 보장까지 하는 것은 아니다. [Mind2Web 공식 데이터 분할](https://github.com/OSU-NLP-Group/Mind2Web#data-splits).

## 3. 개발 사례와 평가 사례를 앱 단위로 분리

| 구분 | 역할 | 결과를 보고 수정해도 되는가 |
| --- | --- | --- |
| 개발 세트 | Maison + 공개 로컬 회귀 fixture | 가능 |
| 검증 세트 | DOM·렌더링 방식이 다른 별도 앱 | 가능. 수정에 사용한 순간 개발 이력에 포함 |
| 최종 평가 세트 | 코드·프롬프트 조정에 사용하지 않은 독립 앱 | 고정 버전의 최종 측정에 사용 |

같은 앱의 상품 페이지를 무작위로 나누지 않는다. 공통 템플릿·컴포넌트·흐름이 양쪽에 남기 때문이다. 다른 이름의 Maison 복제 여러 개도 독립 앱으로 취급하지 않는다.

첫 단계의 제안은 개발용 Maison 외에 최소 두 개의 독립 앱을 검증용·최종 평가용으로 확보하는 것이다. 최소 하나는 다른 기능군을 가진 앱이어야 한다. 예를 들어 다른 구현의 검색·목록 앱과 폼·설정 앱을 고려할 수 있다. 사이트 이름과 실제 범위는 아직 선정하거나 실행하지 않았다. 이 작은 표본으로 웹 전체에 대한 일반화를 주장하지 않는다.

최종 평가 앱의 상세 실패를 분석해서 수정했다면 그 앱은 더 이상 미사용 평가 세트가 아니다. 이후 최종 측정에는 새 평가 앱을 확보하거나, 이미 사용한 평가라는 점을 명시한다.

## 4. 공통 엔진과 앱별 테스트 설정의 경계

### 공통 엔진이 맡을 것

- 관측에서 역할·이름·문맥·링크·현재 값을 읽고 유일한 대상을 확인한다.
- 관측된 목적지로 이동하며 값과 무관한 대상 식별을 유지한다.
- 실제 준비 상태, 행동 결과, checkpoint 사실, 비교 결과를 기록한다.
- 지원하지 않는 기능·모호한 기대·예산 중단을 명시한다.
- 특정 상품명, 특정 상품 경로, 버그 ID를 공통 알고리즘의 분기 조건으로 사용하지 않는다.

### 앱별 설정에 들어가도 되는 것

- 시작 URL, 승인된 테스트 계정과 seed, 데이터 초기화 방법.
- 검토된 요구사항과 기능 목표, 앱이 제공하는 준비 완료 조건.
- 해당 앱에서 실제 관측하고 검증한 테스트 locator와 목적지.

개별 테스트가 특정 앱의 이름·URL을 포함하는 것은 자연스럽다. 새 앱을 검사하려면 엔진 자체를 고치거나 상품마다 예외를 추가해야 하는 구조가 문제다. 기존 `maison_reset`도 명시적인 fixture 기능으로 분리해서 평가하며 일반 초기화 기능으로 간주하지 않는다.

최종 평가에서 허용하는 설정의 수준을 미리 고정한다. 특히 사이트별 selector를 사람이 작성해 제공한 실행과, 에이전트가 새로 발견한 실행은 구분한다. 고정 회귀는 전자를 사용할 수 있지만 새 앱 탐색 평가에는 이전 locator와 계획을 전달하지 않는다.

Playwright는 사용자에게 보이는 행동을 검증하고, role·이름 등의 사용자 관점 locator를 우선하며 고유 대상을 찾도록 권장한다. 이것은 DOM 구조 변경에 대한 의존을 줄이는 방법이며 모든 앱의 기능 의미를 자동으로 보장하지는 않는다. [공식 Best Practices](https://playwright.dev/docs/best-practices), [Locators](https://playwright.dev/docs/locators).

## 5. 구조 변형에서 확인할 것

| 변형 | 의도 | 올바른 결과 |
| --- | --- | --- |
| 초기 수량·목록 개수 변경 | 숫자 상수에 맞춘 검증 탐지 | 관측한 baseline과 변화량으로 비교 |
| DOM wrapper·요소 위치·CSS class 변경 | CSS·순서 의존 탐지 | 의미가 같은 고유 대상을 다시 식별하거나 명확히 실패 |
| main·footer에 같은 라벨 추가 | 첫 요소 선택과 문맥 손실 탐지 | 목표 영역의 고유 대상을 사용 |
| 카드 순서·데이터 순서 변경 | 첫 카드·첫 링크 의존 탐지 | 선택한 카드와 도착 상품의 관계를 검사 |
| 지연 로딩·재렌더링 | 고정 sleep·오래된 snapshot 의존 탐지 | 준비 조건 확인 후 최신 상태로 행동 |
| native control과 custom control | 한 위젯 구현 의존 탐지 | 지원 연산으로 처리하거나 미지원 범위를 명시 |
| 영문·국문 라벨 | 특정 영문 단어 규칙 의존 탐지 | 현재 관측과 제공된 목표를 기반으로 처리 |

기능을 바꾸지 않은 변형은 결과의 의미가 유지돼야 한다. 반대로 수량 증가·이동·검증 기능을 실제로 깨뜨린 변형은 실패를 탐지해야 한다. 정상 앱과 결함 앱을 쌍으로 확보하고, 모든 변형을 통과시키도록 assertion을 약화하지 않는다.

변형 앱이 같은 generator/template에서 만들어졌다는 사실도 manifest에 기록한다. 이를 독립 앱의 수처럼 부풀리지 않는다.

## 6. 입력과 정답 분리

에이전트에는 URL, 기능 목표, 필요한 정상 요구사항·권한·예산을 제공한다. 버그 위치·주입 여부·정답 action sequence·평가용 selector는 제공하지 않는다. 정답표는 실행 후 평가기에서 사용한다. 기본 프로그램의 evidence와 모델 요청 파일로 이 분리를 확인한다.

업무 규칙을 제공하는 것은 적절한 검사 입력이다. 예를 들어 “한 번 누르면 수량이 1 증가한다”는 검토된 기능 규칙을 입력할 수 있다. “이 앱의 특정 + 버튼이 고장났으니 그곳을 클릭하라”는 정답 힌트와 구분한다. 요구사항을 제공하지 않은 heuristic 검사에서는 후보 재현과 업무상 확정을 별도로 집계한다.

## 7. 비교와 지표

수정 전후 코드에 동일한 사례·초기 데이터·모델·스킬·effort·출력 상한·예산을 적용한다. 계획 생성 평가와 고정 실행 평가를 별도 표로 낸다. API 비용도 각 단계와 각 앱별로 나눈다.

| 지표 | 기준 |
| --- | --- |
| 탐색·계획 coverage | 평가 대상 기능 중 실제로 계획·검증한 비율. 선택하지 않은 기능도 남김 |
| 올바른 행동 완료 | 의도한 대상을 조작하고 요구된 흐름까지 수행. 다른 대상을 누른 성공은 제외 |
| 증거 완전성 | 선언한 필수 fact가 available이고 올바른 시점·대상에 연결됨 |
| 비교 정확성 | 정상/결함 fixture의 실제 값과 기대 비교가 맞는지 |
| 결함 탐지와 오탐 | 숨긴 정답표와 사후 대조. 정상 앱의 잘못된 후보도 집계 |
| 불확실성 처리 | 미지원·누락·보류를 통과로 바꾸지 않는지 |
| 반복 안정성 | 동일 조건의 반복 결과와 증거가 일치하는지 |
| 비용·시간 | 실행 전체와 증거 완전·정확한 결과 1건당 값. 중단된 검사의 소비 비용도 포함 |

앱별·기능군별 결과와 가장 낮은 앱의 결과를 함께 공개한다. Maison에서 좋아진 값이 다른 앱의 악화를 평균으로 가리지 않게 한다. skip·미계획·예산 중단도 분모에서 숨기지 않는다. 표본이 작을 때는 건수와 개별 실패를 공개하며 일반화가 증명됐다고 표현하지 않는다.

## 8. 단계별 진행 조건

1. 개발 세트에서 기존 정상 사례를 유지하고 알려진 관측·target·예산 실패를 해결한다. 무료 저장 증거와 로컬 fixture를 우선 사용한다.
2. 검증 앱에서 공통 엔진의 코드를 고치지 않고 첫 검사를 시도한다. 사이트별 우회 수정이 필요하면 그 내용과 비용을 기록한다.
3. 필요한 수정은 개발 세트에 일반적인 실패 fixture로 추가한다. 특정 앱의 상품명·DOM 경로로 분기하지 않는다.
4. 소스·프롬프트·스킬 버전과 평가 manifest를 고정한 뒤 미사용 앱을 측정한다.
5. 회귀 개선과 새 앱 개선을 따로 판정한다. 새 앱에서 증거 완전성·정확성이 악화하거나 오탐이 늘면 일반화 개선으로 승인하지 않는다.

목표는 과적합의 가능성을 없다고 선언하는 것이 아니라, Maison에 맞춘 수정이 다른 구조에서 실패하는지를 드러내고 개선 주장의 범위를 제한하는 것이다. 로컬 회귀 실행은 API 없이 가능하다. 새로운 AI 탐색·생성 성능 측정에는 별도의 유료 호출이 필요할 수 있으며 이 문서 작성 중에는 호출하지 않았다.
