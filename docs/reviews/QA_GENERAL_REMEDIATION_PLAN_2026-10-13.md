# 범용 QA 목표에 따른 수정 방향

작성일: 2026-10-13, 한국 시간. 기준은 루트 [AGENTS.md](C:/Users/lsc05/Documents/ChatGPT/WebTeste/AGENTS.md)다. 이 문서는 후속 수정안이며 제품 구현·새 앱 평가를 완료했다는 보고서가 아니다. 특정 사이트의 녹색 테스트 수보다 공통 능력의 정확성·재현성·비용을 개선한다.

## 1. 기존 실패를 일반적인 문제로 다시 정의

| 관측한 사례 | 공통 문제 정의 | 수정이 의존하면 안 되는 정보 |

이 정의를 사용해 호출자와 계약을 확인한 뒤 공유 함수에서 해결한다. Maison 결과는 원인을 발견한 증거로 유지한다.

## 2. 먼저 고정할 검증 기준

새 기능 구현보다 먼저 수정 전 기준을 보존한다. 계획·기대·초기 상태·모델·스킬·예산과 입력/증거의 출처를 기록한다. 고정 실행과 새로운 탐색 평가를 별도 명령·지표로 구분한다.

무료 로컬 사례는 목록뿐 아니라 폼·설정·숫자 표시·메뉴처럼 다른 문맥을 포함한다. 정상 동작과 결함 동작을 쌍으로 만들고, 라벨·초기 숫자·DOM 배치·중복 컨트롤·지연 렌더링을 바꿔 공통 실패가 재현되는지 검사한다. 이런 fixture 변형을 독립 앱 일반화의 증거로 과장하지 않는다.

독립 앱은 별도로 검증용과 최종 평가용으로 구분한다. 최종 평가 앱에서 기존 계획·selector와 숨긴 정답표를 모델에 전달하지 않는다. 아직 독립 앱을 선정·검사한 것은 아니다. 상세한 분할 기준은 [일반화 평가 계획](C:/Users/lsc05/Documents/ChatGPT/WebTeste/docs/reviews/QA_GENERALIZATION_EVALUATION_PLAN_2026-10-13.md)에 있다.

## 3. 수정할 큰 주제와 하위 작업

### 1장. 관측 정보 보존과 대상 식별

- `preprocessor`의 압축에서 검사에 필요한 객체와 관계를 먼저 보존한다. 목록은 객체명·이동 관계·조작 대상을, 폼은 필드·제약·제출 대상·검증 상태를 함께 읽을 수 있어야 한다.
- 기능 목표·현재 관측·영역 문맥을 기준으로 우선순위를 정한다. 모든 사이트에서 상품 경로를 가정하는 규칙을 넣지 않는다.
- checkpoint의 대상 binding을 실제 값과 독립적으로 확인하고, 현재 값을 읽은 뒤 고정한 기대와 비교한다. 모호함은 기록한다.
- 기존 전역 입력 예산·누락 집계·원본 증거와 고유 대상 검증은 유지한다. 전역 예산 증가만으로 문제를 숨기지 않는다.

완료 조건: 다른 숫자·라벨·DOM 문맥에서도 필수 대상을 고유하게 식별하고, 값이 기대와 달라도 available fact와 올바른 비교를 남긴다. 정보가 예산에서 빠졌다면 누락을 명시한다.

### 2장. 준비 상태와 실행·검증의 연결

- 앱별 seed/fixture에 초기 상태와 관측 가능한 준비 조건을 둔다. 공통 엔진은 조건을 확인하고 기한 초과를 명확히 기록한다.
- 계획 단계마다 의도·실제 대상·행동 결과·checkpoint·비교가 연결되게 한다. 행동 성공을 기능 성공으로 취급하지 않는다.
- 실제 locator·대기·assertion은 기존 Playwright와 수집/실행 계층을 활용한다. 실행 여부 unknown과 증거 부족 시 행동 반복 금지는 유지한다.
- API 없이 동작하는 고정 회귀가 다른 기능 문맥에서도 동일한 초기 상태와 결과를 유지하는지 확인한다.

완료 조건: 지연 로딩·재렌더링·중복 라벨에서도 준비 전 행동과 잘못된 대상의 성공 집계가 없고, 정상·결함 사례가 서로 다른 정확한 결과를 남긴다.

### 3장. 탐색과 반복 실행의 분리

- 처음 보는 기능은 실제 관측으로 탐색·계획한다. 계획 입력에 정보가 부족하면 제한된 추가 관측으로 해결할 수 있는지 검증한다.
- 검토된 계획·기대는 기존 `FixedDriver` 경로로 반복 실행한다. 이를 검토된 locator/assertion 기록과 연결한다.
- 실행 가능한 테스트 export가 필요한지는 이 경로의 정확성·재사용성 확인 후 결정한다. 전체 엔진 재작성이나 공식 내부 runner 복제부터 시작하지 않는다.
- 고정 회귀의 성공과 미사용 앱에서 새 계획을 만든 성공을 따로 보고한다. 사이트별 seed 설정과 사람이 제공한 selector도 구분한다.

완료 조건: 검토된 검사의 무료 반복 실행이 보존된 기대·증거로 재현되고, 독립 앱의 새 검사에서는 이전 사이트 계획이나 엔진 예외 분기 없이 필요한 기능을 검사한다. 독립 앱 검증 전에는 일반화 완료를 주장하지 않는다.

### 4장. 비용 계산과 판정에 필요한 증거

- 공통 비용 계산에서 텍스트·도구·이미지·출력·서버 도구 비용의 범위와 알 수 없는 사용량을 구분한다. 이미지 base64 바이트를 과금 토큰으로 취급하지 않는다.
- 사이트·이미지 압축률이 달라도 공급자와 모델의 단위를 따라 예약하며 실제 예산 부족은 계속 차단한다.
- 완전하고 검토된 사실의 비교 결과는 기존 프로그램 비교·고정 회귀를 활용한다. 업무 의미·UI·불확실한 기대에는 필요한 문맥과 별도 판단을 유지한다.
- 판정·재현 입력의 중복을 측정해 줄이며, 필수 사실·출처·실패 문맥을 제거해서 비용을 낮추지 않는다.

완료 조건: 정상적인 이미지 요청을 전송 크기 때문에 잘못 차단하지 않고, 실제 상한·미확인 단가/사용량은 처리한다. 동일 사례에서 비용 감소와 정확성·증거 보존을 함께 입증한다.

### 5장. 일반화 평가와 CI

- 각 공통 수정의 원인 fixture와 다른 구조의 정상·결함 사례를 관련 CI에 연결한다. 개발 사례를 반복 실행하는 검사와 미사용 앱 평가를 분리한다.
- 앱별·기능군별로 행동 정확성, 필수 사실 확보, 비교·판정 정확성, 오탐·미탐, 불확실성, 반복 안정성, 비용·시간을 기록한다.
- skip·미계획·보류·중단을 숨기지 않고 이전 결과와 비교 조건을 보존한다. 새로운 unsupported 범위도 기록한다.
- 최종 평가 결과를 보고 수정한 앱은 이후 개발 이력에 포함한다. 여러 사이트의 평균만으로 일부 앱의 악화를 가리지 않는다.

완료 조건: 공통 수정이 기존 회귀를 유지하고 다른 구조에서도 성립하는 근거가 있으며, 독립 앱 측정 없이 일반화 성능을 주장하지 않는다. 알려진 버그 ID 적중률을 제품 목표로 대체하지 않는다.

## 4. 진행 방식

각 장에서는 한 공통 원인씩 수정하고 관련 무료 검증을 실행한다. 정확성·증거·예산 중단 같은 관측된 공통 결함은 큰 구조 변경을 기다리지 않고 해당 책임 위치에서 해결한다. 1장의 관측·대상 계약을 안정시킨 뒤 2~3장의 실행 경로를 확장하고, 비용 예약 오류는 이미지 검사가 필요한 시점보다 먼저 해결한다.

여러 장의 모델·시나리오·초기 조건을 동시에 바꾸지 않는다. 구조 변경과 단순 결함 수정을 분리해 영향과 비교 조건을 남긴다. 유료 AI 평가는 기존 사용자 승인 범위와 한도 안에서만 수행한다. 이번 문서 작성에는 유료 호출과 제품 소스 수정이 없다.

다음 구현의 첫 문제는 “Maison의 링크를 살리기”가 아니라 **제한된 관측 예산에서 검사에 필요한 객체·관계·대상을 보존하고 값과 독립적으로 읽기**다. 목록·폼 등 서로 다른 문맥에서 이 조건을 검증하는 것이 시작점이다.
