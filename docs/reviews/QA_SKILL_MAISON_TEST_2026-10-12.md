## 실행 기준

- 대상: `http://13.124.7.113:8081/` 오류 주입 사이트.
- 코드: `integration/`의 현재 `staged/3` 파이프라인. 이번 두 실행 사이에 제품 코드를 수정하지 않았다.
- 흐름: FIFO URL 수집 → 페이지 전처리 → Opus 계획 → Sonnet 실행 에이전트의 실제 Playwright MCP 조작 → 증거 후처리 → 별도 Sonnet 판단 → 후보에 대한 추가 재실행 → 보고서.
- 계획 모델: `claude-opus-5-5`, 실행·판단 모델: `claude-sonnet-5-5`.
- 공식 Claude API와 등록된 `webtestpilot-qa-test-planner` 스킬의 고정 버전을 사용했다. 실행·판단 모델에 스킬을 전달하지 않는다.
- `--maison-reset --allow-writes`: 매 페이지 시작과 후보 재실행 전에 Maison의 전역 상태를 시드 상태로 되돌린다. 다른 사용자가 동시에 검사한다면 상태를 공유하므로 주의해야 한다.
- 별도 사이트 요구사항은 제공하지 않았다. 관측 UI와 잠정적 기대에 기반하여 AI가 계획을 작성했다.
- viewport는 1280×800. password/file 입력, resize/scroll/hover 전용 동작은 현재 실행 계약에 없다.
- `/gt.json` 정답 목록과 GitHub의 버그 주입 코드는 검사 AI에게 제공하지 않았다. 정답표는 실행 결과 평가에만 사용한다.
- 배포 서버의 정답표는 활성 버그 **17개**다. 저장소 main README의 빈 버그 목록과 다르므로 배포 서버의 목록을 기준으로 평가한다.
- 실행 전후 정답표는 생성 시각을 제외하고 같았고, 제품 Python 파일의 SHA-256도 유지됐다.

### 확인한 실패와 누락

1. `/products`의 행동 실행은 완료됐으나 판단 응답이 FN-001에 속하지 않는 action ID를 제시했다. 현재 검증 코드가 전체 응답을 거절하여 이 페이지의 8개 판단이 최종 findings에 저장되지 않았다. 원본 응답은 별도로 남아 있다.
2. 같은 FN-001의 원본 응답은 “ALL을 눌러도 2개가 유지되고 13개로 복원되지 않았다”고 설명하면서 verdict를 `passed`로 작성했다. 버그 F4에 해당하는 실제 변화 누락과 관련이 있으나, 프로그램이 저장한 탐지 결과는 아니다. 설명과 verdict의 모순도 확인됐다.
3. `/about`, `/wishlist`의 이동 후 복귀 버튼 탐색이 `target_not_found`로 중단됐다. 실행 실패를 사이트 버그로 집계하지 않았다.
4. 메뉴를 열고 닫는 UI 시나리오는 최종 닫힌 화면만 캡처한 경우가 있어 열린 메뉴의 가림·잘림을 확인하지 못했다.
5. `/wishlist`는 매 페이지 초기화로 빈 목록에서 시작했다. 빈 페이지의 표시·링크 검사만으로는 “담은 상품이 목록에서 빠지는” F1을 검증할 수 없다.

## 2차 확장 결과

- 12개 URL 모두 전처리 수집 완료. FIFO로 진행했으며 수집된 URL의 그래프상 최단 깊이는 홈 0, 나머지 11개 1이었다. 상품 상세에서도 링크로 도달한 상태와 기능 흐름을 검사했다. 사이트 전체 또는 더 깊은 URL을 모두 검사한 실행은 아니다.
- 크롤러는 `max_pages`로 정상적으로 범위 제한에 도달했다. 60분 시간 상한·360회 API 상한에는 도달하지 않았다. 남은 큐는 29개다.
- 다만 프로그램 종료 코드는 **1**이었다. Arc 상품 상세의 판단 응답 검증 오류가 있어 전체 성공으로 처리되지 않았다.
- 112개 계획 모두 실행 결과 레코드가 있다. 실행 완료 **85개**, 미완료 **8개**, 실행되지 않음 **19개**. 계획 대비 실행 완료율은 **75.9%**다.
- 최종 findings에 저장된 판단은 **98개**다: 정상 66, 보류 29, 후보 3. 나머지는 Arc의 판단 응답 전체 거절에 포함된 7개와 finding 증거 참조 검증 실패 7개다.

- MCP/실행 시도 156개 중 executed 146, not_executed 10. executed에 기록된 보조 클릭이 원래 의도한 검사 대상을 정확하게 누른다는 보장은 없으므로 시나리오 단위 판정도 필요하다.

### F4: 수집했지만 판단에서 놓친 오류

2차 `/products`의 FN-001은 LIGHTING → ALL을 실제 클릭했다.

| 시점 | 저장된 URL | 저장된 상품 수 |
|---|---|---:|
| 시작 | `/products` | 13 |
| LIGHTING 클릭 후 | `/products?collection=lighting` | 2 |
| ALL 클릭 후 | `/products?collection=lighting` | 2 |

그러나 저장된 판단은 `passed`였고, actual에는 “ALL 클릭 후 /products로 돌아오고 13개가 복원됐다”고 썼다. 해당 after_snapshot은 그런 변화를 보여주지 않는다. **증거 수집 성공과 판단 성공은 별개**라는 사례다.
1차도 같은 증상이 있었지만 잘못된 action ID 때문에 판단 응답 자체가 거절됐다.

## 개선 우선순위

1. **행동 실패 뒤 snapshot·flow 상태 복구.** `action incomplete` 후 stale snapshot이 반복되고, 보정 실패가 뒤 시나리오 및 재현 행동을 함께 막는다. 최신 snapshot의 등록·반환을 일관되게 하고, 독립 시나리오 시작 상태 복원 및 새 재현 상태로의 진입을 보장해야 한다.
2. **판단 입력과 참조 검증 개선.** 시나리오별 필요한 전후 상태·변화·증거 ID를 좁혀 전달한다. 다른 시나리오의 ID를 낸 응답에는 예산 내 유한한 수정 경로를 둔다. 원본 응답을 자동으로 정상으로 바꾸지 않는다. F4처럼 수치·URL 변화와 설명이 충돌하는 경우를 검증할 수 있어야 한다.
3. **전처리의 고유 기능 정보 유지.** 아이콘 버튼의 주변 텍스트·SVG/접근성 단서, Quantity 같은 그룹 소속, 관련 링크와 href를 우선 보존한다. 흔한 footer가 상품별 버튼·링크 정보를 밀어내지 않도록 한다. 목적이 없는 버튼을 임의로 클릭하는 것으로 해결하지 않는다.
4. **검사 상태별 UI 이미지와 재현.** 열린 메뉴를 검사하려면 열린 시점의 이미지를 남긴다. 초기 화면 결함은 행동이 0개여도 같은 시작 상태에서 다시 캡처해 재현할 수 있어야 한다.
5. **공통 기능 검사와 준비 조건 확장.** 공통 뉴스레터·헤더 기능은 적절한 공통 회귀 범위로 묶고 페이지별 고유 기능에 행동 예산을 배정한다. 그 후 checkout/로그인 준비, 제한된 resize·scroll·focus 관측을 명시적으로 추가한다.

스킬 적용으로 실제 결과 확인을 포함한 계획이 작성되었지만, 그것만으로 실행 성공·판단 정확도·탐지율 향상이 입증된 것은 아니다. 현재 결과에서는 위 1~4를 해결한 뒤 같은 조건에서 재검사하는 것이 우선이다.

## 결과 해석 기준

- URL 수집 완료, 시나리오 실행 완료, 정상 판정, 버그 후보, 재실행 확정은 각각 다른 단계다.
- `test_status=not_run`은 실제 행동이 하나도 없다는 뜻으로만 쓰이지 않는다. 현재 코드에서는 보류·실행 일부 실패·unplanned가 있어 페이지 전체 통과를 선언할 수 없는 경우에도 이 값이 된다. 개별 시나리오 결과를 함께 읽어야 한다.
- `confirmed`는 코드가 추가 1회 재실행 결과를 바탕으로 붙인 상태다. 최초 설계의 3/3 재현 보장은 현재 구현에 없다.
- 정답표와 불일치하는 후보를 곧바로 오탐으로 단정하지 않는다. 미등록된 추가 문제 또는 불충분한 증거를 구분한다.
- 현재 호출 코드가 저장한 입력·출력 토큰을 집계했다. 공급자의 실제 청구 금액이나 code execution 부가 비용은 이 숫자만으로 확정하지 않았다.
