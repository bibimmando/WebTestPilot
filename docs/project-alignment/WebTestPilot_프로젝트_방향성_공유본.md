# WebTestPilot 프로젝트 방향성 공유본

팀 검토용 | 논의 기준: 2026-10-08 | 버전 1.0

이 문서는 Q1~Q66 논의의 최종 입장을 하나의 프로젝트 방향으로 정리한 자료다. 대화 도중의 제안보다 후반에 합의한 결정을 우선 반영했다. 설계 목표를 설명하는 문서이며, 모든 기능의 구현 완료나 팀 전체의 승인 완료를 뜻하지 않는다. 세부 연결 규격은 팀이 방향성을 확인한 뒤 정한다.

## 1. 한눈에 보는 프로젝트

WebTestPilot은 개발·QA 단계의 승인된 웹사이트를 자동 탐색·검사하고, 페이지별 결함 후보의 재현 절차와 증거를 정리한 PDF를 제공하는 QA 보조 도구다.

- 자동화 대상: 검사할 기능 발견, 검사 행동 준비·실행, 문제 후보 판단, 추가 재현, 증거·보고서 정리.
- 사람의 역할: 제공된 결과를 실제로 검증하고, 결함 여부를 최종 확인하고, 수정에 착수한다.
- 주 사용 환경: 테스트 계정·가상 데이터를 사용하는 개발팀의 로컬·스테이징 사이트.
- 핵심 결과물: 구조화된 JSON, 실제 증거 파일, 실행 전체를 정리한 단일 PDF.
- 사용자 화면: 입력, 실행·중지, 진행 상태, 필요한 승인·준비 안내, 결과 다운로드, 보고서 재생성.
- 범위: 기능·입력 검증·라우팅·UI 네 범주, PC Chrome과 모바일 화면 크기의 반응형 검사.

사용자가 페이지별 테스트 스크립트나 상세 클릭 순서를 작성해야 하는 도구가 아니다. 시스템이 기능과 검사 행동을 발견하는 자율 탐색을 핵심으로 유지한다. 단, URL 하나로 사이트의 모든 결함을 발견한다고 보장하지 않는다.

## 2. 제공하려는 가치와 성공 기준

QA 담당자가 사이트를 살펴보고 테스트를 준비·실행하는 부담과, 발견한 문제의 재현 절차·증거를 정리하는 부담을 줄이는 것이 목적이다. AI 결과를 무조건 신뢰하게 만드는 대신, 실제 행동과 근거를 제공해 검증하기 쉽게 만든다.

성과는 수집한 페이지 수나 입력 크기 감소만으로 판단하지 않는다. 실제 검사를 수행했는지, 결함 후보가 정확한지, 제공한 조건으로 재현되는지, 보고서가 검증에 필요한 자료를 담고 있는지, 시간·API 비용은 얼마인지로 확인한다.

정확한 코드 원인 진단과 자동 수정은 필수 결과물이 아니다. 개발자가 문제를 확인하고 조사·수정에 착수할 수 있는 자료를 책임 있게 제공한다.

## 3. 사용자 입력과 실행 환경

| 구분 | 제공하는 정보 | 원칙 |
|---|---|---|
| 기본 | 시작 URL, 검사 허용 범위와 행동 | 승인된 대상만 검사하고, 단순한 기본 설정을 제공한다. |
| 필요한 실행 준비 | 테스트 계정, 로그인 상태, 승인된 초기화·데이터 준비 방법 | 필요한 검사에만 요구하고, 없으면 가능한 검사와 제한을 구분한다. |
| 선택 문맥 | 사이트의 짧은 설명, 기존 요구사항, 중요한 기대 동작 | 상세 테스트 스크립트를 새로 쓰도록 요구하지 않는다. |
| 실행 한도 | 프로그램의 기본값과 운영 설정 | 사용자가 반드시 시간·토큰 예산을 계산해 입력하지 않는다. |

추가 정보를 준비하는 부담은 기존 테스트 스크립트 작성 부담보다 작아야 한다. 기존 설명서나 요구사항이 있다면 재작성보다 활용을 우선한다.

기본 로그인을 지원하고, 자동 준비가 어려운 경우 사용자가 로그인 상태를 준비할 수 있는 보완 경로를 제공한다. CAPTCHA, 복잡한 외부 인증·다단계 인증의 자동 해결은 초기 필수 범위가 아니다.

개발은 로컬에서 진행한다. 막바지 AWS 서버 배포는 추가 목표로 검토한다. 서버 버전은 허용된 사용자가 서버에서 접근 가능한 승인된 사이트를 검사하는 형태로 시작하며, 누구나 임의 URL을 검사하는 공개 서비스는 제외한다. 서버가 사용자 PC의 로컬 사이트나 로그인 상태에 자동 연결된다고 가정하지 않는다.

## 4. 검사 범위와 판단 기준

| 범주 | 검사 대상 | 판정 근거와 제한 |
|---|---|---|
| 기능 동작 | 버튼·폼·검색·조회 등 기능의 결과와 짧은 연결 흐름 | 명시된 기능·요구사항 등 확보한 기대 조건과 실제 결과를 비교한다. |
| 입력 검증 | 필수값·형식·범위 등 확인 가능한 제약의 처리 | 화면 안내, HTML 제약, 제공된 요구사항 등 근거를 남긴다. |
| 이동·라우팅 | 내부 링크 도착, 기능 실행 후 이동, 연결된 화면 전환 | 관찰한 목적지와 실제 URL·화면을 비교한다. |
| UI 표시·조작 | 필요한 정보·컨트롤의 가림, 잘림, 겹침, 누락 등 | 정보 확인이나 조작 방해를 중심으로 판단한다. 미적 취향은 제외한다. |

사이트가 어떤 종류인지 알아내는 것과, 그 사이트의 정상 업무 규칙을 아는 것은 다르다. AI는 사이트의 문맥과 관찰을 활용해 검사 대상을 선택하지만, 근거 없는 업무 규칙을 확정하지 않는다. 명세가 없는 의도·디자인 문제는 확정 결함 대신 검토 대상으로 구분한다.

PC는 Chrome 기준으로 검사한다. 모바일 화면 크기에서는 반응형 UI와 메뉴·모달·버튼 접근 등 화면 조건에 따라 달라지는 상호작용을 추가 검사한다. PC의 모든 기능 검사를 모바일에서 그대로 반복하는 것을 기본으로 삼지 않는다.

PC와 모바일의 배치가 다르다는 사실만으로 버그라고 판단하지 않는다. 요구되는 정보·기능에 접근할 수 있는지와 확보한 기대 조건이 기준이다. 모바일 해상도 검사 결과를 실제 휴대폰·Safari·모든 브라우저 호환성 검증으로 표현하지 않는다.

## 5. 전체 실행 흐름

1. URL·허용 범위를 설정하고 필요한 로그인·초기 상태를 준비한다.
2. 범위와 실행 한도 안에서 페이지·기능 상태를 방문하고 전처리한다.
3. 현재 관찰과 사이트·흐름 문맥을 AI에 전달한다.
4. AI가 검사할 기능, 행동, 기대 조건과 관찰 대상을 선택한다.
5. 프로그램이 권한·범위·실행 한도를 확인하고 Playwright MCP로 실제 행동을 수행한다.
6. 행동 전후 상태·화면·오류를 기록하고, 기대 조건과 실제 결과를 비교한다.
7. 후보가 발생하면 발견 당시 기록을 보존하고, 가능한 경우 초기 상태를 준비해 추가 1회 재현한다.
8. 검증 상태를 저장하고 다음 페이지·연결 흐름을 검사한다.
9. 정상 종료·한도 도달·사용자 중지 시 실제 완료 범위와 부분 결과를 JSON으로 정리한다.
10. 보고서 AI가 JSON과 연결된 증거를 문서로 정리하고, 렌더링을 거쳐 실행 전체의 단일 PDF를 생성한다.

모든 원본 페이지를 먼저 수집한 뒤 한 번에 AI에 넣는 방식이 아니라, 관찰·검사·새 관찰을 점진적으로 반복한다. 초기 기준 실행에서는 범위와 한도 안에서 방문한 독립적인 페이지·기능 상태의 요약을 AI가 검토하도록 한다. 선택적 AI 호출은 이후 비용 감소와 미탐 증가를 함께 측정한 뒤 적용한다.

검사는 URL 방문만으로 완료되지 않는다. 동일 URL의 로그인 상태, 펼쳐진 메뉴, 입력 결과 등도 의미 있는 상태다. 관련된 짧은 다중 페이지 흐름에서는 상태를 유지하고, 독립 검사와 재현에 필요한 시점에 초기화한다.

## 6. AI·프로그램·사이트 개발자의 역할

| 주체 | 맡는 역할 | 맡지 않는 역할 |
|---|---|---|
| AI | 기능 발견, 검사 선택, 다음 행동, 관찰 해석, 근거 있는 판단, 문서 정리 | 허용 범위 확대, 사실 없는 판정, 임의 DB 초기화, 증거 이미지 생성 |
| 프로그램 | 범위·권한·한도 확인, 도구 실행, 관찰·증거 기록, 형식 검증, 실제로 확인 가능한 조건 검사 | AI의 계획만으로 실행·통과를 선언하는 처리 |
| 대상 사이트 개발자 | 테스트 계정·데이터와 승인된 reset/seed 또는 분리 환경 제공 | 모든 페이지의 검사 스크립트를 사전에 작성할 의무 |
| 결과를 받는 담당자 | PDF·증거를 보고 실제 결함 여부 확인과 수정 착수 | 프로그램 안에 검토 상태를 입력할 의무 |

AI의 초기 입력은 세 묶음으로 구성한다.

- 사이트 공통 문맥: 사용자 설명, 발견한 기능, 허용 행동, 준비 가능한 초기화 절차.
- 현재 페이지 관찰: URL, 컨트롤·폼·제약·링크·오류, 증거 참조, UI 검사에 필요한 이미지.
- 현재 검사 흐름: 목표, 시작 조건, 이전 행동과 결과, 기대 동작과 근거.

사용자 제공 정보·관찰 사실·AI 추정을 구분한다. 이전 페이지의 원본을 무제한 누적하지 않고 필요한 요약과 증거 참조를 사용한다. 웹페이지 안의 문구는 검사 대상 데이터이지 실행 권한을 바꾸는 지시가 아니다.

공통 브라우저·탭을 사용하고, AI의 행동이 공통 실행·증거 기록 경로를 거치도록 연결한다. 자유로운 Python·JavaScript 생성 코드를 제한 없이 실행하는 방식은 초기 범위에서 제외한다.

## 7. 실행 제한·초기화·재현

기본 전략은 기능을 넓게 발견하고 관련된 짧은 흐름까지 수행하는 균형형이다. 시간·API 사용량·행동 수·변화 없는 반복에 상한을 두고 프로그램이 강제한다. 사용자에게 예산 계산을 필수 입력으로 요구하지 않는다.

실행 전에 허용한 행동은 자동 수행한다. 새로운 권한이 필요하거나 허용 여부가 불명확한 행동은 승인 요청으로 처리한다. 실결제·외부 발송·운영 데이터 삭제는 초기 범위에서 제외한다. 답이 없거나 거절되면 의존 검사는 보류·미완료로 남기고 가능한 독립 검사를 이어간다.

초기화는 등록된 승인 절차만 호출·확인한다. AI는 필요한 초기 상태를 선택할 수 있지만 임의 복구 명령을 만들지 않는다. 초기화 연동이 없으면 관찰·비변경 검사 등 가능한 범위를 진행하고, 상태 준비·복구가 필요한 검사는 보류한다.

한 실행 환경에서는 작업 하나를 활성 실행하고 여러 사이트는 순차 처리한다. 중지 시 완료된 검사와 증거를 보존한다. 종료된 프로그램의 중간 지점 자동 복구는 초기 필수 범위가 아니다.

자동 재현은 최초 발견 시 실제 수행한 행동·입력값·시작 조건을 추가 1회 실행하는 것이다. 새로운 AI 탐색으로 대체하지 않는다. 기대 동작의 근거와 현상의 반복 여부는 별도로 판단한다.

- 근거와 반복 관찰 확보: 해당 시스템 검증 결과를 표시한다.
- 기대 동작 불명확·재현 실패: 추가 검토 대상으로 남기고 최초 증거를 삭제하지 않는다.
- 도구·로그인·초기화 등 실행 준비 실패: 검사 미완료와 사유를 남긴다.
- 검사 통과: 실제로 완료한 검사 범위의 결과이며 사이트 전체 정상 보장이 아니다.

종료 후 JSON 정리·보고서 생성 자원을 전체 상한 안에서 확보하는 원칙을 둔다. 배분 수치는 초기 실험으로 정한다.

## 8. 증거와 페이지별 보고

검사 계획, 실제 실행, 판정을 구분해 기록한다. 계획 생성은 실행이 아니고, 클릭 완료는 검사 통과가 아니다. 기대 동작·실제 관찰·시작 조건·실제 행동·재현 결과를 증거와 연결한다.

스크린샷은 행동 전후 자동 기록을 기본으로 한다. 최초 화면, 발견 당시, 추가 재현 당시의 증거를 구분하고 초기화 전에 보존한다. UI 증거는 현재 보이는 화면을 중심으로 하고 전체 페이지 사진은 필요 시 보조한다. 화면 크기·스크롤 위치 등 조건을 함께 남긴다.

사진 저장과 모델 전달은 구분한다. 기능·입력·라우팅 검사는 구조화된 관찰 중심으로, 시각적 UI 검사는 필요한 이미지·위치 정보와 함께 시작한다. 촬영 실패를 사이트 버그로 판정하지 않으며, 증거 부족은 표시한다. 이미지를 AI로 생성하거나 사실을 바꿔 증거를 채우지 않는다.

페이지가 다르면 유사한 문제라도 별도 항목으로 보고한다. 같은 페이지의 동일 문제는 화면 조건별 증거를 함께 표시한다. 다른 상태·기대 조건의 문제는 구분한다. 동일 조건의 반복 발견과 재현은 새 결함으로 세지 않는다. 추정한 코드 원인으로 여러 페이지의 발생 위치를 통합하지 않는다.

## 9. JSON·PDF·웹 화면

JSON은 프로그램 결과의 사실 원본이다. PDF에는 실행 범위·실제 검사·종료 이유·미완료 범위, 페이지별 문제, 기대·실제 결과, 재현 절차·조건, 최초 발견·추가 재현 결과, 주요 스크린샷·로그를 포함한다. 재현 근거가 확보된 문제와 검토 필요 후보·미완료 검사를 구분한다.

보고서 AI는 문장·요약·레이아웃을 정리하되, JSON과 증거에 없는 사실·원인·수치·판정·재현 성공을 추가하지 않는다. 레이아웃 참고 이미지는 스타일 자료이며 결함 증거가 아니다. 실제 PDF 파일은 문서 렌더링 단계에서 생성한다.

실행 전체를 한 PDF로 제공한다. 예산 종료나 중지 시에도 실제 확보된 부분 결과를 정리한다. PDF 생성 실패 시 JSON과 증거를 보존하고 재생성 옵션을 제공한다. 재생성은 저장된 결과로 보고서만 다시 만들며, 새 검사를 자동 시작하지 않는다. AI 실패 때 별도 기본 PDF를 반드시 생성하는 방식은 채택하지 않는다.

웹 화면의 필수 기능은 입력, 시작·중지, 진행 상태, 필요한 승인·준비 안내, JSON·PDF·증거 다운로드, 보고서 재생성이다. 담당자 검토 입력, 판정 수정, 이슈 배정·협업 관리와 외부 이슈 도구 연동은 제외한다. 사람이 확인하지 않은 결과에 담당자 확인 완료를 표시하지 않는다.

비밀번호·API 키·세션 등 비밀값은 모델 입력·공유 결과에서 보호한다. 텍스트 마스킹만으로 화면 속 민감정보가 제거된다고 가정하지 않는다. 초기 적용 환경은 승인된 테스트 계정·가상 데이터로 제한한다.

## 10. 평가 설계

개발용·검증용·최종 평가용 사이트를 분리하고, 사이트·템플릿 계열 단위로 나눈다. 같은 사이트의 정상·결함 버전과 파생 화면이 개발용과 최종 평가용에 나뉘어 들어가 평가가 유출되지 않도록 한다. 색·문구 변경만으로 새로운 구조라고 보지 않는다.

검사 모델은 매 실행에서 사이트 한 버전과 허용된 문맥만 본다. 정상 비교 사이트·결함 라벨·주입 위치·평가 정답은 주지 않는다. 평가자는 정답 결함의 페이지·조건·기대/실제 결과·재현 방법을 보유한다. 정상 버전도 독립 실행해 오탐을 측정한다.

주요 지표는 페이지별 결함 발생 사례의 탐지율·보고 정확도, 자동 재현 결과, 보고서 독립 재현 가능성, 완료·미완료 범위, 실행 시간·토큰·실제 API 비용이다. 반복 발견은 중복 성공으로 세지 않는다. 최종 정답 구조와 지표 수식·집계 규칙은 평가 전에 고정한다.

동일 주력 모델·권한·사전 정보·자원 상한에서 기본 Claude+MCP 자율 탐색과 전체 시스템을 비교해 전처리·흐름·증거·재현 관리의 효과를 확인한다. 기본 비교군에도 필요한 관찰 도구와 충분한 검사 지침을 제공한다. 모델 역할 분리 실험은 별도로 수행한다.

최소 실행 정보 조건과 짧은 설명·요구사항 추가 조건을 별도 평가한다. 정답 힌트는 어느 조건에도 제공하지 않는다. 개발용 정상·결함 사례는 프롬프트·규칙·도구·예시 개선에 사용하되, API 호출 자체를 모델 학습으로 취급하지 않는다.

정량 평가는 정답이 있는 최종 벤치마크를 중심으로 한다. 승인된 상용 사이트는 현실 적용 사례로 활용하며, 전체 결함 정답이 없을 때 전체 탐지율을 계산했다고 주장하지 않는다. 상용 QA 제품 비교는 추가 실험으로 검토한다.

기술 벤치마크와 보고서 독립 재현 시험을 우선한다. 실무 QA 시간 비교는 경험자 참여·실험 여건 확보 시 추가한다. 내부 팀원·초보자 실험만으로 산업 현장 시간 절감률을 주장하지 않는다. 시행할 경우 준비·검사·오탐 확인·재현·보고서 보완 시간을 포함하고 품질과 전체 소요 시간도 함께 측정한다.

## 11. 개발 순서·팀 역할·자원

개발은 고정 주차별 할당보다 의존 관계와 통과 기준으로 진행한다. 다음 단계 준비는 병행하되 전체 연결 확인을 우선한다.

1. 방향성 문서를 팀과 공유하고 목적·범위·제외 사항을 확인한다.
2. 팀 간 최소 입출력·실행·증거·결과 연결 규격을 합의한다.
3. 기존 전처리·AI 프로토타입을 재사용해 짧은 흐름 하나를 연결한다.
4. 실제 행동·새 관찰·판정·추가 재현·JSON까지 확인한다.
5. 네 범주, 로그인, 모바일 반응형, 안전한 초기화·종료·실패 처리로 확대한다.
6. 증거가 포함된 단일 PDF와 웹 화면을 연결한다.
7. 다양한 검증 사이트로 정확도·비용을 개선하고 공정한 비교 실험을 준비한다.
8. 최종 설정을 고정한 후 평가·안정화·데모·발표를 진행한다. 서버 배포는 여건에 따라 병행한다.

첫 프로토타입은 방향 확인 후 약 1주를 목표로 한다. 현재 제공된 개발용 정상·결함 사이트의 사례 하나에서 각 버전을 독립 실행해 실제 검사·판정·추가 재현·JSON을 확인한다. PDF와 네 범주 전체 완성은 첫 주 통과 조건이 아니다.

최종 제출은 12월 첫째 주다. 11월 중순 무렵 필수 기능 안정화, 이후 최종 평가·발표 준비 여유 확보는 권장 기준선이며 고정 주차별 의무가 아니다. 첫 기준선 결과로 세부 목표를 정하되 최종 평가 전에 고정한다.

팀은 총 6명이며 전처리·AI·테스트/벤치마크의 3파트로 구성한다. 실제 가용 시간에 맞춰 세부 작업을 배분한다. 테스트 Claude API 예산은 약 140만 원을 계획 기준으로 사용한다.

| 파트 | 책임 |
|---|---|
| 전처리 | 브라우저 수명주기, URL·상태 탐색, 범위, 관찰 요약, 증거 수집·기록 |
| AI | MCP 연결·모델 도구 루프, 검사 계획·다음 행동·판정, 재현 연계, JSON·보고서 |
| 테스트 사이트·벤치마크 | 여러 구조의 사이트, 계정·데이터·초기화, 정답, 독립 재현·성능평가 |

같은 브라우저·탭의 실행과 증거 연결 규칙은 전처리·AI 파트가 함께 합의한다. 웹 UI·배포 담당은 별도 배정하며 자동으로 AI 파트에 몰아주지 않는다.

## 12. 확정된 경계와 후속 결정

필수 범위에서 제외하는 것은 모든 결함 탐지 보장, 모든 브라우저·실기기 지원, 무제한 긴 업무 흐름, 장기 유지용 회귀 테스트 파일 생성, 정확한 코드 원인 진단·자동 수정, 담당자 검토 관리, 공개 다중 사용자 서비스, 실데이터 위험 행동이다.

서버 배포, 추가 사이트·기능·버그 범주, 재사용 테스트 파일, 상용 도구 비교, 경험자 시간 실험은 조건부 확장이다. 핵심 파이프라인과 평가를 희생하면서 자동으로 필수 범위에 추가하지 않는다.

방향성 확인 후 결정할 사항은 모델별 역할·승격 조건, 실행 한도·자원 배분, 화면 크기 목록, 입출력·증거·판정 스키마, 웹 UI·배포 담당, 평가 데이터 규모·수치 목표·집계 규칙이다. 수치와 구현 방법을 이미 확정한 것처럼 사용하지 않는다.

## 13. 팀 공유 시 확인할 사항

- 우리는 테스트 스크립트 작성과 검사·증거 정리 부담을 줄이는 QA 보조 도구를 만드는가?
- AI의 계획, 실제 실행, 근거 있는 판정이 다른 단계라는 점에 동의하는가?
- 페이지별 발생 위치와 실제 재현 조건을 보고서의 핵심으로 이해하는가?
- 필수·조건부 확장·제외 범위를 같은 의미로 이해하는가?
- 담당자가 없어도 보고서를 생성하며, 앱 내부 검토 관리는 제외한다는 점이 명확한가?
- 첫 목표는 작은 흐름의 실제 연결이며, 세부 규격은 방향 확인 후 정한다는 순서에 동의하는가?

팀원들은 이 문서를 먼저 읽고, 자세한 결정 배경이 필요한 항목은 Q1~Q66 최종 입장 정리본에서 확인한다. 수정 의견은 목적·범위·흐름·평가·역할 중 어느 부분에 대한 것인지 구분해 모은다.
