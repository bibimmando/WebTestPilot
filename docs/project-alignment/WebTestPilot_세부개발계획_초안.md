# WebTestPilot 세부개발계획 초안

작성 기준: 2026-10-10 | 버전 0.6 | PM 검토용

Q1~Q66 방향성, Q68의 진행 동의 및 Q69~Q79의 답변을 기반으로 첫 프로토타입까지의 작업·의존 관계·완료 기준을 정리한다. 번호가 중복된 버그 목록 링크 답변은 Q70 답변으로 해석한다. Q74에서 계획·행동 선택→MCP 실행·후처리→문맥을 이어받은 모델 판단의 루프와 입력·실행 결과의 JSON 통일을 확인했다. Q75에서 JSON 세 종류와 ID 연결을, Q76에서 제한된 오류 교정과 불명확한 결과의 재실행 금지를 확인했다. Q77에서 사용자가 PM으로 작업 배분과 코드 통합을 직접 맡고, Q78에서 전처리팀이 공용 JSON 규격을 관리하는 것으로 정했다. Q79의 웹 화면 담당은 프로토타입 이후 전처리팀 여력을 보고 배정하는 조건부 계획이다. Q73에 따라 F3를 첫 사례로 고정하는 제안은 채택하지 않는다. 확정된 원칙과 아래의 미확정 제안을 구분하며, 이 문서는 구현 완료를 뜻하지 않는다. 제품 코드·기존 연결 규격·인프라는 이 문서 작성으로 변경하지 않는다.

## 1. 이번 단계의 목표

첫 프로토타입은 AI·전처리 파트가 주도하며, 이미 제공된 승인 테스트 페이지에서 짧은 흐름부터 실제 검사·관찰·판정·추가 1회 재현·JSON 저장을 연결한다. 특정 주입 결함을 처음부터 고정하거나 테스트 페이지 파트가 별도 단일 사례를 새로 준비하는 것을 착수 조건으로 두지 않는다. 테스트 페이지 파트는 여러 페이지와 결함을 계속 개발하고, 프로그램은 제공된 페이지에 맞춰 갱신한다.

정상·결함 환경과 대응 정답이 준비된 범위는 독립 실행해 결과를 대조한다. 코드·결함 설정·초기 조건을 실행별로 기록하며, 개발 중 사이트가 바뀌었다는 이유로 서로 다른 조건의 탐지 결과를 같은 성능 수치로 비교하지 않는다. 정답이 불명확한 상태에서는 연결 검증 결과와 정식 탐지/오탐 평가를 구분한다.

그 전에 무과금 기술 연결 검증을 둔다. 기존 로컬 fixture의 간단한 화면 변화로 전처리와 MCP가 같은 브라우저·탭·상태를 사용하는지 확인한다. 이 기술 검증을 실제 버그 탐지나 자율 발견 성능으로 주장하지 않는다.

PDF, 전체 네 범주, 모바일 UI, 웹 화면, 서버 배포를 첫 주 완료 조건에 모두 넣지 않는다. 다만 최종 필수 범위와 안전·권한·실행 제한 원칙은 유지한다.

이전 AI 조사 대상은 `origin/feature/member-02/ai-inspector`의 `ecdba13bf2cfb8b802ffba93af70ea910f02235c`다. 이 ref의 흐름은 hybrid JSONL 증거의 단일 모델 분석이며 실제 브라우저 검사·최종 판정은 연결돼 있지 않았다. 이는 해당 고정 ref의 사실이지 모든 AI 구현의 현재 상태를 뜻하지 않는다. 문자열 검사 제안을 실행 가능한 검사 루프로 취급하지 않는다.

위 이전 ref에는 AI 소스 위치 `src/ai_inspection copy/`와 문서·import의 `src.ai_inspection`에 불일치가 있었다. 공식 코드 위치와 진입점은 실제 통합 대상을 기준으로 확인한다. 이전 커밋의 계획 검증 로직은 선택적 재사용 후보이지 최신 HEAD 전체를 되돌리라는 뜻이 아니다.

## 3. 제안하는 통합 관문

### G0. 실행 기준 정리

공식 전처리 경로와 AI ref·패키지·실행 진입점을 정리하고 유료 호출 없는 준비·검증 경로를 확인한다. import나 단순 실행 준비가 브라우저·API를 자동 시작하지 않아야 한다.

완료 기준: 다른 개발자가 안내된 환경과 명령으로 무과금 준비를 재현할 수 있다. 문서와 실제 경로가 일치하고 코드·환경·비밀값의 경계가 명확하다.

### G1. 같은 브라우저의 MCP 행동과 증거 연결

기존 로컬 fixture에서 MCP로 준비된 행동 하나를 수행하고, 전처리의 행동 전후 수집으로 같은 화면 변화를 확인한다. 기존 콜백의 Page와 MCP가 별개 브라우저를 조작하면 통과가 아니다.

완료 기준: 같은 탭·상태임을 확인하고 실제 행동에 전후 snapshot·관찰 결과·사진을 연결한다. 모델 key 없이 확인할 수 있으며 모델 호출도 없다. 조작 실패와 수집 실패를 사이트 버그로 보고하지 않는다.

### G2. 모델 입력과 실행 결과의 왕복

기존 ai_input/1을 버리지 않고 사이트 공통 문맥과 현재 흐름을 연결한다. 기존 호출 어댑터의 오류·사용량 처리를 재사용하되 선택한 실행 인터페이스에 맞춰 도구 요청·결과·다음 관찰을 처리한다.

완료 기준: 실제 모델이 허용된 다음 행동을 선택하고, 실제 행동 결과를 보고 이어서 판단한다. 처음 만든 계획을 관찰 없이 끝까지 실행하거나 설명형 문자열을 실행 결과로 취급하지 않는다.

### G3. 제공 페이지의 판정·재현·JSON 연결

현재 제공된 페이지에서 모델이 검사 행동을 선택하고 관찰 결과에 따라 후보·판정을 남긴다. 특정 F3를 찾도록 실행 경로나 판정을 하드코딩하지 않는다. 평가자용 결함 라벨·주입 위치·정답은 검사 모델 입력과 분리한다. 프로그램은 실제 행동·시작 조건을 보존하고 가능한 후보에 대해 추가 1회 재현한다. 대응 정상·결함 버전과 정답이 확보된 범위는 독립 실행해 대조한다.

완료 기준: 실제 모델 행동과 후속 관찰이 연결되고, 기대 근거·실제 관찰·최초/재현 결과 또는 미완료 사유·증거·사용량이 JSON에 저장된다. 근거 부족과 실행 실패를 구분한다. 정답이 확보된 실행에서는 정상의 잘못된 보고와 결함의 탐지를 별도로 확인하되, 연결 성공을 탐지 성공이나 전체 성능으로 대신 주장하지 않는다.

## 4. 파트별 작업 카드 초안

Q77~Q78에 따른 전체 통합 담당과 공용 규격 관리 담당은 확정한다. 나머지 실제 사람별 배정은 PM이 팀의 가용 시간과 역량에 맞춰 조정한다. PM은 사용자 본인이며, 조율·검수뿐 아니라 전체 실행 진입점과 파트 간 연결 코드를 직접 통합한다. 각 파트의 내부 구현·오류 수정 책임은 담당 팀에 남는다.

| ID | 작업 | 주도·협업 | 선행 | 완료 결과 |
|---|---|---|---|---|
| T01 | 공식 코드·실행 진입점 정리 | PM 통합 주도, 각 파트 확인 | 없음 | 기준 경로·ref·무과금 준비 안내 |
| T02 | 제공 페이지 실행 조건·검증 자료 정리 | AI·전처리, PM 조율 | 없음 | 현재 버전·허용 범위·시작 조건·계정 참조·확보된 정답/복원 정보 |

| T04 | 최소 입력·실행·증거·판정 규격 초안 | 전처리팀 관리, AI 소비/생산 의미 검토, PM 통합 | T02의 실행 조건·T03 결과 | 기존 규격과 확장의 대응표·예시·오류 처리 |

T01·T02는 병행할 수 있다. 규격의 틀은 미리 논의할 수 있지만 T03의 기술 제약을 확인하기 전에 연결 방법을 완성된 것으로 고정하지 않는다. 테스트 페이지 파트에 프로토타입용 특정 결함의 별도 개발을 요구하거나 이를 기다리며 T03~T06을 멈추지 않는다. 해당 파트가 진행 중인 페이지·결함 개발에서 확보되는 실행 정보와 정답을 공유받는다. 정식 벤치마크 준비 책임은 기존 방향대로 유지한다. 무과금 확인과 유료 모델 검증은 별도 실행 단계다.

## 5. 최소 규격에서 정할 항목

기존 callback과 ai_input/1은 출발점이다. Q74에서 입력·실행 결과를 JSON으로 구조화해 전달하는 원칙을 확인했다. 아래 세부 필드·스키마 이름과 확장은 아직 구현되거나 최종 합의된 규격이 아니다.

- 실행 문맥: 허용 URL·행동, 남은 실행 한도, 준비 가능한 초기 상태·계정 참조.
- 모델 입력: 사이트 공통 문맥, 현재 ai_input/1, 현재 흐름과 필요한 이미지.
- 실행 요청: 선택한 도구·관찰된 대상·안전한 테스트 값 또는 비밀값 참조, 실행 전 검증 조건.
- 실제 결과: 실제 행동, 시작 조건, 전후 상태·증거, 실행·수집 오류, 사용량.
- 판정: 기대 결과·근거, 실제 관찰, 추가 재현, 검토·미완료 사유.
- 저장: run/flow/check/action/snapshot의 연결, 실행 폴더 안의 상세 결과와 최종 JSON.

전처리 요소 key와 MCP 조작 대상의 연결은 검증해야 한다. 관찰 이후 화면이 바뀌면 예전 대상 정보가 계속 유효하다고 가정하지 않는다. 실제 재현에는 안전하게 보존된 입력값·키 동작·시작 조건이 필요하며, 현재 전후 snapshot만으로 완성됐다고 보지 않는다.

현재 콜백은 `passed|failed|not_run` 등 제한된 반환값만 처리한다. 상세 plan/findings/report를 반환한다고 자동 저장되는 것은 아니다. 상세 저장 책임과 기존 콜백 상태로의 변환을 명시한다. 전체 실행·PDF에 필요한 최종 판정 상태와 필드 이름은 별도 합의한다.

### Q74~Q76 확인 사항과 최소 규격 초안

프로그램이 흐름별 대화·실제 행동 기록을 보존하고, 실행 후의 새 관찰과 결과를 같은 모델의 다음 요청에 전달한다. 모델은 다음 행동을 선택하거나 판정을 남긴다. MCP 연결은 실행 시작에 준비하고 필요한 동안 유지하며, 행동마다 새 브라우저를 만드는 방식으로 연결 흐름을 끊지 않는다.

JSON 통일은 내용과 의미가 다른 모든 메시지를 하나의 동일 구조로 만드는 뜻이 아니다. Q75에서 다음 세 종류를 구분하고 공통 실행/흐름/행동/증거 식별자로 연결하는 방향을 확인했다. 세 종류는 세 모델이나 세 물리 파일을 필수로 만든다는 뜻이 아니다. 구체 필드명과 스키마 버전은 공동 검토 대상이다.

| 논리 데이터 | 생산·소비 | 최소 내용 제안 |
|---|---|---|
| 검사 입력 | 전처리 관찰을 AI 파트가 조립 → 모델 | 기존 ai_input/1, 사이트·허용 범위, 현재 흐름의 목표·시작 조건·이전 행동/결과, 필요한 이미지 참조 |
| 실행 결과 | 실행·증거 수집 프로그램 → 모델·결과 저장 | 실제 도구 요청/행동, 실행·수집 상태와 오류, 전후 관찰과 변화, 증거 참조, 관련 식별자 |
| 판정 기록 | 모델 응답을 프로그램이 검증 → 최종 JSON | 기대 동작·근거 출처, 실제 관찰, 후보·검토/미완료 사유, 재현·증거·실제 행동 참조 |

2026-10-09의 좁은 소스 확인에서 ai_input/1은 페이지·요소·폼·링크·오류·준비 상태·신뢰 구분 등을 이미 포함한다. 페이지 snapshot/action 식별자와 controls[].key를 재사용하고, 없는 사이트 공통 문맥·흐름 목표·기대 근거·대화 이력·이미지 연결을 보완한다. 실제 행동 기록은 actions/{action_id}.json에 전후 snapshot·diff·상태·오류·관찰 참조를 저장한다. MCP tool_use_id·도구 인자·실제 재생 값·흐름/초기 상태와의 연결은 추가 검증·보완 대상이다.

실행 결과의 completed/failed 등은 도구 실행·수집 상태다. 클릭이 완료됐다는 이유만으로 기능 검사가 통과하거나 버그가 확인됐다고 판단하지 않는다. 기존 원 도구 결과와 실제 증거는 보존하고, 모델에 주는 요약과 최종 판정을 구분한다.

Claude의 tool_use/tool_result 규약은 그대로 유지한다. 내부 실행 결과 JSON은 요청 ID가 맞는 tool_result에 담아 전달한다. 이미지 메타데이터와 증거 참조는 JSON으로 관리하지만, 모델이 실제 화면을 봐야 할 때는 지원되는 image 블록으로 이미지 내용을 전달한다. 로컬 경로 문자열만 주고 모델이 사진을 봤다고 간주하지 않는다. [도구 결과 형식](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls#handling-results-from-client-tools), [Claude 이미지 입력](https://platform.claude.com/docs/en/build-with-claude/vision)

Q76에서 미실행이 확인된 단순 도구 요청 오류는 한도 안에서 최대 1회 교정하고, 실행 여부·데이터 변경 결과가 불명확하면 자동 반복하지 않는 방향을 확인했다. 교정은 버그 확인용 추가 재현 1회와 별개이며 원 요청·새 시도·횟수·결과를 연결한다. 권한·한도 제한을 교정으로 우회하지 않는다. 기존 failed 상태만으로 미실행을 단정하지 않는다.

이를 반영한 [JSON 최소 연결 규격 초안](C:/Users/lsc05/Documents/ChatGPT/WebTeste/docs/project-alignment/WebTestPilot_JSON_연결규격_초안.md)에 필드 제안·합성 예시·오류 규칙·검수 기준을 정리했다. Q78에 따라 전처리팀이 기존 AI_INPUT_CONTRACT.md·INTEGRATION_GUIDE.md 및 실제 코드와 초안의 대응 관계를 관리한다. 기존 ai_input/1·snapshot/action을 유지하고, 없는 실행/흐름 문맥·MCP 요청·교정·판정 연결은 확장으로 구분한다. member-06의 별도 입력/행동 형식을 곧바로 같은 규격으로 간주하지 않는다. AI팀은 모델 요청·도구 루프·판정의 변환을 구현하고 PM이 전체 실행에 통합한다. 구체 필드명·예시·검증 코드는 파트 간 검토 후 고정한다. 사이트 준비 실패·도구 실패를 사이트 버그로 오인하지 않는 기존 원칙은 유지한다.

## 6. 개발 중 검증 자료의 최소 내용

AI·전처리 파트가 이미 제공된 페이지와 결함 자료를 바탕으로 실행 조건을 정리한다. 외부 소스의 실제 결함 정의와 배포 사이트의 활성 결함을 구분한다. 아래 항목은 재현·정답 대조에 필요한 정보이며, 테스트 페이지 파트가 특정 첫 사례 카드를 새로 완성해야 프로토타입을 시작할 수 있다는 뜻은 아니다. 확보되지 않은 항목은 미확인으로 기록한다.

1. 정상·결함 버전의 시작 경로와 평가자용 사례 ID·유형.
2. 필요한 로그인 역할·계정의 안전한 전달 방식.
3. 시작 데이터·상태와 승인된 준비·복원 방법.
4. 정상 기대 결과·근거와 결함 버전의 잘못된 실제 결과.
5. 평가자가 사용하는 짧은 수동 재현 절차·화면 조건.
6. 모델에 제공 가능한 요구사항과 숨겨야 하는 정답·주입 위치의 구분.

첫 연결은 가능하면 짧고 초기 조건이 명확한 흐름부터 검증한다. 로그인·DB 변경이 없는 흐름은 연결 문제를 분리하기 쉽지만 특정 결함 하나를 개발 목표로 고정하지 않는다. 테스트 계정·API 비밀값을 공유 채팅이나 정답 문서 본문에 노출하지 않는다.

연결 검증용으로 행동을 고정하는 시험과, 모델이 입력을 보고 기능·행동을 선택하는 시험은 구분한다. 고정 경로의 성공을 자율 발견 성공으로 대체하지 않는다.

### 소스 참고: F3 수량 증가 무반응 — 첫 사례 고정 제안 미채택

확인한 소스는 기능 브랜치 SHA `2ee8b794ef1a0a0f3f7d6763e9bf9a8817e5228d`의 [F3 정의](https://github.com/Majunseo/Maison/blob/2ee8b794ef1a0a0f3f7d6763e9bf9a8817e5228d/server/bugs/functional.ts#L45)다. 상품 `/product/arc-pendant-light`에서 수량을 늘리는 짧은 사례이며, 로그인·장바구니 담기·주문·서버 데이터 변경을 필요로 하지 않는다. 아래는 기존 조사 사실의 보존이며, Q73에 따라 이 결함을 프로토타입의 고정 대상·착수 조건으로 삼지 않는다.

- 시작 조건: 새 상품 상세 페이지의 수량은 1이고 증가 버튼은 활성화돼 있다. 기본 최소는 1, 최대는 10이다.
- 기대 결과: 정상 증가 동작은 수량 1을 2로 바꾼다. F3가 켜지면 증가·감소의 상태 변경 호출을 생략한다. [수량 제어 구현](https://github.com/Majunseo/Maison/blob/2ee8b794ef1a0a0f3f7d6763e9bf9a8817e5228d/src/components/QuantitySelector.tsx#L17)
- 오탐 주의: 수량 1에서 감소 버튼이 비활성화돼 변화가 없는 것은 정상이다.
- 소스상 분리 가능한 조건: 같은 위 SHA의 코드에서 정상은 모든 결함 설정을 끄고, F3만 분리할 때는 `BUG_F3=1`만 사용한다. `BUGS_ON=all`은 그 실행 코드에 등록된 모든 결함을 활성화한다. 이는 [토글 구현](https://github.com/Majunseo/Maison/blob/2ee8b794ef1a0a0f3f7d6763e9bf9a8817e5228d/server/bugs/index.ts#L45)에 근거한 구성 가능성이지 현재 채택한 개발 프로필이나 실행 검증 결과가 아니다.
- 대상 연결 주의: 아이콘 버튼에 직접 텍스트·aria-label이 없어 접근성 이름이 비어 있을 수 있다. 이름이 `+`라고 하드코딩하지 않고 관찰된 요소 참조와 화면/위치를 연결한다. 대상 선택 실패를 사이트 결함으로 보고하지 않는다.
- 준비 완료 주의: 사이트의 결함 설정을 비동기로 불러오므로 설정 적용 전 행동은 정상 동작처럼 보일 수 있다. 테스트 파트가 제공하는 준비 완료 조건을 실행기에서 확인하되 활성 결함 ID는 판단 모델에 전달하지 않는다. [설정 로딩 구현](https://github.com/Majunseo/Maison/blob/2ee8b794ef1a0a0f3f7d6763e9bf9a8817e5228d/src/hooks/useBugs.ts#L19)
- 재현 조건: 상품 수량은 페이지의 React 상태다. 새 페이지/컨텍스트에서 시작 수량 1을 확인하면 되므로 이 사례에는 서버 데이터 초기화가 필수는 아니다. 초기 증거는 새로 시작하기 전에 보존한다.

T02는 제공된 페이지의 실행 조건을 정리하는 AI·전처리 공동 작업으로 수정한다. 현재 8080/8081이 위 F3 단독 구성을 사용한다고 가정하지 않는다. 판단 모델에는 결함 ID·주입 위치·수동 정답 절차·정상 비교본을 주지 않고 관찰에서 검사 행동을 선택하게 한다.

### 정답 분리와 초기화에 관해 추가로 확인한 사실

이 테스트 사이트는 `/gt.json`에 결함 설명·재현 경로, `/api/bugs`에 활성 ID를 제공하며 body의 `data-bugs`에도 활성 ID를 넣는다. [정답 생성](https://github.com/Majunseo/Maison/blob/28463852d389d54ca7ebffa1df1d82faedbdcd26/server/bugs/index.ts#L73), [브라우저 메타데이터](https://github.com/Majunseo/Maison/blob/28463852d389d54ca7ebffa1df1d82faedbdcd26/src/hooks/useBugs.ts#L19)

기존에 합의한 평가자 정답/모델 입력 분리 원칙을 전처리·도구 결과에도 적용한다. 정답 경로 직접 조회를 판단 모델의 허용 도구 범위에서 제외하고 DOM·네트워크 요약 등에 활성 ID가 들어가는지 확인한다. 사이트 자체의 `/api/bugs` 요청을 차단해 결함 적용을 깨뜨리는 방식은 사용하지 않는다. 준비 완료 확인·평가자 정답 대조와 모델에게 주는 정보는 별도 책임이다.

서버 메모리의 계정·주문·세션 등을 시드 상태로 되돌리는 [초기화 함수](https://github.com/Majunseo/Maison/blob/28463852d389d54ca7ebffa1df1d82faedbdcd26/server/store.ts#L86)는 이미 있다. 다만 장바구니·위시리스트의 브라우저 persist 상태까지 초기화하는 것은 아니므로 서버 초기화와 브라우저 시작 조건은 별도로 정한다. 어떤 초기화든 사이트 담당자가 승인한 준비/복원 프로필을 프로그램이 실행하는 기존 원칙을 유지한다.

## 7. PM 운영·코드 통합과 조건부 역할 배정

Q77에 따라 사용자가 PM으로 전체 우선순위·작업 배분·의존 관계·연결 변경 조율뿐 아니라 코드 통합을 직접 맡는다. 각 파트의 구현을 하나의 실행 진입점으로 연결하고, 실행 상태·종료/실패·결과 저장 등 파트 사이의 흐름을 맞추며 통합 검증을 주도한다. 단순히 완성된 코드를 검수하는 역할로 제한하지 않는다. 다만 모든 파트 내부 기능과 오류 수정을 PM 혼자 처리한다는 뜻도 아니다. 파트 담당자는 실행 방법·입출력·검증 근거와 함께 자신의 구현을 전달한다.

Q78에 따라 공용 JSON 규격의 문서·변경 이력·호환 관계는 전처리팀이 관리한다. AI팀은 모델 입력·도구 결과·판정/재현·보고서에서 필요한 의미와 필드를 검토하고 해당 코드를 구현한다. 규격 관리 담당이 AI 판단 로직까지 대신 개발하거나, 기존 코드가 새 초안을 이미 지원한다고 선언하는 역할은 아니다.

각 작업 보고에는 담당·입력·산출물·실행 방법·실제 검증 결과·미구현 부분·다음 의존 작업을 적는다. 설명이나 코드 존재만으로 완료하지 않는다. 공통 규격 변경은 생산자·소비자·fixture·문서의 영향을 함께 확인하고 조율한다.

Q79에 따라 웹 화면은 프로토타입 이후 전처리팀 여력이 생기면 담당하는 조건부 계획으로 둔다. 프로토타입 완료를 전처리 작업 종료로 보지 않는다. 후속 상태/연결 흐름·로그인·승인된 초기화·모바일/viewport 관찰·증거 품질 작업이 남으므로 PM이 잔여 작업과 가용 시간을 보고 실제 담당자를 배정한다. UI·배포를 AI팀에 자동 추가하지 않으며 서버 배포 담당도 이번 답변만으로 확정하지 않는다. 웹 화면은 최종 범위로 유지하되 모델 루프·전체 실행 통합보다 먼저 완성할 조건은 아니다.

## 8. 후속 결정과 확대 순서

이번 답변에서 기술 연결 검증을 먼저 하는 방향과 초기 단일 모델 운영을 동의한 것으로 정리한다. 계획·다음 행동 선택·실행 결과 판단은 같은 모델이 맡을 수 있다. 실제 브라우저 행동은 MCP와 프로그램이 수행하고, 권한·대상·한도 검증 및 증거 기록은 코드가 책임진다. 단일 모델은 단일 API 호출을 뜻하지 않는다.

Q72에서 Claude 표준 도구 호출 방향에 동의했고 Q74에서 계획·행동 선택, MCP 실행·후처리, 결과를 전달받은 모델 판단의 루프를 확인했다. 사용자가 말한 두 번째 AI는 MCP가 AI라는 뜻이 아니라 API 호출 사이에 메모리가 자동 공유되지 않는다는 의미였으므로 그 구분을 반영한다. 같은 모델을 호출하더라도 이전 요청을 자동 기억하는 것으로 가정하지 않는다. 프로그램이 흐름별 문맥과 실제 결과를 보존·다음 요청에 전달한다. [Claude 다중 턴](https://platform.claude.com/docs/en/build-with-claude/working-with-messages#multiple-conversational-turns)

같은 Claude 모델의 tool_use 요청을 프로그램이 검증·MCP 실행한 뒤 tool_result로 관찰을 돌려주는 구조를 사용한다. MCP는 브라우저 도구 서버이고, 입력·실행 결과·판정의 내부 자료는 JSON으로 정리한다. API 표준 도구 호출과 이미지 전달 형식은 유지한다. [Claude 공식 도구 호출 규약](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls#handling-results-from-client-tools), [Playwright MCP 공식 설명](https://github.com/microsoft/playwright-mcp)

API key는 Claude API 요청의 인증 수단이다. 요청 횟수·역할 수·API key 수를 모델이나 독립 에이전트 수와 같은 것으로 보지 않는다. 계획·기대 근거·실제 행동·판정의 JSON 기록은 별도로 보존한다. 모든 행동을 한 번에 고정하는 자체 JSON 실행 계획과 관찰을 반영하는 도구 루프를 혼동하지 않는다.

Q73에 따라 첫 실제 사례를 F3로 고정하지 않고 AI·전처리 파트가 현재 제공된 페이지를 사용해 프로토타입을 만들고 갱신한다. 테스트 페이지 파트는 페이지·결함 개발을 우선한다. Q74~Q76의 루프·JSON 구분·오류 복구 원칙과 Q77~Q78의 담당 구분에 따라 전처리팀이 규격을 정리하고 AI팀이 소비/생산을 맞추며 PM이 실제 코드를 통합·검증한다. Q79의 웹 화면 배정은 프로토타입 뒤 여력을 보고 결정한다. 실제 모델명·API key·공유 브라우저 연결 설정을 지금 문서에서 임의로 확정하거나 연결하지 않는다.

첫 기준선이 통과하면 네 범주·연결 흐름·로그인·모바일 UI·안전한 종료/실패 처리, PDF·웹 화면, 다양화 평가·모델 배분 최적화 순으로 확대한다. 서버 배포는 조건부 추가 목표다. 정확한 모델명·예산 수치·화면 목록·평가 규모는 검증 후 정하고 최종 평가 전에 고정한다.

방향 확인 후 약 1주라는 첫 프로토타입 목표는 유지하되 실제 일정은 연결 검증·사례 준비 결과로 조정한다. 12월 첫째 주 제출과 마지막 평가·발표 준비 여유를 우선한다. 이 문서는 유료 API 호출·사이트 변경·서버 공개·코드 병합을 수행한 기록이 아니다.
