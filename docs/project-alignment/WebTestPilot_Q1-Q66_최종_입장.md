# WebTestPilot Q1~Q66 최종 입장 정리

팀 검토용 | 논의 기준: 2026-10-08 | 버전 1.0

이 문서는 인터뷰의 질문 번호를 유지하고 표현을 정돈한 최종 입장 정리본이다. 대화체·개인적 고민·중간 제안은 제외하고, 뒤의 답변에서 수정된 결정을 앞 질문에도 반영했다. 같은 주제의 질문이 반복돼도 답변은 현재 방향으로 통일했다. 설계 목표이며 구현 완료나 팀 전체 승인 완료를 뜻하지 않는다.

특히 필수 예산 입력 제외, MCP 연결의 AI 파트 담당, 첫 주 JSON 우선, 단일 PDF, PDF 실패 시 JSON 보존·재생성, 담당자 검토 입력 제외, 페이지별 별도 보고, 최종 모바일 반응형 포함을 최종 결정으로 적용했다. 세부 연결 규격과 수치는 방향 공유 후 정한다.

## A. 목적·자원·자율성: Q1~Q13

### Q1. QA 담당자에게 제공할 핵심 가치는 무엇인가?

**최종 입장:** 사이트별로 검사할 기능을 찾고 테스트 행동을 준비·실행하는 부담과, 발견한 문제의 재현 절차·증거를 정리하는 부담을 줄인다. 시스템은 검사와 증거 정리를 자동화하고, 담당자는 결과의 실제 재현·검증과 수정 착수에 집중한다. 앱 안에서 담당자의 검토 결과를 관리하는 기능은 요구하지 않는다.

### Q2. URL만 입력받는 것이 필수 조건인가?

**최종 입장:** URL은 기본 입력이지만 URL만 받아야 한다는 제약은 없다. 사이트 설명·요구사항·테스트 계정·초기화 등 필요한 정보를 추가로 받을 수 있다. 상세 테스트 스크립트를 작성하도록 요구하지 않으며, 최소 정보 조건과 설명 추가 조건의 성능은 구분한다.

### Q3. 우선 지원할 검사 환경은 무엇인가?

**최종 입장:** 개발팀이 관리하고 검사·데이터 전달을 승인한 로컬·스테이징 환경을 우선한다. 테스트 계정과 가상 데이터를 사용한다. 실제 상용 사이트의 적용 사례는 허가된 범위에서 별도로 검토하며, 공개돼 있다는 이유만으로 상태 변경 검사를 허용하지 않는다.

### Q4. 일정·인력·예산과 결과물의 기준은 무엇인가?

**최종 입장:** 최종 제출은 12월 첫째 주이며 팀은 6명, 테스트 Claude API 예산은 약 140만 원을 계획 기준으로 사용한다. 세부 작업은 실제 가용 시간에 맞춰 배분한다. 실행 가능한 검사 엔진·웹 화면·JSON·증거·PDF와 검증 결과를 목표로 하며, 작은 전체 연결본을 먼저 만든다. 가용 시간과 세부 담당은 팀에서 확인한다.

### Q5. 팀의 파이프라인 이해 차이는 어떻게 해소할 것인가?

**최종 입장:** 목적·입력·AI 역할·실제 실행·판정·출력·성공 기준을 동일 문서로 맞춘다. 전체 방향을 먼저 공유·확인하고 최소 연결 규격을 정한다. 페이지 단위 처리는 관찰 이후의 반복이나 연결 흐름을 생략하는 뜻이 아니며, 계획·실행·판정은 분리한다.

### Q6. 재사용 가능한 테스트 스크립트도 필수 산출물인가?

**최종 입장:** 초기 필수는 실행 중 검사 행동을 만들고 수행하는 자동 검사와 문제 보고서다. 실제 행동·조건을 기록해 자동 추가 재현과 담당자의 재현을 지원한다. 모든 정상 기능의 장기 유지용 회귀 테스트 파일 생성·재사용은 핵심 시스템 안정화 이후의 확장이다.

### Q7. QA 담당자에게 어느 정도의 추가 정보를 요청할 수 있는가?

**최종 입장:** 짧은 사이트 설명, 테스트 역할·계정, 핵심 기대 동작, 기존 문서 등 준비 부담이 작은 정보를 받는다. 추가 정보 준비가 기존 스크립트 작성보다 무거워지지 않도록 한다. 요구사항·화면의 명시적 제약·관찰·AI 추정을 구분하고, 근거 없는 업무 규칙을 확정하지 않는다.

### Q8. 검사 중 데이터 생성·변경을 허용할 것인가?

**최종 입장:** 승인된 테스트 환경과 행동 범위 안에서 허용한다. 실제 DB나 외부 서비스와 연결될 가능성을 고려해 테스트 계정·가상 데이터·허용된 준비·복구 절차를 사용한다. 실결제·외부 발송·운영 데이터 삭제는 초기 범위에서 제외하고, 불명확한 권한은 확인한다.

### Q9. 네 가지 범주의 초기 검사는 어디서부터 시작할 것인가?

**최종 입장:** 관찰과 기대 근거를 만들기 쉬운 기능·입력 검증·라우팅·UI 문제부터 시작하고, 실제 연결 결과를 보며 기능과 사이트 구조를 순차 확대한다. 짧은 다중 페이지 흐름과 기본 로그인, 최종 모바일 반응형 검사를 포함한다. 복잡한 업무 계산·다역할 정책·긴 결제 흐름·추가 범주는 자동으로 필수 범위에 넣지 않는다.

### Q10. 보고하기 전에 시스템이 어디까지 검증할 것인가?

**최종 입장:** 가능한 경우 같은 시작 조건에서 실제 기록한 행동을 추가 1회 실행해 반복 여부를 확인한다. 기대 동작 근거와 재현 성공은 별도로 판단한다. 의도 불명확·재현 실패는 검토 대상으로, 실행 준비·도구 실패는 검사 미완료로 구분하고 최초 증거를 보존한다.

### Q11. 자율 탐색을 프로젝트의 핵심으로 유지할 것인가?

**최종 입장:** 유지한다. 사용자가 개별 기능과 클릭 순서를 작성하지 않아도 시스템이 기능·검사 행동을 발견하고 지원 범위·실행 한도 안에서 검사한다. 추가 정보는 정확도를 높이는 문맥이며 검사 시나리오 전체를 사용자에게 넘기는 방식이 아니다. 모든 결함 탐지를 보장하지 않는다.

### Q12. AI가 알 수 없는 업무 규칙은 짧은 질문으로 보완할 수 있는가?

**최종 입장:** 명세·화면·관찰에서 근거를 찾지 못한 필요한 규칙은 최소한의 확인이나 추가 정보 안내로 보완할 수 있다. 정상 동작에 대한 질문과 행동 허용에 대한 승인은 구분한다. 응답이 없으면 관련 판정은 보류·검토 대상으로 남기며, 보고서 작성 전에 사람의 버그 검토를 강제하지 않는다.

### Q13. 초기 상태 준비의 책임은 누구에게 있는가?

**최종 입장:** 대상 사이트 개발자 또는 테스트 사이트 파트가 승인된 reset/seed·테스트 데이터·분리 환경을 제공한다. WebTestPilot은 필요한 절차를 선택·호출하고 준비 결과를 확인한다. 임의로 DB 복구 방법을 생성하지 않으며, 연동 수준에 따른 검사 제한을 표시한다.

## B. 페이지 처리·실행·상태: Q14~Q22

### Q14. 어떤 페이지를 AI가 검토하고, 수집과 검사는 어떤 순서로 진행하는가?

**최종 입장:** 범위·한도 안에서 방문한 독립적인 페이지·기능 상태의 전처리 요약을 AI가 검토하는 기준 실행을 만든다. 전체 원본을 먼저 모으지 않고 관찰·검사·새 URL/상태 발견을 반복한다. 선택적 AI 호출은 이후 비용 감소와 미탐 증가를 함께 측정한 뒤 적용하며, 방문한 범위를 사이트 전체라고 표현하지 않는다.

### Q15. AI와 공통 실행기는 각각 무엇을 하는가?

**최종 입장:** AI는 검사 목표·행동·기대 조건·다음 행동·결과 해석을 선택한다. 프로그램은 허용 여부·요소·한도를 확인하고 MCP 도구로 실제 조작과 관찰·기록을 수행한다. 초기에는 도구 조합을 사용하고 자유로운 생성 코드를 제한 없이 실행하지 않는다.

### Q16. 페이지를 넘나드는 짧은 검사 흐름도 포함할 것인가?

**최종 입장:** 포함한다. 작성 후 목록·상세 확인, 목록 항목과 상세 화면의 일치, 로그인 상태 유지 등 연결된 기능을 함께 검사한다. 흐름 안에서는 상태를 유지하고, 독립 검사·재현에 필요한 시점에 초기화한다. 한도 때문에 중단된 흐름은 통과로 처리하지 않는다.

### Q17. 정상 동작 질문에 사용자가 응답하지 않으면 어떻게 하는가?

**최종 입장:** 응답에 의존하는 검사만 보류하고 가능한 독립 검사는 계속한다. 답이 없는 규칙을 AI가 확정하지 않으며, 필요한 정보와 보류 이유를 남긴다. 계정·초기화 등 필수 준비 자체가 없는 경우는 실행 준비 문제로 안내한다.

### Q18. 초기화의 기준은 URL인가, 검사 흐름인가?

**최종 입장:** 검사 흐름을 기준으로 한다. 연결된 검사 중 상태를 유지하고 독립 검사나 추가 재현 시작에 필요한 초기 상태를 준비한다. URL마다 일괄 초기화해 연결 기능을 끊지 않는다. AI는 등록된 준비 절차를 선택하고 프로그램이 실행 조건을 확인한다.

### Q19. Playwright MCP를 채택할 것인가?

**최종 입장:** 공식 Playwright MCP를 실행 도구 기반으로 채택한다. 기존 전처리기와 같은 브라우저·탭을 사용하고 증거·권한·사용량 기록이 연결되는지 검증한다. 채택을 이유로 Python 전처리기 전체를 미리 재작성하지 않는다. 세부 연결 방식과 모델 배치는 통합 실험 후 정한다.

### Q20. AI는 초기화 절차를 어디까지 실행할 수 있는가?

**최종 입장:** 사전에 등록·허용된 테스트 환경과 초기화 절차 안에서는 프로그램이 조건을 확인한 뒤 자동 실행할 수 있다. 등록되지 않은 초기화나 범위 확대는 허가가 필요하다. AI의 요청만으로 새로운 DB 초기화 권한을 만들지 않는다.

### Q21. 초기화 연동이 없는 사이트는 검사를 막아야 하는가?

**최종 입장:** 전체 실행을 일괄 차단하지 않는다. 허용된 관찰·비변경 검사 등 가능한 부분을 진행하고, 상태 준비·복구가 필요한 검사는 보류한다. 보고서에 미검사 범위와 필요한 설정을 명시한다. 준비 실패는 사이트 결함으로 단정하지 않는다.

### Q22. AI의 추정과 근거 있는 기대 동작을 구분할 것인가?

**최종 입장:** 구분한다. AI 추정은 기능 발견과 검사 생성에 활용하되, 요구사항·명시 조건의 근거 없이 버그로 확정하지 않는다. 반복 재현은 현상의 반복을 증명할 뿐 개발 의도 위반까지 자동 증명하지 않는다. 추정만으로 발견한 이상은 의도 확인이 필요한 검토 대상으로 표시한다.

## C. 입력·검사 경계·실행량: Q23~Q28

### Q23. 사용자가 준비할 기본·선택 입력은 무엇인가?

**최종 입장:** URL과 허용 범위를 기본으로 하고, 계정·초기화는 필요한 검사에, 설명·요구사항·기대 조건은 선택 정보로 받는다. 상세 테스트 절차를 새로 작성하도록 요구하지 않는다. 실행 예산은 사용자 필수 입력에서 제외하고 프로그램 기본값과 운영 설정으로 관리한다.

### Q24. 네 가지 버그 범주를 어떤 경계로 정의하는가?

**최종 입장:** 기능은 확보한 기대 동작과 결과의 불일치, 입력 검증은 확인 가능한 제약의 잘못된 처리, 라우팅은 내부 이동의 실패·목적지 불일치, UI는 필요한 정보·조작을 방해하는 표시 문제다. 미적 취향은 제외한다. 한 발생 사례를 여러 범주에 해당한다는 이유만으로 중복 집계하지 않는다.

### Q25. 스크린샷은 언제 모델에 전달하는가?

**최종 입장:** 촬영·저장과 모델 전달을 분리한다. 기능·입력·라우팅은 구조화된 관찰 중심으로, 시각적 UI 검사는 필요한 이미지·위치 정보를 보고 시작한다. 모든 이미지를 일괄 전달하지 않으며, 이미지 없이 시각 문제를 판단하고 요청이 있을 때만 제공하는 방식도 기본으로 삼지 않는다.

### Q26. 넓은 탐색과 깊은 검사 중 기본 전략은 무엇인가?

**최종 입장:** 기능을 넓게 발견하면서 관련된 짧은 흐름을 수행하는 균형형을 기본으로 한다. 시간·API 사용량·행동 수와 무변화 반복에 상한을 둔다. 방문한 URL, 실제 수행한 검사, 보류·미완료를 구분하고 전체 정상 보장으로 표현하지 않는다.

### Q27. 일반 사용자가 실행량을 직접 설정해야 하는가?

**최종 입장:** 적절한 기본 균형형 실행량은 프로그램이 제공한다. 운영 상한과 필요 시 고급 설정으로 제한을 관리하고 한도 도달 시 부분 결과와 남은 범위를 제공한다. 사용자가 기본 실행 전에 토큰·시간 예산을 계산해야 하는 구조는 피한다.

### Q28. 자동 재현의 구체적인 정책은 무엇인가?

**최종 입장:** 발견 당시 행동·시작 조건·증거를 저장하고 같은 조건을 준비해 실제 행동을 추가 1회 실행한다. 재현을 새로운 AI 탐색으로 대체하지 않는다. 반복 결과와 기대 근거를 별도 기록하고, 재현 실패·초기화 불가·실행 미완료를 구분해 최초 후보와 증거를 보존한다.

## D. 보고서·개발 사례·평가: Q29~Q39

### Q29. 담당자가 받는 최종 리포트의 구성은 무엇인가?

**최종 입장:** 사실 원본은 JSON이고 담당자에게는 실행 전체의 단일 PDF를 제공한다. 페이지·흐름·초기 조건·실제 행동·테스트 값의 안전한 표현·기대/실제 결과·근거·스크린샷·로그·추가 재현·검토 사유를 포함한다. 비밀값은 노출하지 않으며 PDF만으로 기본적인 문제 이해와 재현 준비가 가능하도록 한다.

### Q30. 검사 모델 입력과 평가 정답은 어떻게 분리하는가?

**최종 입장:** 모델은 매 실행 사이트 한 버전과 허용된 문맥만 본다. 정상 비교 사이트·정상/결함 라벨·주입 위치·정답은 제공하지 않는다. 평가자는 정답과 정상·결함 버전을 보유하고 각각 독립 실행해 탐지·오탐을 측정한다. 개발·검증·최종 평가를 사이트·템플릿 계열로 분리한다.

### Q31. 시스템의 효과를 어떤 비교로 입증할 것인가?

**최종 입장:** 동일 주력 모델·권한·사전 정보·자원 상한에서 기본 Claude+MCP 자율 탐색과 전체 시스템을 비교한다. 기본 비교군에도 필요한 관찰 도구·충분한 지침을 제공한다. 모델 역할 분리 효과와 상용 제품 비교는 별도 실험으로 검토하고 입력량 감소를 결함 탐지 성능으로 대체하지 않는다.

### Q32. QA 작업 시간 절감은 어떻게 측정할 수 있는가?

**최종 입장:** 시간 비교를 수행한다면 준비·검사·결과 확인·오탐 검토·재현·보고서 보완의 사람 작업 시간과 전체 소요 시간·품질을 함께 측정한다. 초기 연동 준비 시간은 별도로 기록하고 사례·순서에 따른 학습 효과를 통제한다. 다만 경험자·여건이 없는 상태에서는 필수 평가로 약속하지 않는다.

### Q33. 보고서 AI에는 어떤 권한을 부여하는가?

**최종 입장:** 의미를 보존하는 문장 정리·요약·레이아웃 구성만 허용한다. JSON의 판정·수치·증거를 바꾸거나 없는 사실·원인·재현 성공을 추가하지 못하게 한다. JSON과 연결된 실제 증거가 원본이며 PDF의 핵심 내용과 대조한다.

### Q34. 개발용 정상·결함 사례는 성능 개선에 사용할 수 있는가?

**최종 입장:** 개발용 쌍은 프롬프트·규칙·도구·선별된 예시 개선에 활용할 수 있다. API 대화만으로 모델 가중치가 학습되는 것으로 취급하지 않는다. 최종 평가는 튜닝하지 않은 별도 사이트를 단일 입력으로 실행하며, 같은 계열의 사례와 정답이 유출되지 않도록 한다.

### Q35. 사람의 작업 시간 비교 실험은 필수로 수행하는가?

**최종 입장:** 전문 QA 경험과 참여 여건이 확보되면 추가한다. 기존 QA·일반 AI 보조·WebTestPilot 조건에서 품질과 작업 시간·전체 시간을 함께 비교하는 방식은 후보로 유지한다. 내부 팀원 실험은 방법 검증에 활용할 수 있지만 산업 현장의 시간 절감률 근거로 사용하지 않는다.

### Q36. 평가의 우선순위는 무엇인가?

**최종 입장:** 기술 벤치마크와 보고서 독립 재현 시험을 우선 진행한다. 실무 QA 시간 비교는 참여자·여건 확인 후 확정하는 조건부 평가다. 시간 실험이 미정이어도 탐지·오탐·재현·비용 평가 준비는 계속한다.

### Q37. 첫 통합 검증은 어떤 단위로 진행하는가?

**최종 입장:** 한 사이트의 짧은 흐름에서 실제 도구 행동·새 관찰·판정·추가 1회 재현·JSON까지 연결한다. PDF는 실행이 종료된 후 누적된 전체 JSON을 한 번 정리해 생성한다. 첫 주 프로토타입에 PDF와 네 범주 전체 완성을 동시에 요구하지 않는다.

### Q38. 보고서 생성 자원을 별도로 확보할 것인가?

**최종 입장:** 전체 안전 상한 안에서 JSON 정리·보고서 생성에 사용할 여유를 확보하는 원칙을 둔다. 새로운 탐색을 중단할 시점을 내부 설정으로 관리하고 남은 검사는 미완료로 표시한다. 배분량은 측정 후 정하며 사용자에게 필수 예산 입력을 추가하지 않는다.

### Q39. PDF 생성이 실패하면 어떻게 처리하는가?

**최종 입장:** JSON과 실제 증거를 보존하고 보고서 생성 실패를 검사 실패와 구분해 안내한다. 저장된 결과로 보고서만 다시 만드는 재생성 옵션을 제공한다. AI 실패 시 기본 레이아웃 PDF를 반드시 대신 생성하는 제안은 채택하지 않았으며, 없는 내용을 보완하거나 새 검사를 자동 시작하지 않는다.

## E. 책임·입출력·프로토타입: Q40~Q47

### Q40. 공통 실행 기반과 검사·보고서의 책임은 어떻게 나누는가?

**최종 입장:** 전처리 파트는 브라우저·탐색·관찰·증거 기반을, AI 파트는 MCP 연결·모델 도구 루프·검사·판정·재현 연계·JSON/PDF를 주도한다. 테스트/벤치마크 파트는 사이트·초기 상태·정답·독립 평가를 맡는다. 실행 권한·상한·같은 탭의 증거 연결은 공동 규격으로 정한다. 제품의 재현과 평가자의 독립 재현은 별개다.

### Q41. MCP 연결은 어느 파트가 주도하는가?

**최종 입장:** AI 파트가 MCP 클라이언트 연결과 모델·도구 실행 루프를 주도한다. 전처리 파트가 브라우저 수명주기·관찰·증거 수집 기반을 제공한다. 브라우저·탭·행동과 증거의 연결 규칙은 함께 합의하며 서로 독립된 브라우저로 같은 검사를 수행하지 않는다.

### Q42. 판단 AI의 입력과 기억은 어떤 구조인가?

**최종 입장:** 사이트 공통 문맥, 현재 페이지 관찰, 현재 검사 흐름의 세 묶음이다. 설명·기능·허용 행동·초기화, 요소·폼·제약·오류·이미지, 목표·시작 조건·이전 행동·기대 근거를 연결한다. 원본 전체를 무제한 누적하지 않고 요약·증거 참조·추가 관찰을 사용한다.

### Q43. 검사 계획·실제 실행·판정은 왜 분리하는가?

**최종 입장:** 계획만으로 실제 검사나 통과를 주장하지 않도록 구분한다. 실제 기록은 다음 행동과 상태 갱신, 발견 당시 경로 재현, 실패 원인 분석, 최종 JSON/PDF에 사용한다. 기록이 자동 모델 학습을 뜻하지 않으며, 별도 AI 세 개나 파일 세 개를 반드시 만들 필요는 없다.

### Q44. 개발·검증·최종 평가용 사이트는 어떻게 구성하는가?

**최종 입장:** 현재 제공된 정상·의도적 결함 사이트에서 작은 연결을 시작하고 여러 개념·구조의 개발용 사이트로 확대한다. 검증용과 최종 평가용은 별도로 확보하고 동일 템플릿 파생을 섞지 않는다. 정량 평가용 사이트 외에 승인된 상용 사이트 적용 사례를 추가할 수 있다. 특정 게시판·쇼핑몰 순서를 고정하지 않는다.

### Q45. 개발 일정과 순서는 어떻게 정하는가?

**최종 입장:** 전체 방향 확인, 연결 규격 합의, 기존 코드 연결, 짧은 실제 검사·재현·JSON, 범위 확대, 웹·PDF, 검증·최종 평가 순으로 진행한다. 첫 연결은 방향 확인 후 약 1주를 목표로 한다. 제출은 12월 첫째 주이며 11월 중순 안정화·하순 평가 여유는 권장 기준선이다. 고정 주차 완료 후 대기하지 않는다.

### Q46. 상용 사이트는 정량 평가와 같은 역할인가?

**최종 입장:** 아니다. 정답이 있는 최종 벤치마크가 정량 평가의 중심이고, 승인된 상용 사이트는 현실 적용 사례다. 모든 결함의 정답이 없으면 전체 탐지율을 계산했다고 주장하지 않는다. 실제 후보의 재현·담당자 확인 가능성·검사 한계·시간·비용을 확인하며 데이터 변경은 별도 허가와 환경이 필요하다.

### Q47. 1주 프로토타입의 완료 기준은 무엇인가?

**최종 입장:** 현재 사이트의 알려진 결함 사례 하나를 대상으로 정상·결함 버전을 독립 실행한다. 모델에는 정답을 알려주지 않고 실제 행동·관찰·근거 있는 판정·추가 재현·JSON 저장을 확인한다. 단순 API 응답이나 계획 생성만으로 완료하지 않는다. PDF와 네 범주 전체 완성은 다음 단계다.

## F. 제품 화면·로그인·실행 방식: Q48~Q56

### Q48. 최종 결과물에 웹 화면도 포함하는가?

**최종 입장:** 포함한다. URL·선택 정보 입력, 실행·중지, 진행 상태, 필요한 승인·준비 안내, 결과 다운로드, 보고서 재생성을 제공한다. 화면 디자인뿐 아니라 실제 실행 상태·결과와의 연결을 구현한다. 담당자 검토·이슈 관리 기능은 초기 범위에서 제외한다.

### Q49. 로그인 이후 기능도 지원하는가?

**최종 입장:** 테스트 계정으로 진입하는 기본 로그인을 포함한다. 첫 프로토타입은 단순 흐름으로 시작할 수 있지만 최종 범위에는 로그인 이후 검사가 포함된다. 복잡한 외부 인증·CAPTCHA 자동 해결과 인증 보안 취약점 검사는 별도 범위다.

### Q50. 브라우저·해상도의 필수 지원 범위는 무엇인가?

**최종 입장:** PC Chrome과 모바일 화면 크기의 반응형 UI·관련 상호작용 검사를 최종 필수로 한다. 대표 화면 조건을 정해 평가하고 정확한 목록은 세부 설계에서 결정한다. 실제 기기·모바일 Safari·다중 브라우저 호환성 검증까지 수행했다고 표현하지 않는다.

### Q51. 외부 API에 전달할 수 있는 데이터의 전제는 무엇인가?

**최종 입장:** 검사와 외부 API 전달이 승인된 테스트 계정·가상 데이터 환경을 전제로 한다. 비밀번호·API 키·세션 등 비밀값은 모델 입력·공유 결과에서 보호하고 증거는 기본적으로 실행 환경에 보존한다. 텍스트 마스킹으로 이미지 속 민감값까지 제거됐다고 가정하지 않으며 실개인정보 환경 지원은 초기 필수에서 제외한다.

### Q52. 로컬 실행과 서버 배포는 어떻게 계획하는가?

**최종 입장:** 개발은 로컬에서 진행하고 막바지 AWS 서버 배포를 검토할 수 있도록 구조를 잡는다. 서버 배포는 현재 추가 목표이며 핵심 검사·평가 완료를 희생하지 않는다. 서버는 제한된 사용자와 서버에서 접근 가능한 승인 대상부터 지원하고 사용자 PC의 localhost 자동 연결을 가정하지 않는다.

### Q53. 자동 로그인이 어려우면 어떻게 보완하는가?

**최종 입장:** 제공된 테스트 계정으로 기본 자동 로그인을 시도하고, 어려운 경우 사용자가 로그인 상태를 준비하는 경로를 제공한다. 비밀값은 프로그램이 처리하고 AI에 그대로 노출하지 않는다. 실패하면 로그인 이후 기능이 검사되지 않았다고 표시한다. 서버의 로그인 상태 준비는 실행 환경에 맞춰 정한다.

### Q54. 모바일에서 PC 기능 검사를 모두 반복하는가?

**최종 입장:** PC는 기본 기능을 검사하고 모바일에서는 UI와 화면 조건에 따라 달라지는 상호작용을 추가한다. 메뉴·모달·버튼 접근·가림·잘림 등을 확인하고 실제 수행 범위를 기록한다. 배치 차이 자체를 버그로 보지 않으며 모바일에서 발견한 문제는 해당 조건으로 재현한다.

### Q55. 실행 승인은 매 행동마다 받는가?

**최종 입장:** 시작 전에 정한 범위·행동 안에서는 자동 수행한다. 새 권한이나 불명확한 행동에만 확인을 요청한다. 거절되면 의존 검사는 미완료로 남기고 가능한 독립 검사를 계속한다. 승인을 반복해 검사 절차를 사용자에게 넘기거나 한 번의 승인으로 무제한 권한을 부여하지 않는다.

### Q56. 여러 검사 작업의 동시 실행과 중지는 어떻게 처리하는가?

**최종 입장:** 한 실행 환경에서는 작업 하나를 활성 실행하고 여러 사이트는 순차 처리한다. 진행 확인·중지를 지원하고 완료된 검사·증거를 보존해 부분 결과를 제공한다. 승인 후 계속 진행하는 것과 프로그램 종료 후 중간 지점 자동 복구는 다르며, 후자는 초기 필수에서 제외한다.

## G. 최종 보고·발생 단위·증거: Q57~Q66

### Q57. 시스템 판정과 담당자의 검토 결과는 어떻게 구분하는가?

**최종 입장:** 보고서에는 프로그램의 기대 근거·관찰·재현·검증 상태를 표시한다. AI 재현 성공을 사람의 확인 완료로 표현하지 않는다. 담당자 검토 입력·관리는 최종적으로 제외했으므로 담당자는 PDF를 받은 뒤 기존 업무 방식으로 검증한다.

### Q58. 담당자 검토 결과를 웹 화면에 입력해야 하는가?

**최종 입장:** 필요하지 않으며 초기 범위에서 제외한다. PDF 생성 전에 담당자의 버그 확인·오탐 판정을 기다리지 않는다. 단, 실행 권한 승인·로그인 보완·필요한 준비 안내는 별개의 실행 기능으로 유지한다.

### Q59. 서버는 누구에게 어떤 대상으로 제공하는가?

**최종 입장:** 개발 단계에서는 팀이 사용하고 배포 시에도 허용된 사용자부터 제공한다. 승인된 테스트·스테이징 대상, 실행 상한, 비밀값 보호, 결과 접근 제한을 유지한다. 누구나 임의 URL을 검사하는 공개 서비스와 사용자 PC의 자동 원격 연결은 초기 범위에서 제외한다.

### Q60. 유사한 문제가 다른 페이지에 나타나면 합칠 것인가?

**최종 입장:** 다른 페이지의 발생 사례는 별도 항목으로 보고한다. 핵심은 코드 원인의 추정·통합보다 어느 페이지에서 어떤 문제가 발생했는지를 제공하는 것이다. 평가 정답도 페이지별 사례에 맞추고, 같은 사례의 반복 발견·추가 재현은 중복 성공으로 세지 않는다.

### Q61. 추가 입력의 효과도 별도 평가할 것인가?

**최종 입장:** 평가한다. URL과 계정·범위·초기화 등 최소 실행 정보 조건, 짧은 설명·기존 요구사항을 추가한 조건을 구분한다. 탐지·오탐·판정 불가·비용 변화를 비교하고 추가 준비 부담의 가치도 해석한다. 어느 조건에도 결함 위치나 정답 힌트를 제공하지 않는다.

### Q62. 같은 페이지에서 화면 크기가 다른 동일 문제는 어떻게 표시하는가?

**최종 입장:** 페이지별 구분을 유지하면서 같은 페이지의 동일 문제에는 화면 크기별 발생 조건과 증거를 함께 표시한다. 서로 다른 상태·기대 조건의 문제는 구분한다. 같은 조건의 반복 발견과 추가 재현은 새 결함이 아니라 기존 항목의 증거다.

### Q63. 주요 증거를 PDF 안에 포함할 것인가?

**최종 입장:** 포함한다. 주요 스크린샷·필요한 오류와 로그 발췌·기대/실제 결과·재현 절차·화면 조건을 PDF 안에서 볼 수 있게 한다. 전체 로그·JSON·원본 증거는 별도로 보존·제공하되 다른 PC에서 접근할 수 없는 로컬 경로만 적어 증거 전달을 대신하지 않는다.

### Q64. 정확한 원인 분석·수정 제안도 필수인가?

**최종 입장:** 아니다. 필수는 문제 위치·기대/실제 동작·재현 절차·증거·검증 상태까지다. 브라우저 관찰만으로 정확한 코드·서버 원인을 항상 알아낸다고 약속하지 않는다. 근거 없는 원인·수정법을 채우지 않으며 실제 수정은 개발자가 수행한다.

### Q65. 스크린샷 촬영은 AI 요청에만 맡기는가?

**최종 입장:** 검사 행동 전후를 프로그램이 자동 기록한다. 최초 발견·추가 재현의 증거를 초기화 전에 보존한다. 촬영 시간·저장량을 측정한 뒤 반복 기록 최적화를 검토한다. 모든 사진을 모델에 전달하는 것은 아니며 AI 이미지 생성으로 실제 증거를 대체하지 않는다.

### Q66. 현재 화면과 전체 페이지 중 어느 사진을 기본으로 사용하는가?

**최종 입장:** UI 증거는 현재 보이는 화면 캡처를 기본으로 하고 전체 페이지는 필요한 경우 보조 자료로 사용한다. 화면 크기·스크롤 위치·관련 행동을 함께 기록한다. 촬영 실패는 사이트 결함이 아니며 사진이 필요한 판단에는 증거 부족을 표시한다.
