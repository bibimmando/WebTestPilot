# 멘토링 사전 자료: 기능·입력 버그 판정과 재현

> 2026-11-11 · 브랜치 `feature/member-01/qa-v2` (커밋 `bba1b72`) · 코드 `qa/src/`

## 1. 이 자료의 범위

QA 엔진이 실행 결과를 보고 무엇을 버그로 판정하는지, 그 판정을 어떻게 다시 확인하는지를 설명합니다.

- **기능 버그:** 링크, 버튼, 목록, 개수, 수량 등이 기대대로 동작하지 않는 것
- **입력 버그:** 잘못된 입력을 받아들이거나, 거부하면서 안내를 하지 않는 것

판정 앞 단계(사이트 탐색, 계획 작성)는 판정에 필요한 만큼만 설명합니다.

## 2. 큰 흐름: 버그 판정은 "계획한 검사의 실패"에서 시작합니다

엔진은 화면을 보고 "이상해 보인다"는 이유만으로 버그를 만들지 않습니다. 모든 버그는 **실행 전에 계획한 검사 하나가 실패한 것**에서 출발합니다.

```
[계획] AI가 사이트를 써 보고 검사를 작성  → 검사마다 "무엇을 읽어서, 무엇과, 왜 비교하나"
   ↓  계획을 실행 폴더에 복사해 고정 (이후 바뀌지 않음)
[실행] Playwright가 계획대로 행동하고 값을 읽음  → 실행 기록(ledger.jsonl)
   ↓
① 기록 대조      실행 기록을 믿지 않고, 고정된 계획으로 비교를 다시 계산
② 1차 분류       실패 원인이 기록만으로 분명한 것을 먼저 나눔 (차단, 준비 실패, 실행 안 됨)
③ AI 분류        애매한 실패만 AI가 "앱 문제냐, 자동화 문제냐"를 골라 증거 원문 인용과 함께 답함
④ 재현           결함 후보를 같은 계획으로 다시 실행해서 같은 결과가 나오는지 확인
⑤ 최종 등급      근거 종류 × 재현 결과로 등급을 정함
```

**설계 원칙**
1. **값 비교는 코드가 합니다.** AI는 원인 분류에만 쓰고, 분류할 때는 증거 파일의 원문을 인용해야 합니다.
2. **기대값에는 근거가 있어야 하고, 근거 종류가 등급의 상한을 정합니다.**
3. **재현되지 않은 결과는 버그로 올리지 않습니다.**
4. **판단하지 못한 항목은 숨기지 않고** "판단 불가"로 사유와 함께 보고합니다.

**"고정된 계획"이란**
- AI가 만든 계획(`plan.json`)을 실행 직전에 실행 폴더로 복사한 사본입니다.
- 정책(`policy.json`)과 실행 코드(`src/`)도 함께 복사하고, 해시를 `manifest.json`에 기록합니다.
- 실행, 기록 대조, 재현은 모두 이 사본만 씁니다. 그래서 실행 결과를 보고 기대값을 바꿀 수 없고, 재현은 최초 실행과 같은 조건으로 돌아갑니다.

## 3. 검사 하나는 이렇게 생겼습니다

```jsonc
{ "id": "S3.C2",
  "after": "S3.A1",                 // 언제 읽나: 시작 직후("start") 또는 어떤 행동 뒤
  "target": "T4",                   // 무엇을 읽나: 탐색 중 고정한 요소
  "read": "text",                   // 어떻게 읽나: text·value·checked·visible·count·url·items·visual
  "op": "equals",                   // 어떻게 비교하나: equals·contains·less·greater·same_number·sorted_asc …
  "expected_from": "S3.C1",         // 무엇과 비교하나: 고정값(expected) 또는 앞서 읽은 검사의 값
  "source": { "kind": "inferred", "rule": "link-target",
              "quote": "카드 이름이 상세 페이지 제목과 같아야 함" } }  // 왜 그게 정답인가
```

### 근거 4종 (`source.kind`)

| 근거 | 뜻 | 계획 검증이 거는 조건 | 등급 상한 |
|---|---|---|---|
| `requirement` | 사용자가 준 요구사항 문장 | 알려진 요구사항 ID여야 함 | 높음 |
| `constraint` | 화면 안내·HTML 제약 인용 | 탐색 중 실제로 본 텍스트여야 함. 검사 대상 자신의 이름이나 값은 인용할 수 없음 | 중간 |
| `inferred` | 일반 웹 규칙(`rules.ts`의 19개) | 목록에 있는 규칙 ID여야 하고, 그 규칙이 정한 비교 형태와 연산을 지켜야 함 | 중간 (결정적 규칙은 높음) |
| `observed` | 탐색 때 본 값 | 시작 시점 확인에만 쓸 수 있음. 행동 뒤 검사에는 거부 | 버그 근거 아님 |

- **`constraint`가 '중간'인 이유:** 인용한 문구가 그 기대값을 정말 뒷받침하는지는 코드가 확인할 수 없기 때문입니다.
- **대상 자신의 이름을 인용할 수 없는 이유:** 상품명을 제약으로 인용해서 '높음' 판정이 나온 실측 사례(10/16)가 있었습니다.
- **`observed`를 행동 뒤 검사에 쓸 수 없는 이유:** 탐색할 때 본 앱에 결함이 있을 수 있습니다. 그 화면을 정답으로 삼으면 결함이 정답이 됩니다.
- **결정적 규칙:** 화면에서 읽은 두 값을 코드가 직접 비교해서 판정이 정해지는 규칙입니다. 지금은 `link-target`, `count-matches-list` 두 개입니다.
- **HTML 제약(`maxlength` 등):** 근거로 인용할 수는 있지만, 탐색 화면에 속성이 보이지 않아서 실제로는 화면 문구만 쓰이고 있습니다.

### 일반 규칙의 비교 형태

일반 규칙마다 쓸 수 있는 비교 형태를 정해 두고, 계획 검증이 그 형태를 강제합니다. 관찰한 결함 값에 규칙 이름만 붙여 정답으로 고정하는 것을 막기 위해서입니다.

| 형태 | 뜻 | 규칙 예 |
|---|---|---|
| `relation` | 같은 시나리오에서 먼저 읽은 값과 비교(`expected_from`) | `link-target`, `step-by-one`(누르기 전 수량 +1), `action-has-effect`(누르기 전후가 다름) |
| `bound` | 크다·작다만 허용 | `quantity-bounds`(수량 > 0) |
| `items` | 목록 전체 조건 | `filter-matches`, `sort-order` |
| `hidden` | 기대값이 규칙에서 정해짐 | `close-dismisses`(앞서 열려 있음을 확인한 뒤 닫혀야 함) |
| `any` | 제한 없음 | `no-error-page`, `required-input`, `invalid-input-feedback` |

## 4. 한 항목이 버그가 되기까지 거치는 관문

검사 하나는 아래 관문을 차례로 통과해야 버그가 됩니다. 중간에 걸리면 사유와 함께 다른 결과로 남습니다.

```
실행 기록
 │
 ├─ 시나리오 기록이 계획과 어긋남(순서, 정책 위반, 탭 여러 개)? ── 예 → invalid → 판단 불가
 ├─ 검사 통과? ──────────────────────────────── 예 → 통과 → 버그 아님
 ├─ 금지 주소 뒤 / 쓰기 차단 바로 뒤의 실패? ──── 예 → 차단 → 판단 불가
 ├─ 선행조건 실패 / 앞이 멈춰서 실행 안 됨? ───── 예 → 준비 실패 → 판단 불가
 ├─ 값을 읽어 비교했는데 불일치?
 │    아니오(대상 못 찾음, 오류) → AI 분류 → 결함 후보여도 "값 못 읽음" → 판단 불가
 │    예 ↓
 ├─ AI 분류: 자동화 실패? ──────────────────── 예 → 버그 아님 (원래 불일치는 보존)
 │           판단 불가? ─────────────────────── 예 → 판단 불가
 ├─ 재현: 재실행에서 통과? ─────────────────── 예 → 판단 보류 (flaky)
 │        조건이 달라 비교 불가? ───────────── 예 → 판단 불가 (사유 기록)
 │        같은 결과 ↓
 └─ 최종 등급: 근거 종류로 결정
      requirement → bug_high
      inferred + 결정적 규칙 + 진짜 두 값 비교 → bug_high
      constraint / 그 밖의 inferred / 초기화 없이 재현 → bug_medium
      observed → 판단 불가 (결함 근거 아님)
```

AI 분류를 거치지 못한 불일치(한도 초과, 대화 실패)도 재현은 합니다. 하지만 분류가 끝나지 않았으므로 최종 등급은 판단 불가입니다.

## 5. 단계별 로직

### ① 기록 대조 (`reconcile.ts`)

**입력:** 고정된 계획, 실행 기록(`ledger.jsonl`)
**출력:** `results.json`

- **결과를 다시 계산합니다.** 기록에 적힌 통과·불일치를 그대로 쓰지 않고, 고정된 계획의 연산과 기대값으로 실제값을 다시 비교합니다. 기록과 다르면 다시 계산한 쪽을 쓰고 문제로 남깁니다.
- **`expected_from` 검사:** 참조한 검사가 실제로 읽은 값으로 기대값을 다시 풉니다. 참조 검사가 값을 읽지 못했으면 비교하지 않습니다.
- **무효 시나리오:** 기록 순서가 계획과 다르거나, 정책 위반이 있거나, 기록이 여러 탭에서 나오면 그 시나리오 전체를 무효로 봅니다.
- **실행되지 않은 검사:** `not_run`으로 남기고 분모에서 빼지 않습니다.

### ② 1차 분류 (`triage.ts` `preclassify`, AI 없음)

| 분류 | 조건 |
|---|---|
| `passed` / `passed_inferred` / `passed_observed` | 통과. 근거가 약한 통과는 따로 셈 |
| `mismatch` | 값을 읽었고 기대와 다름 |
| `needs_triage` | 행동 실패, 값을 못 읽음 등 원인을 모름 |
| `precondition_failed` | 시작 조건을 만들지 못함 |
| `not_run` | 앞 단계가 멈춰서 실행 안 됨. 멈춘 항목을 원인으로 기록 |
| `policy_blocked` | 금지 주소(로그아웃 등)로 가려다 막힌 뒤의 실패 |
| `write_blocked` | 같은 화면의 행동이 보낸 쓰기 요청을 우리가 막았고, 그 행동 바로 뒤 검사가 실패 |
| `not_applicable` | 같은 종류의 다른 페이지에서 이름으로 고정한 대상이 없음 |

`write_blocked`는 범위를 좁게 잡았습니다.
- **같은 화면만:** 행동 전후 URL이 같고 새 탭을 열지 않은 경우만 해당합니다. 이동이 틀린 결함까지 숨기면 안 되기 때문입니다.
- **바로 뒤 검사만:** 다음 행동 뒤의 실패는 그 행동 자체의 결함일 수 있어서 바꾸지 않습니다.

### ③ AI 분류 (`triage`)

**대상:** `mismatch`, `needs_triage`
**답:** `app_defect_candidate`(앱 결함 후보), `automation_failure`(자동화 실패), `uncertain`(판단 불가)

**AI에게 주는 것**
- 요구사항, 실패한 계획 항목, 고정한 대상 설명
- 비교 기록: 읽기 방식, 연산, 기대·실제값, 다시 읽은 횟수와 기다린 시간
- 행동 기록: 누른 요소의 접근성 표현과 화면 위치, 행동 전후 URL. **입력값은 원문 대신 길이만** 줌
- 일반 규칙 본문, 적용 조건, 정상 예외
- 쓰기 정책
  - 차단이면 막은 요청 목록
  - 허용이면 서버로 간 요청과 응답 상태
- 콘솔·요청 오류
- 실패 시점·시작 직후·행동 직전과 직후의 접근성 텍스트, 실패 시점 스크린샷 1장

**AI 답을 받는 조건 (코드가 검사)**
- 인용은 제공한 증거 파일에 **글자 그대로 있는 원문**이어야 하고, 공백을 빼고 6자 이상이어야 합니다.
- 실패 시점 증거가 있으면 그중 하나 이상을 인용해야 합니다.
- 조건을 어기면 돌려보내고 다시 받습니다(최대 3턴). 끝내 받지 못하면 분류 미완료로 둡니다.

**비용 절감:** 같은 검사가 기대값·실제값까지 같게 실패했다면 한 번만 분류하고, 복제 페이지들은 그 결과를 공유합니다.

### ④ 재현 (`reproduce`)

**대상:** 원래 불일치이거나 AI가 결함 후보로 본 항목
- AI가 자동화 실패로 분류했어도, 원래 불일치였다면 재현은 별도로 기록합니다.
- `write_blocked`는 같은 정책으로 다시 돌려도 판단할 수 없어서 제외합니다.

**방법:** 최초 실행 폴더의 `plan.json`과 `policy.json`으로 해당 시나리오만 다시 실행합니다.

**비교하지 않고 판단 불가로 두는 경우**

| 사유 | 조건 |
|---|---|
| `code_changed` | 실행 코드 해시가 최초와 다름 |
| `login_differs` | 로그인 여부가 다름 |
| `execution_incomplete` | 재실행이 무효이거나 값을 읽지 못함 |
| `start_differs` | 재실행에서 선행조건이 통과하지 못함 |
| `reset_unavailable` / `reset_failed` | 쓰기 허용 실행에서 초기화가 없거나 실패 |
| `result_differs` | 값은 읽었지만 최초와 다른 불일치 |

**결과 서명 비교**
- 검사는 `상태|실제값|요소 수|오류 문구`로 비교합니다. 오류 문구의 숫자는 지웁니다.
- `expected_from` 검사는 실제값을 서명에서 뺍니다. 추천 카드처럼 회차마다 값이 달라도 같은 규칙이 다시 깨지면 같은 결과로 봅니다.
- 서명이 같으면 `reproduced`, 재실행에서 통과하면 `flaky`입니다.

**초기화와의 관계**

| 실행 | 재현 전 처리 |
|---|---|
| 쓰기 차단 (기본) | 초기화하지 않음. 우리가 서버 상태를 바꾸지 않았고, 초기화 자체가 쓰기라서 |
| 쓰기 허용 + 초기화 등록 | 앱 설정에 등록된 초기화 요청을 프로그램이 호출하고, 확인 요청으로 초기 상태인지 검사 |
| 쓰기 허용 + 초기화 없음 | `expected_from`으로 같은 시나리오 안의 앞뒤를 비교하는 검사만 재현(확신 중간까지). 나머지는 `reset_unavailable` |

### ⑤ 최종 등급 (`systemVerdict`)

| 등급 | 조건 |
|---|---|
| `bug_high` | 요구사항 위반이 재현되고 AI가 증거 인용으로 자동화 실패가 아님을 보임 |
| `bug_high` | 결정적 관계 규칙 위반이 재현됨. 참조한 값이 다른 시점이나 다른 대상에서 읽혔을 때만 (같은 요소를 다시 읽는 비교 제외) |
| `bug_medium` | 화면 안내 위반, 그 밖의 일반 규칙 위반, 초기화 없이 앞뒤 비교로 재현 |
| `ui_defect` / `improvement` | 시각 위반 재현(조작을 막으면 `ui_defect`), 철자 규칙 위반 |
| `hold` (판단 보류) | 재현 안 됨, 행동 실패만 재현, 같은 종류 페이지에서 대상 없음 |
| `incomplete` (판단 불가) | 분류·재현 미완료, 값을 못 읽음, 실패 시점 증거 수집 실패, 쓰기·정책 차단, 근거가 `observed` |
| `not_bug` | 통과, 자동화 실패로 분류 |

판정 파일은 덮어쓰지 않습니다. 다시 판정하면 `verdicts-2.json`, `repro-2`처럼 새로 만듭니다.

## 6. 예시 1: 기능 버그가 판정되는 전 과정

> 아래 값은 이해를 돕기 위한 예시입니다. 실행 결과에서 가져온 것이 아닙니다.

**상황:** 상품 목록에서 카드 "린넨 셔츠"를 누르면 "코튼 팬츠" 상세가 열리는 결함

**1. 계획 (AI가 작성, 계획 검증 통과)**

```jsonc
"steps":  [{ "id": "S3.A1", "op": "click", "target": "T4" }],          // T4 = 목록 첫 번째 카드
"checks": [
  { "id": "S3.C1", "after": "start", "target": "T4", "read": "text", "op": "equals",
    "expected": "린넨 셔츠", "source": { "kind": "observed" }, "precondition": true },  // 시작 상태 확인
  { "id": "S3.C2", "after": "S3.A1", "target": "T7", "read": "text", "op": "equals",  // T7 = 상세 페이지 제목
    "expected_from": "S3.C1",
    "source": { "kind": "inferred", "rule": "link-target", "quote": "카드에 적힌 상품명이 열린 상세의 제목과 같아야 함" } }
]
```

- `link-target`은 `relation` 형태라 `expected_from`이 없으면 계획 검증이 거부합니다.
- 행동 뒤 검사에 "린넨 셔츠"를 고정값으로 쓰면서 근거를 `observed`로 적어도 거부됩니다.

**2. 실행 기록**

```jsonc
{"kind":"check","id":"S3.C1","status":"passed","actual":"린넨 셔츠","expected":"린넨 셔츠", ...}
{"kind":"act","id":"S3.A1","status":"ok","urlBefore":".../products","url":".../product/88", ...}
{"kind":"check","id":"S3.C2","status":"mismatch","actual":"코튼 팬츠","expected":"린넨 셔츠","reads":51,"waitedMs":5020, ...}
```

**3. 단계별 처리**

| 단계 | 처리 | 결과 |
|---|---|---|
| ① 기록 대조 | `S3.C1`의 실제값 "린넨 셔츠"로 기대값을 다시 풀고 "코튼 팬츠"와 비교 | `mismatch` 확인 |
| ② 1차 분류 | 값을 읽은 불일치, 차단 없음 | `mismatch` |
| ③ AI 분류 | 클릭한 요소가 "린넨 셔츠" 카드였고(행동 기록), 직후 화면 제목이 "코튼 팬츠"임을 실패 시점 증거에서 인용 | `app_defect_candidate` |
| ④ 재현 | 같은 계획으로 재실행, 서명 `mismatch|1|`이 같음(`expected_from`이라 실제값 제외) | `reproduced` |
| ⑤ 최종 등급 | 결정적 규칙(`link-target`) + 다른 시점·다른 대상에서 읽은 두 값의 비교 | **`bug_high`** |

**다른 결과가 나오는 경우**
- 5초 동안 51번 다시 읽었는데 첫 읽기가 로딩 중 문구였다면, AI가 "너무 일찍 읽음"으로 보고 자동화 실패로 분류할 수 있습니다 → `not_bug`
- 재실행에서는 "린넨 셔츠"가 열렸다면 → `hold`(재현 안 됨)
- 클릭할 때 카드가 2개로 찾아졌다면 행동이 실행되지 않습니다(`not_executed`). 그러면 결과가 둘로 나뉩니다.
  - 행동: AI 분류를 거쳐 앱 결함 후보로 분류되고 재현까지 되면 `hold`(행동 실패만 재현, 근거 없음)
  - 뒤 검사 `S3.C2`: 실행되지 않아 `not_run` → 판단 불가

## 7. 예시 2: 입력 검증 버그가 판정되는 전 과정

> 아래 값은 이해를 돕기 위한 예시입니다.

**상황:** 회원가입 폼의 이메일 칸에 `notanemail`을 넣고 가입 버튼을 누름

**1. 계획**

```jsonc
"steps": [
  { "id": "S5.A1", "op": "fill",  "target": "T2", "value": "notanemail" },   // 이메일 칸
  { "id": "S5.A2", "op": "click", "target": "T3" }                           // 가입 버튼
],
"checks": [
  { "id": "S5.C1", "after": "start", "read": "url", "op": "equals", "expected": ".../signup",
    "source": { "kind": "observed" }, "precondition": true },
  { "id": "S5.C2", "after": "S5.A2", "read": "url", "op": "equals", "expected_from": "S5.C1",
    "source": { "kind": "inferred", "rule": "invalid-input-feedback", "quote": "형식이 틀린 이메일은 받아들여지지 않아 가입 화면에 남아야 함" } },
  { "id": "S5.C3", "after": "S5.A2", "target": "T5", "read": "visible", "op": "equals", "expected": "true",
    "source": { "kind": "inferred", "rule": "invalid-input-feedback", "quote": "형식 오류 안내가 보여야 함" } }
]
```

- 입력 검증 규칙(`invalid-input-feedback`, `required-input`)은 형태가 `any`라서 확신은 **최대 중간**입니다.
- `T5`(오류 안내 요소)는 탐색 중에 AI가 직접 틀린 값을 넣어서 안내가 나온 것을 보고 고정한 요소입니다.
- 계획에 값을 넣는 시나리오가 있는데 형식 오류 값 검사가 없으면, 계획 단계에서 한 번 더 묻습니다(11/8부터).

**2. 앱의 동작에 따라 결과가 갈립니다**

| 앱의 동작 | 쓰기 차단 실행 (기본) | 쓰기 허용 + 초기화 등록 | 쓰기 허용 + 초기화 없음 |
|---|---|---|---|
| **A.** 클라이언트에서 막고 안내 표시 (요청 안 나감) | C2·C3 통과 → `not_bug` | 같음 | 같음 |
| **B.** 클라이언트 검증 없이 POST를 보냄 | 막힌 요청 뒤 C3 실패 → `write_blocked` → **판단 불가** | 아래 C 또는 D로 진행 | 아래 C 또는 D로 진행 |
| **C.** 서버가 4xx로 거부하고 안내 표시 | — | C2·C3 통과 → `not_bug` | 같음 |
| **D.** 서버가 2xx로 받아들이고 완료 화면으로 이동 | — | C2·C3 불일치 → AI가 2xx 응답을 근거로 결함 후보 → 초기화 뒤 재현 → **`bug_medium`** | C2(`expected_from`)는 초기화 없이 재현 → **`bug_medium`**. C3(고정값)은 `reset_unavailable` → 판단 불가 |

**이 표에서 볼 점**
- **쓰기 차단에서는 B를 버그로 올리지 않습니다.** 서버에서만 검증하는 설계일 수 있어서입니다. 대신 판단 불가 사유에 "막은 쓰기 요청"이 남아서, 쓰기 허용 실행으로 다시 확인할 대상이 됩니다.
- **D를 버그로 올리려면 쓰기 허용과 초기화가 함께 필요합니다.** 초기화가 없으면 앞뒤 비교(`expected_from`) 형태의 검사만 살아남습니다.
- **쓰기 허용 실행에서는 AI 분류에 서버 응답 상태가 들어갑니다.** 그래서 C(거부)와 D(수락)를 가를 수 있습니다.

## 8. 입력 검증: 실측에서 놓친 이유와 남은 한계

### 실측에서 놓친 이유

| 실행 | 놓친 이유 |
|---|---|
| 중간발표 (심어 둔 버그 25개) | 입력 검증 버그 5개가 **모두** 폼까지 못 갔거나(탐색 범위) 쓰기가 필요했음. 판정이 약해서가 아니라 판정 단계까지 오지 못함 |
| email 앱 A (11/5, 쓰기 차단) | 형식 안내는 있었는데 계획이 **빈 값만** 넣음. 형식 오류 값을 시도하지 않음 → "한 번 더 묻기" 추가(11/8) |
| email 앱 E (11/8, 쓰기 허용) | 형식 오류 검사 2개가 **불일치를 잡았지만** 버그는 0건. 하나는 초기화가 없어 재현하지 못했고(판단 불가), 하나는 AI 분류가 판단 불가 |

정리하면 지금 막히는 곳은 순서대로 이렇습니다.
1. 폼까지 도달하기
2. 형식 오류 값을 계획하기
3. 쓰기와 재현(초기화)

### 엔진이 아직 못 하는 것

실측에서 이것 때문에 놓친 사례는 아직 없습니다. 브라우저 기본 검증에만 기대는 사이트에서 검사 범위와 등급을 제한합니다.

1. **유효성 상태를 읽지 못합니다.** `validity`, `validationMessage`가 접근성 트리에 없습니다. 오류 문구 없이 브라우저 말풍선만 쓰는 사이트는 "제출 뒤 화면이 그대로인가"로만 간접 확인합니다.
2. **HTML 속성이 탐색 화면에 보이지 않습니다.** 화면 문구 없이 `maxlength`만 있는 칸은 근거를 만들 수 없습니다.
3. **글자 수 비교 연산이 없습니다.** 길이 제한은 화면 카운터가 있을 때만 간접으로 검사합니다.
4. **오류 문구와 입력칸을 연결해서 읽지 못합니다.** `aria-invalid`, `aria-describedby` 연결이 없습니다.

### 과적합을 막는 판단 기준

이 기준은 팀 통합 파이프라인용 skill(`webtestpilot-input-validation`)에 정리했습니다.
- `required` 속성이 없거나 `novalidate`인 것만으로는 결함이 아닙니다. 서버 검증과 앱 자체 안내를 쓰려고 브라우저 검증을 끄는 것은 권장되는 설계입니다.
- 한도를 넘겨 입력하게 두고 경고로 표시하는 것, 입력 마스크가 값을 고치는 것도 결함이 아닙니다.
- 화면 안내가 없는 상식 규칙은 결과가 깨질 때만 후보로 봅니다. NaN, 음수 합계, 5xx, 값이 조용히 바뀌는 경우입니다.
- 이메일 `+` 허용, 공백 trim처럼 정책일 수 있는 것은 질문으로 남깁니다.
- 실제 서비스 1곳(GitLab 회원가입)에서 쓰기 차단으로 직접 점검했고, 오탐은 0건이었습니다.

## 9. 멘토님께 여쭙고 싶은 것

1. **확신 등급:** 화면 안내 근거와 입력 검증 규칙을 '중간'으로 묶어 두었습니다. 인용 문구와 기대값의 관계를 기계적으로 확인할 방법이 없어서인데, 현업에서는 이런 근거를 어떻게 등급화하나요?
2. **재현 기준:** 지금은 1회 재실행에서 결과 서명이 같으면 재현으로 봅니다. 시간에 따라 바뀌는 화면에서 횟수를 늘리거나 통계로 판단하는 게 필요할까요?
3. **초기화 없는 서비스:** 실제 서비스는 서버 상태를 되돌릴 수 없어서 쓰기 차단으로만 검사하고, 쓰기가 필요한 검증은 초기화할 수 있는 테스트 사이트로 나누려 합니다. 이 분담이 평가 방법으로 타당한가요?
4. **HTML 속성을 근거로 쓰는 문제:** 브라우저 기본 검증 상태를 판정 근거로 쓰면 HTML 속성 자체를 "앱이 밝힌 규칙"으로 인정하는 셈입니다. 화면 문구가 없는 속성을 근거로 삼아도 될까요?
