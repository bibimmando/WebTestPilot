# QA v2 전체 로직 정리

> 2026-11-11 · 브랜치 `feature/member-01/qa-v2` (커밋 `bba1b72`) · 코드 `qa/src/`
>
> 각 단계의 입력, 출력, 내부 세부 로직을 정리했습니다. 코드는 `qa/src/` 기준입니다.

## 0. 한눈에 보기

```
입력: 시작 URL (+ 요구사항, 앱 설정)
 │
 ├─ 0. 준비            cli.ts, login.ts, reset.ts        코드
 ├─ 1. 사이트 지도      sitemap.ts                        코드
 ├─ 2. 탐색·계획        explore.ts, plan.ts, browser.ts   AI (계획 검증은 코드)
 ├─ 3. 계획 고정·실행    run.ts, generate.ts, fixture.ts   코드 (Playwright)
 ├─ 4. 기록 대조        reconcile.ts                      코드
 ├─ 5. 판정             triage.ts, visual.ts              코드 + AI(분류만)
 │    5-1 1차 분류 → 5-2 AI 분류 → 5-3 시각 판정 → 5-4 재현 → 5-5 최종 등급
 ├─ 6. 발견 제목        headline.ts                       AI (코드가 대조)
 └─ 7. 보고서           report.ts                         코드
 │
출력: runs/<이름>-<시각>/report.json · report.html · report.pdf
```

**핵심 원칙**
- AI는 무엇을 어떻게 검사할지 정하는 데까지만 씁니다(2단계).
- 그 계획을 파일로 고정하고, 실행과 값 비교는 코드가 합니다(3~4단계).
- 고정 뒤에 AI가 다시 나오는 곳은 세 군데뿐입니다: 실패 원인 분류, 시각 판정, 발견 제목. 셋 다 계획이나 비교 결과를 바꾸지 않습니다.

## 1. 단계별 입력·출력 요약

| 단계 | 입력 | 출력 |
|---|---|---|
| 0. 준비 | 명령행 옵션, 요구사항 JSON, 앱 설정 JSON | 정책(policy), 로그인 상태, 예산 장부, 결과 폴더 |
| 1. 사이트 지도 | 시작 URL, 정책 | `SiteMap`: 페이지 종류(템플릿), 방문·미방문 URL, 깨진 링크, 화면 점검 결과 |
| 2. 탐색·계획 | 사이트 지도, 요구사항, 정책 | `plan.json`: 시나리오, 고정한 대상, 기능 목록, 미계획, 질문, 관찰 |
| 3. 실행 | `plan.json`, 정책, 로그인 상태 | `run/` 폴더: 고정 사본, `ledger.jsonl`(실행 기록), `evidence/`(증거) |
| 4. 기록 대조 | 고정된 계획, `ledger.jsonl` | `results.json`: 시나리오별 결과, 요구사항별 집계, 문제 목록 |
| 5. 판정 | 계획, `results.json`, 증거 | `verdicts.json`(항목별 분류·재현·등급), `repro/`(재실행 폴더) |
| 6. 발견 제목 | 판정 결과 | `headlines.json` |
| 7. 보고서 | 위 파일 전부 | `report.json`, `report.html`, `report.pdf` |

## 2. 단계별 세부 로직

### 0. 준비 (`cli.ts`)

**입력**
- `--url`(필수), `--requirements`, `--app`, `--budget`(기본 $10), `--allow-writes`(기본 꺼짐)
- 페이지 수 한도 등 기타 옵션

**세부 로직**
1. **정책을 만듭니다.**
   - 허용 origin: 기본은 시작 URL의 origin
   - 쓰기 허용 여부
   - 금지 주소: 앱 설정의 `deny`, 예: logout
2. **비용 장부(`Budget`)를 만듭니다.**
   - 모든 AI 호출이 장부 하나를 함께 쓰고, 호출하기 전에 최악의 비용을 먼저 예약합니다(`agent.ts`).
   - 탐색 단계는 예산의 30%를 분류·재현 몫으로 남겨 둡니다.
3. **로그인합니다** (`login.ts`, 앱 설정에 로그인 절차가 있을 때만).
   - 프로그램이 직접 로그인해서 브라우저 상태(쿠키, 저장소)를 만듭니다.
   - 실패해도 멈추지 않고 로그인 없이 진행하며, 보고서에 남깁니다.
   - 비밀번호는 환경 변수에서만 읽고 AI 입력이나 기록에 넣지 않습니다.
4. **초기화를 준비합니다** (`reset.ts`, 쓰기 허용 + 앱 설정에 `reset`이 있을 때만).
   - 등록된 요청 하나를 보내고, 확인 요청으로 초기 상태인지 검사합니다.
   - 실행 전에 한 번, 재현 전에 한 번 부릅니다.

**출력**
- `policy`, `storageState`(로그인 상태), `budget`
- 결과 폴더 `qa/runs/<이름>-<시각>/`

### 1. 사이트 지도 (`sitemap.ts` `crawl`)

**입력:** 시작 URL, 정책. 쓰기 허용 여부와 상관없이 **항상 읽기 전용**입니다.

**세부 로직**
1. **너비 우선 방문**
   - 같은 origin의 `a[href]` 링크만 따라갑니다.
   - 방문 한도는 기본 30페이지이고, 같은 종류는 2페이지까지만 방문합니다.
2. **페이지 종류로 묶기** (`groupTemplates`)
   - 경로 조각 중 식별자처럼 보이는 것(숫자, 한글, 인코딩 문자, 긴 조각)은 `:x`로 바꿉니다.
   - 한 위치만 다른 경로가 둘 이상이면 그 위치도 `:x`로 묶습니다.
   - 예: `/product/12`, `/product/35` → `/product/:x`
   - 첫 경로 조각(`/products`, `/cart`)은 서로 다른 기능이라 묶지 않습니다.
3. **깨진 링크**
   - 따라간 링크가 404·410·5xx면 페이지 종류에 넣지 않고 "깨진 링크"로 기록합니다.
   - 한 번 더 요청해서 같은 결과면 확인됨(`confirmed`)으로 봅니다.
4. **화면 점검** (`auditPage`, AI 없음)
   - 데스크톱과 모바일 폭에서 이름 없는 버튼, 가림, 가로 넘침, 글자 대비 등을 잽니다.
   - 문제가 나온 페이지는 새로 열어 다시 재고, 두 번 다 나온 것만 확인됨으로 봅니다.

**출력:** `SiteMap`

| 필드 | 내용 |
|---|---|
| `templates` | 페이지 종류와 그 페이지들 |
| `visited`, `unvisited`, `failed` | 방문한 URL, 한도 때문에 못 간 URL, 이동 실패한 URL |
| `broken` | 깨진 링크 |
| `audit` | 화면 점검 결과 |

### 2. 탐색·계획 (`explore.ts`, `browser.ts`, `plan.ts`)

**입력:** 사이트 지도, 요구사항(선택), 정책, 로그인 상태

**세부 로직**

1. **페이지 종류마다 AI 대화를 하나씩 엽니다.**
   - 시작 페이지의 종류부터 시작하고, 기본 8종류까지 합니다.
   - 대화마다 **새 브라우저 상태**로 시작합니다. 앞 대화에서 담은 장바구니를 보고 계획하면, 실행할 때 시작 조건이 맞지 않기 때문이에요.
   - 대화 하나는 기본 25턴입니다.

2. **AI가 쓰는 도구**

   | 도구 | 하는 일 |
   |---|---|
   | `snapshot` | 페이지의 접근성 트리를 `ref` 번호와 함께 읽음 |
   | `navigate`, `click`, `fill`, `select`, `press` | 실제 브라우저 조작 |
   | `pin` | 계획에 쓸 요소를 고정하고 대상 ID(`T1`…)를 받음 |
   | `read_guide` | 기능 유형별 점검 안내 읽기(입력 폼, 목록, 이동, 메뉴, 흐름, 화면) |
   | `ask_user` | 업무 규칙에 달린 질문 남기기. 답을 기다리지 않음 |
   | `submit_plan` | 계획 제출 |

3. **`pin`: 대상 고정**
   - `ref`는 그 순간의 번호라서 재실행에 쓸 수 없습니다. 그래서 역할, 이름, 라벨 영역, 순서 같은 **구조화된 설명(`Target`)**으로 바꿉니다.
   - 같은 페이지를 새로 열었을 때 사라지는 요소는 거부합니다(`stableOnReload`). 재실행할 수 없기 때문이에요.
   - 추천 목록처럼 매번 바뀌는 요소는 이름 대신 순서로 고정합니다(`position=true`).

4. **`submit_plan`: 계획 검증** (`plan.ts`의 `validate`)
   - **근거:** 검사마다 근거 4종(`requirement`, `constraint`, `inferred`, `observed`) 중 하나가 필요합니다.
   - **행동 뒤 검사:** 탐색 때 본 값(`observed`)을 기대값으로 쓸 수 없습니다.
   - **화면 안내 근거(`constraint`):** 인용 문구가 탐색 중에 실제로 본 텍스트여야 하고, 검사 대상 자신의 이름이면 안 됩니다.
   - **일반 규칙 근거(`inferred`):** 규칙 목록(`rules.ts`)에 있는 ID여야 하고, 그 규칙이 정한 비교 형태와 연산을 지켜야 합니다.
   - **대상과 범위:** `pin`한 대상만 쓸 수 있고, 허용 origin 안이어야 합니다.
   - **제출 결과:**
     - 오류가 있는 시나리오만 돌려보내고, 통과한 시나리오는 받아 둡니다(10/30부터).
     - 정책 위반이 하나라도 있으면 계획을 받지 않습니다.

5. **한 번 더 묻기**
   - 계획이 통과했어도 아래 경우에는 한 번 더 확인을 요청합니다. 거부는 아닙니다.
     - 입력칸에 값을 넣는 시나리오가 있는데 형식 오류 값 검사가 없을 때
     - 턴을 절반도 쓰지 않고 끝냈을 때(옵션)
   - 그대로 다시 제출하면 확정됩니다.

6. **대화가 계획 없이 끝났을 때**
   - 받아 둔 시나리오만으로 계획을 만들고, 못 다룬 기능은 미계획(`unplanned`)에 이유와 함께 남깁니다.
   - 턴 한도로 끝난 종류는 새 대화로 한 번 더 시도합니다.

7. **합치기와 복제**
   - 종류별 계획을 하나로 합칩니다.
   - 같은 종류의 다른 페이지(기본 대표 포함 3개)에 시나리오를 복제합니다(`variantOf` 표시).

**출력:** `plan.json`

| 필드 | 내용 |
|---|---|
| `scenarios` | 시작 URL, 행동 목록(`steps`), 검사 목록(`checks`), 다루는 요구사항·기능(`covers`) |
| `targets` | `T#` → 구조화된 대상 설명 |
| `features` | 탐색으로 찾은 기능(`F#`) |
| `unplanned` | 계획하지 못한 기능과 이유 |
| `questions` | 업무 규칙 질문 |
| `observations` | 검사로 만들지 못한 관찰 |

**검사 하나의 구조** (`Check`)

```
{ id, after: 'start' 또는 행동ID,  // 언제 읽나
  target, read: 'text'|'value'|'checked'|'visible'|'count'|'url'|'items'|'visual',  // 무엇을 읽나
  op: 'equals'|'contains'|'less'|..., // 어떻게 비교하나
  expected  또는  expected_from(앞서 읽은 검사 ID) + offset,  // 무엇과 비교하나
  source: { kind, id|rule, quote },  // 왜 그게 정답인가
  precondition?: true }              // 시작 상태 확인용인가
```

### 3. 계획 고정·실행 (`run.ts`, `generate.ts`, `fixture.ts`)

**입력:** `plan.json`, 정책, 로그인 상태, 동시 실행 수

**세부 로직**

1. **다시 검증합니다.** 계획 검증을 한 번 더 돌리고, 통과하지 못하면 실행하지 않습니다.
2. **고정합니다.** 새 실행 폴더(`run/`)에 다음을 복사합니다. 폴더가 이미 있으면 거부해요.
   - `plan.json`, `policy.json`
   - 실행 코드 사본 `src/`
   - 위 파일들의 해시를 담은 `manifest.json`
3. **테스트 파일을 만듭니다** (`generate.ts`).
   - 시나리오마다 `S1.spec.ts` 같은 파일이 생기는데, **ID만 들어 있습니다.**
   - 실행 순서는 `start → 시작 시점 검사 → (행동 → 그 행동 뒤 검사)… → finish`입니다.
   - 실제 연산, 값, 기대값은 실행 헬퍼가 `plan.json`에서 읽어요. 그래서 같은 계획이면 항상 같은 코드가 됩니다.
4. **Playwright로 실행합니다.**
   - 재시도는 하지 않습니다.
   - 쓰기 허용 실행은 시나리오끼리 서버 상태를 공유하므로 동시에 돌리지 않습니다.

**실행 헬퍼 (`fixture.ts`)**

모든 결과를 바로 `ledger.jsonl`에 한 줄씩 씁니다.

| 함수 | 하는 일 |
|---|---|
| `start` | 시작 URL로 이동 → 화면이 멈출 때까지 대기 → 시작 화면 증거 저장 → 화면 점검 기준선 측정 |
| `act` | 행동 하나를 아래 순서로 실행 |
| `check` | 검사 하나를 아래 순서로 실행 |
| `finish` | 마지막 행동 뒤 화면 점검 |

**`act`의 순서**
1. 대상을 찾고, **정확히 1개**인지 확인합니다. 아니면 `not_executed`(`target_changed`)로 남기고 시나리오를 멈춥니다.
2. 금지 주소로 가는 링크면 누르지 않습니다(`denied_by_app_config`).
3. 실제 효과 없이 누를 수 있는지만 먼저 확인합니다(`trial` 클릭).
4. 행동 직전 화면과, 누를 요소의 접근성 표현·화면 위치를 기록합니다.
5. 행동을 실행합니다. 도중에 오류가 나면 실행됐는지 알 수 없으므로 `uncertain_execution`으로 남기고 멈춥니다.
6. 행동 직후 화면을 기다리지 않고 바로 기록합니다.

**`check`의 순서**
1. 기대값을 정합니다. 고정값이거나, 앞서 읽은 검사의 실제값(`expected_from`)에 `offset`을 더한 값입니다.
2. **기한(기본 5초)까지 반복해서 읽습니다.** 비동기로 그려지는 화면 때문이에요.
   - 첫 읽기 값도 함께 남깁니다.
   - "없어서 안 보임"으로 통과한 경우는 1.5초 동안 계속 없어야 확정합니다.
3. 불일치는 시나리오를 멈추지 않습니다. 단 선행조건 검사가 실패하면 멈춥니다.
4. 시각 검사(`read: visual`)는 판단하지 않고, 화면을 촬영한 뒤 `visual_pending`으로 남깁니다.

**네트워크 정책 (`browser.ts`의 `guardContext`)**
- 다른 origin으로 가는 스크립트, fetch, 이동은 막습니다. 이미지·글꼴·스타일시트는 허용합니다.
- 쓰기 차단 실행에서는 POST 같은 쓰기 요청을 막고 기록합니다(`writeBlocked`).
- 쓰기 허용 실행에서는 요청과 응답 상태를 기록합니다(`writes`).

**출력** (`run/` 폴더)

| 파일 | 내용 |
|---|---|
| `plan.json`, `policy.json`, `src/`, `manifest.json` | 고정 사본 |
| `specs/` | 생성된 테스트 파일 |
| `ledger.jsonl` | 실행 기록: `start`, `act`, `check`, `policy` 줄 |
| `evidence/` | 접근성 텍스트와 스크린샷(비밀번호 칸은 가림) |

### 4. 기록 대조 (`reconcile.ts`)

**입력:** 고정된 계획, `ledger.jsonl`

**세부 로직**
1. **무효 시나리오를 가려냅니다.** 아래 중 하나면 그 시나리오를 무효로 봅니다.
   - 기록 순서가 계획과 다름
   - 시작에 실패했는데 뒤 기록이 있음
   - 정책 기록이 없음
   - 정책 위반이 있음
   - 기록이 두 개 이상의 탭에서 나옴
2. **검사 결과를 다시 계산합니다.**
   - 고정된 계획의 연산과 기대값으로 실제값을 다시 비교하고, 기록과 다르면 다시 계산한 값을 씁니다.
   - `expected_from` 검사는 참조한 검사의 실제값으로 기대값을 다시 풉니다.
3. **선행조건을 정리합니다.** 결과는 `none`(선언 안 함), `met`(모두 통과), `failed`(실패) 중 하나입니다.
4. **정책 정보를 모읍니다.** 막힌 주소, 막은 쓰기 요청, 허용된 쓰기와 응답, 새 탭, 콘솔·요청 오류, 화면 점검 결과
5. **요구사항별로 집계합니다.** 실행되지 않은 검사도 분모에 넣습니다.

**출력:** `results.json` = `{ scenarios, requirements, problems }`

### 5. 판정 (`triage.ts`, `visual.ts`)

**입력:** 계획, `results.json`, 증거 파일, 로그인 상태, 초기화 함수

#### 5-1. 1차 분류 (`preclassify`, AI 없음)

| 상황 | 분류 |
|---|---|
| 무효 시나리오 | `invalid` |
| 통과 | `passed` / `passed_inferred` / `passed_observed` |
| 값을 읽었고 불일치 | `mismatch` |
| 시작·행동 실패, 값을 못 읽음 | `needs_triage` |
| 선행조건 실패 | `precondition_failed` |
| 앞이 멈춰서 실행 안 됨 | `not_run` |
| 금지 주소 뒤 | `policy_blocked` |
| 같은 화면에서 막은 쓰기 요청 바로 뒤의 실패 | `write_blocked` |
| 복제 페이지에서 이름으로 고정한 대상이 없음 | `not_applicable` |
| 시각 검사 | `needs_visual` |

#### 5-2. AI 분류 (`triage`)

- **대상:** `mismatch`, `needs_triage`
- **AI 답:** 앱 결함 후보, 자동화 실패, 판단 불가 중 하나
- **AI에게 주는 것:**
  - 비교 기록
  - 행동 기록(입력값은 길이만)
  - 일반 규칙과 정상 예외
  - 쓰기 정책
  - 콘솔·요청 오류
  - 실패 시점·행동 전후 접근성 텍스트, 스크린샷 1장
- **답을 받는 조건:** 증거 파일에 그대로 있는 원문을 6자 이상 인용해야 하고, 실패 시점 증거를 하나 이상 인용해야 합니다. 어기면 돌려보냅니다(최대 3턴).
- **같은 검사 공유:** 기대값·실제값까지 같은 실패는 한 번만 분류하고 결과를 공유합니다.

#### 5-3. 시각 판정 (`visual.ts`)

- AI는 검사에 적힌 조건마다 `met`(충족), `unmet`(위반), `unknown`(판단 불가)과 근거를 답합니다.
- 판정은 코드가 정하고, **낮추는 방향으로만** 정합니다.
  - 근거 있는 위반이 하나라도 있으면 결함 후보
  - 위반은 없고 판단 불가가 있으면 증거 부족
  - 모두 충족이면 통과

#### 5-4. 재현 (`reproduce`)

- **대상:** 원래 불일치이거나 AI가 결함 후보로 본 항목. `write_blocked`는 제외합니다.
- **방법:** 고정된 `plan.json`과 `policy.json`으로 해당 시나리오만 다시 실행해서 `repro/` 폴더를 만듭니다.
- **판단 불가로 두는 경우:** 실행 코드 해시가 다름, 로그인 여부가 다름, 재실행이 무효, 선행조건 실패, 초기화가 없거나 실패
- **비교:** 결과 서명(상태, 실제값, 요소 수, 오류 문구)이 같으면 `reproduced`, 재실행에서 통과하면 `flaky`입니다.
- **초기화:**
  - 쓰기 차단 실행은 초기화하지 않습니다.
  - 쓰기 허용 실행은 등록된 초기화 뒤에 재실행합니다. 초기화가 없으면 같은 시나리오 안에서 앞뒤를 비교하는 검사만 재현합니다.

#### 5-5. 최종 등급 (`systemVerdict`)

| 등급 | 대표 조건 |
|---|---|
| `bug_high` | 요구사항 위반 재현, 또는 결정적 관계 규칙 위반 재현 |
| `bug_medium` | 화면 안내 위반 재현, 일반 규칙 위반 재현, 초기화 없이 재현 |
| `ui_defect` / `improvement` | 시각 위반 재현(조작을 막으면 `ui_defect`), 철자 규칙 위반 |
| `hold` | 재현 안 됨, 행동 실패만 재현, 복제 페이지에서 대상 없음 |
| `incomplete` | 분류·재현 미완료, 값 못 읽음, 증거 수집 실패, 차단 |
| `not_bug` | 통과, 자동화 실패 |

**출력:** `run/verdicts.json`, `run/triage/`(AI 대화 기록), `repro/`
- 다시 판정하면 `verdicts-2.json`, `repro-2`로 새로 만들고 이전 판정은 덮어쓰지 않습니다.
- 단계마다 바로 저장해서, 중간에 멈춰도 거기까지의 결과가 남습니다.

### 6. 발견 제목 (`headline.ts`)

- **입력:** 판정이 끝난 발견
- **세부 로직:**
  - AI가 발견마다 "무엇이 잘못됐나" 한 줄을 씁니다.
  - 제목 안의 숫자와 인용이 검사 기록에 그대로 있는지 코드가 대조하고, 통과한 제목만 씁니다.
  - 판정과 등급은 바꾸지 않습니다.
- **출력:** `headlines.json`. 실패하면 보고서가 "기대 동작 + 실제 한 줄"로 대신합니다.

### 7. 보고서 (`report.ts`)

- **입력:** 결과 폴더의 저장된 파일들. 새 검사는 하지 않으므로 몇 번이든 다시 만들 수 있습니다(`node src/report.ts <폴더>`).
- **출력:** `report.json`(형식 `report/2`), `report.html`, `report.pdf`

`report.json`의 주요 묶음:

| 묶음 | 내용 |
|---|---|
| `bugs` | 버그(`bug_high`, `bug_medium`) |
| `visual` | 시각 위반 |
| `improvements` | 개선 제안 |
| `hold` | 판단 보류 |
| `incomplete` | 판단 불가와 사유별 건수 |
| `questions` | 업무 규칙 질문 |
| `observations` | 관찰 |
| `coverage` | 검사 범위 |
| `actions` | 계획·시도·완료된 행동 수 |
| `passed` | 통과한 검사 수 |

## 3. 결과 폴더 구조

```
qa/runs/<이름>-<시각>/
├─ explore.json      탐색 기록 (사이트 지도, 대화별 상태, 막힌 요청)
├─ plan.json         계획 (탐색 결과)
├─ run/              ── 실행 폴더 (고정)
│  ├─ plan.json · policy.json · manifest.json · src/ · specs/
│  ├─ ledger.jsonl   실행 기록
│  ├─ evidence/      접근성 텍스트·스크린샷
│  ├─ results.json   기록 대조 결과
│  ├─ verdicts.json  판정
│  └─ triage/        AI 분류 대화 기록
├─ repro/            재현 실행 폴더 (run/과 같은 구조)
├─ headlines.json    발견 제목
├─ summary.json      요약 (시간, 비용, 로그인·초기화 결과)
├─ calls.json        AI 호출 기록
└─ report.json · report.html · report.pdf
```

## 4. 헷갈리기 쉬운 용어

| 용어 | 뜻 |
|---|---|
| 고정된 계획 | 실행 직전에 `run/`에 복사한 `plan.json`. 실행, 대조, 재현이 모두 이 사본만 씀 |
| 페이지 종류(템플릿) | URL 모양으로 묶은 같은 종류의 페이지. AI 탐색 대화의 단위 |
| 복제 시나리오(`variantOf`) | 같은 종류의 다른 페이지에 코드가 복사한 시나리오 |
| `ref` / `Target` | `ref`는 탐색 중 그 순간의 요소 번호. `Target`은 재실행에서도 찾을 수 있는 구조화된 설명 |
| 선행조건 | 시작 상태 확인 검사. 실패하면 결함이 아니라 준비 실패 |
| `expected_from` | 기대값을 고정하지 않고 같은 시나리오에서 앞서 읽은 값으로 씀 |
| 쓰기 차단 | 기본 정책. 앱의 POST 같은 요청을 막아 서버 상태를 바꾸지 않음 |
| 결과 서명 | 재현 비교에 쓰는 값(상태, 실제값, 요소 수, 오류 문구에서 숫자를 지운 것) |
| `ledger.jsonl` | 실행 헬퍼가 남긴 원본 기록. 대조 단계가 그대로 믿지 않고 다시 계산함 |
