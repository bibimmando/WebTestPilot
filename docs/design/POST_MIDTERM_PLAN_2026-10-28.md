- 심어 둔 입력 검증 버그 5개는 모두 G 또는 H다. 입력 검증 "판정"이 약한 게 아니라 거기까지 가지 못했다.
- 놓친 버그의 가장 큰 덩어리는 **쓰기(7)**와 **본 것을 검사로 잇지 못함(10)**이다.

### 2.2 오탐 (우리 6건, 모두 Adminator)

- 6건 중 4건은 같은 앱 스크립트 오류(`crypto.randomUUID is not a function`) 뒤에 나왔다. 이 기능은 브라우저가 보안 연결(HTTPS·localhost)에서만 준다. `http://IP` 배포에서 생긴 실제 오류로 보인다(확인 안 함).
  - **일반 원인:** 같은 원인에서 나온 증상이 시나리오마다 따로 후보가 된다(S5·S107은 주소만 다른 중복).
  - Maison 오탐 0과 Adminator 6의 차이는 과적합 징후로 받아들인다. 미사용 앱 평가 전까지 일반화를 주장하지 않는다.

### 2.3 비용과 시간

- 비용의 89~94%, 시간의 대부분이 탐색·계획 단계다(Maison 13.6분·175턴, Adminator 20.2분·260턴).
- 원인: 계획 초안에 오류가 하나라도 있으면 `submit_plan`이 **전체를 거부**하고 모델이 전체를 다시 쓴다.

### 2.4 질문에서 나온 숙제

- 과적합 대응 → 평가 분리(3장 W10)와 "사이트 이름 없는 공통 원인 수정" 원칙 유지.
- 버그 순서가 영향도가 아니라 확신 등급순이다 → W8.
- 사용자 의도(업무 규칙)를 받는 기능이 없다 → W7.
- 화면 판정이 AI 스크린샷에 기댄다 → 잴 수 있는 것은 DOM 측정으로 옮기고, 시각 판정은 재현으로 확정(유지).

## 3. 작업 목록

각 작업은 AGENTS.md "수정안을 선택하는 기준" 네 가지(일반 원인·수정 책임·일반화 근거·검증)를 짧게 적었다. **모든 작업은 fixture 무료 검증 → 필요할 때만 승인받고 유료 실측** 순서다.

### 1순위 — 비용과 정확도의 공통 원인 (~11/7)

**W1. 계획을 시나리오 단위로 받기 (비용)**
- 원인: 계획 검사가 초안 전체를 거부해 모델이 통째로 다시 쓴다.
- 수정: `plan.ts` 검사 결과를 시나리오별로 나눠, 통과한 시나리오는 확정하고 실패한 것만 돌려보낸다. 기존 계약(검사 규칙)은 그대로 둔다.
- 검증: 가짜 모델 테스트(일부 시나리오만 틀린 초안 → 틀린 것만 다시 요청). 유료로는 같은 앱·같은 한도로 턴 수·비용 전후 비교 1회.
- 완료: 오류 1건당 다시 쓰는 양이 시나리오 하나로 줄고, 거부 규칙은 하나도 느슨해지지 않음.

**W2. 같은 원인 묶기 (오탐·중복)**
- 원인: 같은 콘솔 오류·같은 앱 오류 문구 뒤에 실패한 검사들이 각각 후보가 된다.
- 수정: 판정 뒤 보고서 단계에서, 같은 오류 신호(콘솔 오류 문구·화면 오류 문구)를 공유하는 후보를 한 묶음으로 보이고 "공통 원인 의심"을 적는다. 등급은 바꾸지 않는다.
- 검증: fixture에 같은 스크립트 오류를 내는 버튼 두 개 + 서로 다른 결함 하나 → 앞의 둘만 묶임.

**W2-b. 작은 정리**
- 발표 문서(`docs/presentation/`) 커밋, HANDOFF (40) 항목.
- 외부 정적 자원 허용 목록(assetOrigins) 재검토(10/25 결정: 발표 뒤 다시 본다).

### 2순위 — 놓친 버그를 줄이는 탐색·계획 (~11/14)

**W3. 탐색 범위 넓히기 (G)**
- 원인: 로그인 뒤 영역과 폼으로 이어지는 흐름이 사이트 지도·계획에 들어오지 않는다. 계획 못 한 기능(unplanned)을 다시 시도하지 않는다.
- 수정: 로그인 상태 크롤링 결과를 지도에 합치고, 남은 예산으로 unplanned 기능을 한 번 더 큐에 넣는다.
- 검증: 로그인 뒤에만 보이는 폼이 있는 fixture.

**W4. 관찰을 검사 후보로 (B·C)**
- 원인: 탐색 중 `observations`에 적은 이상이 검사로 바뀌는 단계가 없다.
- 수정: 계획 마감 전에 관찰 목록을 다시 보여 주고, 검사로 만들거나 "검사 못 하는 이유"를 남기게 한다(관찰값을 그대로 기대값으로 쓰는 것은 계속 금지).
- 검증: 관찰만 남던 fixture 결함이 검사로 계획되고, 정상 버전에서는 오탐 0.

**W5. 이동 앞뒤 문맥·상태와 표시 일치 규칙 (E·F)**
- 원인: 이동 검사가 "도착했나"만 보고, 상태 검사가 값 변화만 본다.
- 수정: 일반 규칙 추가 후보 — 뒤로 가기 뒤 이전 상태 유지, 선택·체크·배지 표시와 실제 값 일치. 사이트 이름 없이 적용 조건을 적고, 결정적 관계로 볼 수 있는지 따로 판단한다.
- 검증: 구조가 다른 fixture 2종 이상의 정상·결함 쌍.

**W6. 쓰기 허용 실행 + 입력 검증 읽기 (H, M5)**
- 원인: 쓰기를 막아 제출·저장 결과를 볼 수 없다. 브라우저 검증 말풍선은 화면 글자가 아니라 읽지 못한다.
- 수정:
  - 등록된 초기화가 있는 앱에서만 `--allow-writes` 실행(이미 있는 정책 위에). 결제·외부 발송·삭제는 계속 금지 목록.
  - 입력칸 유효성 상태 읽기(`validity`·`validationMessage`)를 새 읽기 종류로.
- 검증: 쓰기·초기화 fixture, 입력 검증 정상·결함 쌍. **공유 서버 쓰기는 사용자 승인과 초기화가 있을 때만**.
- 결정 필요: 쓰기 실행을 돌릴 서버(우리가 초기화할 수 있는 사본).
