# 4. ATUSA: URL 안의 UI 상태를 탐색하고 규칙으로 검사하기

[전체 가이드](../PAPERS_GUIDE_KO.md) · [논문 공개 PDF](https://people.ece.ubc.ca/amesbah/resources/papers/tse11.pdf)

## 원문에서 확인한 방법

AJAX 페이지는 URL을 바꾸지 않고 DOM을 갱신한다. 이 연구는 **URL 기반 수집만으로 놓치는 UI 상태를 탐색하고 불변식으로 검사하는 방법**을 제시한다. Crawljax의 탐색을 기반으로 한 ATUSA다.

```text
상태 관찰 → 폼·클릭 후보 수집 → 입력·행동 실행
          → DOM 비교 → 새 상태·전이 기록
          → 상태의 불변식 검사 → 다음 상태 탐색
          → 수집한 경로에서 테스트 생성·재실행
```

상태 비교에는 중요하지 않은 동적 차이를 다루는 비교기를 적용한다. 검사 규칙은 공통 DOM 규칙, 앱별 상태 규칙, 공통 상태 전이 규칙, 앱별 전이 규칙으로 나뉜다. 요청 실패가 있는 클릭이나 뒤로가기 일관성도 다룬다. 앱별 불변식과 일부 입력 설정에는 사람의 작업이 필요하다. [§4–6](https://people.ece.ubc.ca/amesbah/resources/papers/tse11.pdf)

이 논문의 불변식은 정해진 적용 범위의 조건이다. 모든 화면에 동일한 규칙을 무조건 적용하는 방식으로 이해하면 안 된다.

## 프로젝트를 위한 해설: URL 하나에 네 화면이 있다면

아래는 직접 구성한 로컬 회원 정보 페이지다. URL은 계속 `/profile`이지만 다음 네 상태가 있다.

| 상태 | 화면에서 관찰하는 내용 |
|---|---|
| A: 기본 조회 | 현재 표시 이름과 수정 버튼 |
| B: 편집 모달 | 이름 입력과 저장·취소 버튼 |
| C: 입력 오류 | 편집 모달과 필수 입력 안내 |
| D: 저장 완료 | 모달 닫힘과 갱신된 표시 이름 |

URL 방문만 집계하면 한 페이지다. 사용자 동작 관점에서는 최소 네 가지 상태이며, 각 상태에서 수행할 수 있는 행동도 달라진다.

상태 간 연결은 다음처럼 기록할 수 있다.

```text
A --수정 클릭--> B --빈 값 제출--> C
B --정상 테스트 값 저장--> D
B --취소 클릭--> A
```

이 그림은 같은 URL의 각 관찰을 이해하기 위한 예시다. 현재 프로젝트가 이 상태 그래프를 자동 생성한다는 뜻은 아니다.

이 페이지의 공개 요구사항이 ‘취소하면 변경이 저장되지 않는다’라면 B에서 값을 입력하고 취소한 뒤 A의 표시 이름이 그대로인지 확인할 수 있다. 요구사항이 ‘빈 이름은 거부한다’라면 C에서는 해당 안내와 저장 결과를 확인한다. 기본 조회 상태 A에 오류 안내가 없다는 이유로 입력 검증 기능이 없다고 판단하면 C를 놓친다.

## 중요하게 이해할 지점

### URL, 논리적 화면, 실제 관찰 상태를 나눈다

우리 설계에서 다음처럼 구분할 수 있다.

| 구분 | 예시 | 역할 |
|---|---|---|
| URL | `/profile` | 방문 범위와 URL 큐 관리 |
| 논리적 화면 | 회원 정보 조회·편집 | 비슷한 기능 문맥 연결 |
| 개별 관찰 상태 | 모달 열림·오류 표시·이름 변경 | 실제 검사와 증거 저장 |

현재 `snapshot_id`는 개별 수집 자료를 식별한다. 같은 URL이라는 이유로 모든 snapshot이 같은 상태인 것은 아니다. 반대로 snapshot ID가 새로 생겼다고 새로운 기능 화면을 발견한 것도 아니다.

### 중복 화면을 줄이면서 중요한 증거는 유지한다

시계가 1초 바뀌었다고 매번 새 탐색 화면으로 잡으면 예산을 소모한다. 하지만 저장한 이름이 달라진 것은 중요한 판정 자료일 수 있다.

따라서 탐색용으로 ‘같은 편집 화면’이라고 묶는 기준과, 결과 비교에 필요한 이름·선택·오류 자료를 보존하는 기준을 나누는 것이 좋다. 탐색에서 묶은 두 snapshot도 증거 자료로는 각각 유지한다.

화면 골격이 같다는 이유로 정상 상태와 오류 상태를 동일 취급하면 검증 경로를 놓칠 수 있다. 초기에 ‘모달 열림’, ‘오류 안내 있음’, ‘주요 컨트롤 enabled 여부’처럼 실제 테스트를 달라지게 하는 관찰부터 비교하는 방식이 적합하다.

### 불변식은 적용 조건까지 적어야 한다

‘저장 버튼이 항상 보여야 한다’는 규칙은 기본 조회 상태에서는 틀릴 수 있다. ‘편집 모달이 열린 상태에서는 저장과 취소를 조작할 수 있어야 한다’라면 적용 범위가 분명하다.

불변식을 만들 때는 검사 대상, 적용 상태, 기대 성질, 관찰 방법을 함께 정한다. 실제 버튼이 disabled인 것이 오류인지 여부도 입력 조건과 요구사항을 확인해야 한다.

### 되돌아가는 방법도 탐색의 일부다

모달을 닫거나 저장을 취소하면 앞선 상태로 돌아갈 수 있다. 그러나 브라우저 뒤로가기, 페이지 새로고침, 새 세션 생성은 서로 다른 효과를 낸다. 재현에는 어떤 초기화가 필요한지 명시해야 한다. URL에 다시 방문하는 것만으로 서버 데이터가 초기화된다고 가정하지 않는다.

## 현재 프로젝트에 연결하는 위치

| 현재 기반 | 활용 방향 |
|---|---|
| URL 큐·그래프 | 전체 방문 범위를 관리 |
| `evidence.action()` | 같은 URL 안의 행동·전후 snapshot 연결 |
| snapshot의 요소·폼·오류·표시 상태 | 의미 있는 UI 상태 차이 관찰 |
| `diff`, `quality`, `omitted` | 차이와 수집 한계를 함께 해석 |
| 최신 요소 상세·검증 locator | 새 상태의 실제 조작 대상 확인 |

현재 URL 방문 순서는 FIFO다. 상태 탐색 아이디어를 적용하려고 이 큐를 곧바로 바꿀 필요는 없다. AI 콜백이 한 페이지에서 제한된 행동을 수행하고 각 전후 상태를 기록하는 방식부터 시작할 수 있다. 공통 상태 탐색 저장 구조를 추가할 때는 전처리·AI 팀이 함께 계약을 정한다. [프로젝트 통합 가이드](../../INTEGRATION_GUIDE.md)

상태별 검사 규칙은 AI 팀의 판정 기능으로 연결할 수 있다. 전처리가 diff를 만들었다는 이유로 그 단계에서 자동으로 결함을 확정하지 않는다. 요소가 요약에서 빠진 경우와 실제 화면에서 사라진 경우도 구분한다.

## 작은 적용 순서

1. 모달 하나가 있는 로컬 페이지로 상태 A·B·C·D를 준비한다.
2. 기존 행동 증거에 전후 상태를 연결하고 상태 특징을 수작업으로 확인한다.
3. 시계 변화와 오류·모달 변화가 구분되는 간단한 탐색 기준을 만든다.
4. 조건이 명확한 규칙 2개를 판정 기능에 연결한다.
5. 실제 행동 경로로 상태를 다시 만들 수 있는지 확인한다.

뒤로가기 등 현재 계획 초안에 없는 행동은 실행기 지원과 증거 기록 범위를 합의한 뒤 추가한다. 초기 `fill`, `click`, `press`만으로도 상당수 모달·폼 상태를 실험할 수 있다.

## 검증할 사례

| 로컬 조건 | 확인할 성질 |
|---|---|
| URL 변화 없이 모달 표시 | 새로운 검사 가능 상태를 관찰하는가? |
| 시계만 계속 갱신 | 새로운 기능 상태가 무한히 늘지 않는가? |
| 입력 오류만 추가됨 | 같은 화면 골격이어도 오류 상태를 보존하는가? |
| 취소 후 이름이 잘못 저장됨 | 전후 값 관계 검사에서 실패하는가? |
| 요약에서 요소가 생략됨 | 실제 삭제로 단정하지 않는가? |

이 논문에서 우리 프로젝트가 먼저 가져올 기능은 **URL 내부의 상태 변화를 행동 경로와 연결하고, 적용 조건이 명확한 규칙으로 검사하는 것**이다.
