# 5. WebExplor: 반복 행동을 줄이고 깊은 기능에 도달하기

[전체 가이드](../PAPERS_GUIDE_KO.md) · [논문 원문](https://arxiv.org/html/2103.06018v1)

## 원문에서 확인한 방법

이 연구는 **긴 행동 순서를 거쳐야 나오는 기능과 반복 탐색 문제**를 다룬다. 실행 중 학습하는 Q-learning과, 방문 상태·전이를 저장하는 모델을 결합한다.

```text
현재 상태·가능 행동 확인 → 행동 선택·실행
                        → 전이 방문 횟수에 따라 보상 계산
                        → 다음 행동 선택값 갱신
                        → 상태 전이 모델 갱신
                        → 탐색 정체 시 드물게 방문한 경로로 이동
```

보상은 전이 방문 횟수의 제곱근 역수로 감소한다. 새로운 경로를 찾는 데 도움이 되는 앞선 행동에도 선택값이 전달된다. 탐색 정체 시 모델에서 목표 전이를 선택하고 짧은 경로를 따라 재도달한다. 같은 URL의 비슷한 HTML 구조는 탐색 상태로 묶는다. [§III](https://arxiv.org/html/2103.06018v1)

기본 입력값은 표준에 따른 무작위 값이다. 실패 탐지는 JS 예외·클라이언트·서버 오류 등을 사용하므로 업무 규칙 판정과는 구분해야 한다. 홈페이지로 이동하는 초기화도 서버 데이터 전체 복원을 뜻하지 않는다. [§II-B, §III](https://arxiv.org/html/2103.06018v1)

## 프로젝트를 위한 해설: 일정 등록 기능에 도달하기

아래는 직접 구성한 로컬 일정 페이지다. 초기 화면에는 메뉴 버튼 10개가 있다. 일정 수정 기능은 다음 흐름을 거쳐야 나타난다.

```text
일정 메뉴 → 목록 → 새 일정 → 필수 입력 → 저장
→ 새 일정 상세 → 수정 버튼
```

초기 화면의 메뉴만 계속 클릭하면 목록까지는 잘 도달하지만, 새 일정을 만들어야 생기는 수정 버튼을 보지 못할 수 있다. 입력 없이 저장을 누르면 오류 상태에 머무를 수도 있다.

이때 우리 탐색기가 해야 할 일은 무작정 메뉴 선택을 반복하는 것이 아니라, 어떤 경로를 이미 실행했는지와 어떤 단계가 새로운 행동을 열었는지를 기억하는 것이다. ‘새 일정 생성’이 다음 수정·조회 기능에 도달하는 준비 단계라는 사실을 기록하면 같은 긴 경로를 매번 다시 추측할 필요가 줄어든다.

다음 기록은 초기 구현에서 사용할 수 있는 예다.

| 기록할 내용 | 설명용 예 | 쓰는 이유 |
|---|---|---|
| 상태와 가능한 행동 | 일정 목록: 새 일정, 검색 | 아직 시도하지 않은 행동 확인 |
| 행동 시도 횟수 | 새 일정 클릭 1회 | 같은 행동 반복 파악 |
| 관찰된 전후 상태 | 목록 → 입력 폼 | 이미 알려진 경로 보관 |
| 새로 가능해진 행동 | 일정 생성 후 상세의 수정 버튼 | 준비 단계의 가치 파악 |
| 종료 원인 | 시간 상한, 도구 실패, 완료 | 도달 못 한 기능의 원인 구분 |

이 기록만으로도 ‘아직 안 해 본 행동을 먼저 선택한다’는 단순 전략을 만들 수 있다. 이 전략은 논문의 강화학습 구현과 동일하지 않으며, 우리 프로젝트가 먼저 비교할 수 있는 작은 기준 구현이다.

## 중요하게 이해할 지점

### 신규 상태 발견과 결함 발견은 다른 목적이다

새로운 폼을 열었다면 탐색 범위는 늘어난다. 그 폼에 결함이 있다는 뜻은 아니다. 반대로 이미 방문한 폼에서도 다른 입력 조건으로 결함이 드러날 수 있다.

따라서 ‘새 상태를 발견하지 못했으니 검사할 가치가 없다’고 단정하지 않는다. 탐색용 행동 선택과 검증용 입력·오라클 선택을 나눠 기록하면 목적을 혼동하지 않는다.

### 앞선 행동에 가치를 주는 이유

신규 데이터를 만드는 행동 자체는 정상적으로 끝날 수 있다. 그러나 그 행동이 수정·삭제·상세 조회 같은 다음 기능의 전제라면 탐색에 가치가 있다. 우리 초기 계획에는 ‘기능 목적’과 함께 ‘어떤 다음 상태를 열기 위한 준비인지’를 적을 수 있다.

이때 실제 데이터 변화가 다음 검사에 영향을 준다. 한 테스트가 일정을 생성한 후 다른 테스트가 이를 보게 되면 초기 상태가 달라진다. 재사용 가능한 경로를 저장하더라도 전제 상태와 데이터 초기화 정책을 같이 기록해야 한다.

### 행동 가능 여부는 상태마다 다시 확인한다

데이터가 없을 때는 수정 버튼이 없다가 생성 후 등장할 수 있다. 앞선 화면의 행동 목록을 고정해 두면 이런 기능을 놓친다. 조작 후 새 요약을 받고 최신 컨트롤·표시·disabled 상태를 확인한다.

이미 실행한 행동도 상태가 달라지면 다시 의미가 있을 수 있다. 따라서 ‘이 버튼은 한 번 눌렀으니 영구 제외’보다는 ‘이 상태에서 이 행동을 몇 번 했는가’를 기록하는 것이 적합하다.

### 경로 재사용은 복제한 상태가 아니라 다시 실행하는 절차다

도달한 상세 화면의 URL만 저장하면 앞선 데이터가 사라졌을 때 같은 화면을 만들 수 없다. 재도달에 필요한 단계, 공개 테스트 입력, 전제와 완료 조건을 보관한다. 로그인·데이터 준비에 필요한 민감값은 증거 문서에 넣지 않고 테스트 설정으로 관리한다.

저장한 경로를 실행하다가 예상한 화면이 나오지 않으면 성공으로 집계하지 않는다. 전제 변화·동적 UI·환경 실패를 확인하고 새 상태를 관찰한다.

## 현재 프로젝트에 연결하는 위치

| 현재 기반 | 추가할 수 있는 기능 |
|---|---|
| `controls[].key`, 상세 요소 | 상태별 가능한 행동 목록 |
| action의 전후 snapshot ID | 실행한 상태 전이 기록 |
| 조작 후 요약과 새 링크 | 다음 행동·경로 발견 |
| 현재 실행 시간·계획 한도 | 탐색 중단과 미실행 사유 기록 |
| 별도 상세 결과 저장 | 시도 횟수·도달 경로·새 기능 집계 |

현재 URL 큐는 FIFO다. 이 아이디어는 우선 콜백 안의 행동 선택에 적용할 수 있다. URL 순회 순서를 바꾸거나 중요도가 낮은 페이지를 생략하는 기능을 현재 구현으로 설명하면 안 된다. [프로젝트 통합 계약](../../INTEGRATION_GUIDE.md)

간단한 기준 전략은 ‘현재 상태의 미실행 행동 우선 → 진행 중 기능의 다음 단계 우선 → 반복만 지속되면 종료 사유 기록’이다. 초기 페이지당 검사·단계 한도 안에서 시도한다. 전체 강화학습을 도입할지는 이 기준 전략과 비교한 뒤 결정한다.

## 작은 적용 순서

1. 데이터 생성 후에만 수정 기능이 나타나는 로컬 페이지를 준비한다.
2. 상태별 행동·시도 횟수·도달 경로를 저장한다.
3. 미실행 행동을 우선하는 작은 전략을 연결한다.
4. 원래 고정 순서 전략과 같은 시간·행동 예산으로 비교한다.
5. 판정 기능은 별도로 연결하고 탐색 성과와 결함 성과를 나눠 집계한다.

## 검증할 사례

| 로컬 조건 | 확인할 성질 |
|---|---|
| 공통 메뉴가 계속 같은 화면으로 돌아감 | 반복 행동에 예산이 소모되는 정도 |
| 유효 입력 후에만 다음 단계 열림 | 다단계 준비 행동 수행 여부 |
| 데이터 생성 후 수정 버튼 등장 | 가능한 행동 목록 갱신 여부 |
| 초기 데이터가 리셋돼 경로가 달라짐 | 저장 경로를 무조건 성공 처리하지 않는지 |
| HTTP 오류는 없지만 저장 내용이 틀림 | 별도 업무 오라클로 실패를 잡는지 |

관찰한 상태 수뿐 아니라 고유 기능 도달 수, 새 기능을 찾는 데 걸린 행동 수, 반복 행동 비율, 미실행 사유를 함께 비교하면 좋다. 한 번의 실행 결과보다 동일 조건의 여러 실행을 비교해야 행동 선택의 변동도 드러난다.

이 논문에서 우리 프로젝트가 먼저 가져올 기능은 **상태별로 시도한 행동과 경로를 기록해 반복을 줄이고, 필요한 준비 단계를 거쳐 다음 기능으로 이어가는 것**이다.
