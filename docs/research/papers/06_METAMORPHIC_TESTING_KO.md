# 6. 메타모픽 테스팅: 정확한 정답 대신 실행 사이의 관계 검사하기

[전체 가이드](../PAPERS_GUIDE_KO.md) · [논문 저자 공개 PDF](https://hub.hku.hk/bitstream/10722/254895/1/content.pdf)

## 원문에서 확인한 주제와 흐름

이 서베이는 **단일 실행의 정확한 정답을 얻기 어려울 때, 여러 입력·출력의 관계를 이용하는 방법**을 정리한다. 한 실행에만 적용되는 범위 조건과 여러 실행을 연결하는 메타모픽 관계는 구분한다.

```text
대상 기능의 명세·성질 확인 → 타당한 입력·출력 관계 선택
                         → 원래 테스트 실행
                         → 관계에 따른 후속 테스트 생성·실행
                         → 두 실행의 입력·출력 관계 검사
```

관계 식별, 좋은 관계의 선택, 원래 테스트 입력의 선택, 다른 검증 기법과의 결합을 다룬다. 관계와 원래 테스트 입력이 모두 결함 발견에 영향을 준다. 관계는 정확성의 필요조건이므로 통과만으로 전체 정확성을 보장하지 않는다. 또한 관계를 어겨도 어느 실행의 결과가 틀렸는지 바로 특정하지 못할 수 있다. [§2–6](https://hub.hku.hk/bitstream/10722/254895/1/content.pdf)

2018년 논문이며 링크의 저자 공개본에는 출판 전 서지 자리표시자가 남아 있다. 확정 출판 정보는 [대학 서지 기록](https://acquire.cqu.edu.au/articles/journal_contribution/Metamorphic_testing_A_review_of_challenges_and_opportunities/13446482)을 기준으로 한다.

## 프로젝트를 위한 해설: 검색 결과를 전부 알지 못한다면

아래는 직접 구성한 로컬 도서 검색 페이지다. 제목이 검색어를 포함하는 자료를 반환하고, 필터는 같은 결과 집합에 조건을 추가한다는 요구사항을 제공했다고 가정한다.

AI가 ‘네트워크’를 검색했을 때 정답 도서 전체 목록을 모른다고 하자. 검색 결과의 정확한 정답을 직접 비교하기는 어렵지만, **같은 데이터에서 필터를 추가했을 때 기존 결과에 없던 자료가 나타나서는 안 된다**는 조건은 검사할 수 있다.

| 실행 | 입력·조건 | 관찰한 자료 ID |
|---|---|---|
| 첫 번째 | ‘네트워크’, 필터 없음 | A, B, C, D |
| 두 번째 | 같은 검색어, ‘2025년 이후’ 필터 | B, D |

두 번째 결과가 첫 번째 결과에 포함되므로 설정한 관계는 통과한다. 반면 B, D, X가 나타나면 X가 관계 위반의 증거다. 다만 서비스가 필터 적용 시 다른 검색 모드로 바뀌도록 명세돼 있다면 이 관계를 사용할 수 없다.

또한 결과가 100개인데 현재 첫 페이지의 10개만 관찰했다면 포함 관계를 제대로 확인하기 어렵다. 필터 후 첫 페이지로 올라온 X가 원래 결과의 두 번째 페이지에 있었을 수 있기 때문이다. 전체 비교 범위를 확보하거나, 그 범위가 작은 로컬 fixture로 먼저 실험한다.

이 사례에서 검사 근거는 ‘검색은 제목 포함 방식이며 필터는 같은 집합의 조건을 좁힌다’는 공개 요구사항이다. ‘필터는 보통 이럴 것’이라는 AI 추정만으로 확정하지 않는다.

## 중요하게 이해할 지점

### 정확한 목록을 몰라도 관계는 명확하게 정할 수 있다

첫 실행의 목록이 서비스 전체의 올바른 정답인지까지 알 필요는 없지만, 비교에 사용할 목록의 관찰이 완전한지는 확인해야 한다. ‘정답을 모름’과 ‘수집 자료가 불완전함’은 서로 다른 문제다.

두 실행은 같은 사용자 권한, 같은 고정 데이터, 같은 검색 규칙을 사용해야 한다. 실행 사이에 데이터가 바뀌면 관계가 깨진 이유가 결함인지 데이터 변화인지 구분하기 어렵다. 초기에는 고정된 로컬 데이터를 권장한다.

### 정렬 검사는 두 조건으로 나눌 수 있다

정렬이 순서만 바꾸는 기능이라고 명세돼 있다면 아래 두 검사를 구분한다.

| 검사 | 무엇을 비교하는가? |
|---|---|
| 정렬 전후 자료 보존 | 자료 ID와 각 ID의 등장 횟수가 유지되는가? |
| 정렬 방향의 정확성 | 정렬 키가 요구한 방향으로 배열됐는가? |

예를 들어 정렬 전 A, B, C이고 정렬 후도 A, B, C인데 가격 순서가 뒤섞여 있다면 자료 보존 관계만 통과하고 방향 검사는 실패한다. 정렬 전후가 같다는 이유로 정렬 전체를 통과 처리하지 않는다.

자료 ID를 단순한 집합으로만 바꾸면 중복 개수를 잃을 수 있다. A, A, B가 A, B로 줄어도 집합은 같다. 개수 보존이 필요한 기능에서는 각 항목의 등장 횟수도 비교한다.

### 입력 변환은 서비스 규칙에 맞아야 한다

다음은 우리 프로젝트용 검사 후보다. 자동 적용 규칙이 아니다.

| 후보 관계 | 필요한 명시적 전제 |
|---|---|
| 검색어 앞뒤 공백을 추가해도 결과 동일 | 검색어를 trim한다고 명세돼 있음 |
| 대소문자를 바꿔도 결과 동일 | 검색이 대소문자를 구분하지 않음 |
| 정렬 방향만 바꿔도 자료 구성 동일 | 정렬이 항목 선택을 바꾸지 않음 |
| 동일 데이터에 필터를 추가하면 결과가 부분집합 | 필터가 같은 검색 결과의 조건을 좁힘 |

유사도 검색, 추천, 실시간 인기순 결과에는 위 전제가 성립하지 않을 수 있다. 후보 관계를 자동으로 생성하는 AI와, 관계를 실제 적용할지 결정하는 검증 단계를 나눠야 한다.

### 관계 위반은 비교 쌍 전체의 문제다

첫 검색에서 C가 누락돼 있고 두 번째 검색에서는 C가 제대로 나타날 수도 있다. 관계가 깨졌다고 두 번째 실행만 결함이라고 보고하면 원인을 잘못 짚을 수 있다.

보고서에는 두 실행의 입력·전제·관찰·비교 규칙을 모두 남긴다. 어느 단계가 원인인지 더 확인할 필요가 있으면 이를 명시한다. 관계 위반 관찰과 원인 확정은 다른 결과다.

## 현재 프로젝트에 연결하는 위치

메타모픽 검사는 콜백에서 두 개 이상의 실행과 증거를 연결해야 한다. 현재 `evidence.action()`은 한 조작의 전후 상태를 제공하므로, 검사 팀이 여러 action/snapshot ID를 하나의 비교 결과에 묶는 로직을 추가할 수 있다.

| 필요한 내용 | 현재 활용할 기반 | 추가 확인 |
|---|---|---|
| 두 실행의 목적·입력 변환 | 계획 초안의 목적·단계 | 허용된 테스트 값과 공개 전제 기록 |
| 조작과 결과 | action/snapshot ID | 각 실행 완료 조건·비교 데이터 확보 |
| 자료 ID·정렬 값 등 | 상세 snapshot·요소·본문 관찰 | 현재 수집 범위로 값 추출이 가능한지 |
| 부분 수집 여부 | `quality`, `omitted`, `source_truncated` | 업무 목록 전체를 수집했는지 별도 확인 |
| 관계 판정·보고서 | AI 팀 상세 결과 | 비교 쌍의 근거·판정 보류 사유 저장 |

현재 API가 일반 목록 추출과 관계 판정을 자동 제공하는 것은 아니다. 특히 수집 상태가 `complete`여도 무한 스크롤·페이지 분할의 전체 업무 데이터까지 완전하다는 뜻은 아니다. 검사에 필요한 범위의 완전성을 따로 확인한다. [프로젝트 입력 계약](../../../integration/docs/AI_INPUT_CONTRACT.md)

## 작은 적용 순서

1. 한 화면에 전체 자료가 보이는 고정된 로컬 목록을 준비한다.
2. ‘정렬은 순서만 변경’이라는 공개 요구사항을 제공한다.
3. 정렬 전후 ID·중복 개수·정렬 키를 관찰한다.
4. 자료 보존과 정렬 방향을 각각 검사한다.
5. 정상·자료 누락·중복·역방향·부분 수집 모드로 결과를 확인한다.

## 검증할 사례

| 로컬 조건 | 기대되는 검사 결과 |
|---|---|
| 정상: 자료 보존, 올바른 방향 | 두 검사 통과 |
| 자료 한 개 누락 | 자료 보존 실패 |
| 자료 중복이 줄거나 늘어남 | 중복 개수 보존 실패 |
| 자료는 그대로지만 정렬 방향 틀림 | 보존 통과, 방향 실패 |
| 목록 일부만 수집 | 전체 목록 관계 판정 보류 |
| 두 실행 사이에 데이터 변경 | 비교 전제 불충족으로 판정 보류 |

이 논문에서 우리 프로젝트가 먼저 가져올 기능은 **명세와 비교 전제를 확인한 뒤, 두 실행의 결과 관계를 검사하는 것**이다. 정답을 모른다는 이유로 임의 관계를 만들기보다 조건이 명확한 작은 기능부터 적용하면 된다.
