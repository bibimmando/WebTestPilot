# 3. AutoE2E: 화면에서 기능을 발견하고 테스트 흐름으로 묶기

[전체 가이드](../PAPERS_GUIDE_KO.md) · [논문 원문](https://arxiv.org/html/2408.01894v2)

## 원문에서 확인한 방법

이 연구는 **화면을 많이 방문하는 것과 사용자 기능을 수행하는 것은 다르다**는 문제를 다룬다. 기능을 실현하는 관련 행동의 순서를 찾아 테스트로 만든다.

```text
상태 탐색·행동 수집 → 페이지 문맥 추출
                    → 현재 행동만으로 기능 후보 추론
                    → 직전 행동까지 포함해 기능 후보 다시 추론
                    → 두 추론의 순위를 이용해 기능 점수 갱신
                    → 중복 기능 통합·행동 연결 → 테스트 생성
```

탐색에는 BFS를 사용한다. 문맥은 화면 이미지·앱 설명·직전 행동에서 얻는다. 기능 설명과 행동 연결을 별도 저장하며, 임베딩 유사도와 LLM 확인으로 기능을 묶는다. 출력 순위를 확률 추정에 활용하는 계산은 모델의 실제 확률을 직접 얻는 방식과 다르다. [§II–III](https://arxiv.org/html/2408.01894v2)

E2EBench는 8개 앱의 기능 커버리지를 평가한다. 보고된 79%는 기능 수행 범위이며 결함 탐지 정확도가 아니다. 결론에서는 assertion generation을 후속 과제로 둔다. [§IV–VIII](https://arxiv.org/html/2408.01894v2)

## 프로젝트를 위한 해설: ‘저장’ 버튼의 기능을 알아내기

아래는 직접 구성한 게시글 관리 페이지다. 현재 화면에 ‘제목’, ‘본문’ 입력과 ‘저장’ 버튼이 있다. 버튼 이름만 보면 새 게시글을 만드는 것인지, 기존 게시글을 수정하는 것인지 알 수 없다.

두 진입 흐름을 비교해 보자.

| 앞선 행동 | 현재 화면 단서 | 추정할 기능 |
|---|---|---|
| 목록에서 ‘새 글’ 클릭 | 비어 있는 제목·본문 | 게시글 생성 |
| 상세에서 ‘수정’ 클릭 | 기존 제목·본문 | 게시글 수정 |

우리 AI 입력에 현재 컨트롤만 전달하면 같은 ‘저장’ 버튼을 같은 기능으로 해석할 수 있다. 직전 행동과 해당 상태에 도달한 목적을 같이 전달하면 구분할 근거가 늘어난다.

기능 후보를 발견한 다음에도 실제 기대 결과는 별도로 정해야 한다. ‘수정 기능이 있는 것 같다’는 추정은 ‘저장 후 바뀐 제목이 유지돼야 한다’는 요구사항의 근거를 대신하지 않는다. 공개 요구사항이나 테스트 목적을 연결하고, 그에 맞는 관찰을 계획한다.

게시글 수정이라는 기능을 확인하려는 흐름은 다음처럼 구성할 수 있다.

```text
목록에서 테스트 자료 선택
→ 상세 확인 → 수정 화면 열기 → 테스트 제목 입력
→ 저장 → 저장 완료 조건 확인 → 결과 화면에서 제목 확인
```

중간에 공통 메뉴를 열었다 닫는 행동이 있었다고 해서 그것까지 수정 기능의 필수 단계로 묶지는 않는다. 실제 실행 기록은 그대로 남기고, 재현에 필요한 단계와 우연히 수행한 단계를 구분하면 된다.

## 중요하게 이해할 지점

### 기능은 컨트롤 하나와 같지 않다

검색은 검색칸 입력과 제출로 끝날 수 있지만, 수정은 대상 선택부터 저장 결과 확인까지 여러 화면을 연결할 수 있다. 따라서 한 페이지에서 버튼이 몇 개 있는지와 사이트의 기능을 몇 개 검사했는지를 별도로 센다.

동일 기능에도 여러 진입 경로가 있을 수 있다. 예를 들어 목록의 수정 버튼과 상세 화면의 수정 버튼이 같은 편집 폼으로 이어진다면, 두 경로를 관찰했다고 수정 기능 두 개를 발견한 것은 아니다. 기능 수 집계와 경로 수 집계를 나눈다.

### 기능 이름만으로 중복을 묶으면 실수가 생긴다

‘저장’이라는 이름은 여러 기능에서 사용한다. 우리 초기 구현은 대상 엔터티, 동작 목적, 관련 폼·상태, 진입 행동을 함께 보고 후보를 비교할 수 있다. 대규모 벡터 DB를 먼저 구축하기보다 작은 벤치마크에서 단순한 후보 목록과 대응 관계로 시작하는 것이 적합하다.

또 공통 메뉴가 모든 페이지에서 반복된다는 이유만으로 그 기능이 수십 개라고 세면 안 된다. 반복 관찰 건수는 근거 추적용으로 남기고, 고유 기능 수는 별도 기준으로 정한다. 동일한 화면을 반복 관찰한 것과 새 단계에서 추가 증거를 얻은 것은 다르다.

### 계획을 실행하며 다시 관찰해야 한다

저장 뒤에 확인 모달이 나올 수 있다. 처음 세운 계획에 모달이 없으면 다음 행동을 무리하게 실행하지 않고 최신 상태에서 필요한 다음 단계를 정한다. 처음의 selector·key가 새 화면에서 같은 의미로 유지되는지도 확인한다.

‘기능 추정 점수’는 기능의 존재를 판단하는 보조 정보다. 그것을 ‘실제 버그일 확률’로 사용하지 않는다. 기능 발견의 불확실성과 결함 판정의 불확실성은 서로 다른 항목이다.

## 현재 프로젝트에 연결하는 위치

| 현재 기반 | 추가할 수 있는 기능 |
|---|---|
| `page`, `feature_candidates`, `controls`, `forms` | 현재 화면의 기능 후보와 관련 요소 연결 |
| `parent_snapshot_id`, `action_id` | 직전 행동·도달 경로 문맥 구성 |
| `proposed_checks` 초안 | 발견한 기능을 검사 목적·단계로 변환 |
| 조작 후 최신 `ai_input` | 새 상태에 맞춰 다음 행동 계획 갱신 |
| 별도 상세 결과 저장 | 고유 기능·관련 행동·검사 판정 집계 |

현재 전처리기의 기능 후보는 관찰 단서다. 논문의 기능 집계·점수·테스트 생성 과정은 아직 연결돼 있지 않다. 구현한다면 AI 검사 콜백에서 기존 Page와 증거 API를 사용한다. 통합용 별도 크롤러나 브라우저를 만들면 상태·증거 연결이 갈라진다. [프로젝트 통합 계약](../../INTEGRATION_GUIDE.md)

기능의 존재를 발견한 뒤 판정까지 하려면 Oracle Survey의 근거 기록과 WebTestPilot에서 착안한 전후 비교를 추가로 연결한다.

## 작은 적용 순서

1. 로컬 페이지의 기능 3개를 사람이 먼저 목록으로 정한다. 예: 생성, 조회, 수정.
2. AI에 현재 요약과 필요한 직전 행동 문맥을 주고 기능 후보를 받는다.
3. 후보에 실제 관찰 요소 key와 관련 snapshot ID를 연결한다.
4. 단순 기준으로 중복 후보를 통합하고 실행 가능한 단계로 바꾼다.
5. 실행 후 기능 수행 여부와 기대 결과 검사 여부를 따로 평가한다.

## 검증할 사례

| 로컬 조건 | 확인할 성질 |
|---|---|
| 생성과 수정에 모두 ‘저장’ 버튼 사용 | 진입 문맥으로 기능을 구분하는가? |
| 모든 페이지에 같은 메뉴 표시 | 반복 기능을 고유 기능 여러 개로 세지 않는가? |
| 특정 버튼은 숨겨진 다음 화면에서 등장 | 조작 후 새 상태를 관찰하는가? |
| 기능은 실행했지만 저장 값이 틀림 | 수행 성공과 판정 실패를 구분하는가? |
| 처음 보는 기능의 기대 결과가 없음 | 기능 후보로 남기고 결함을 단정하지 않는가? |

평가용 기능 목록을 검사 AI에게 그대로 주면 자율 기능 발견 성능을 측정하기 어렵다. 공개 요구사항을 사용하는 실험과 UI에서 자율 발견하는 실험을 나누고, 각 실험에 무엇을 입력했는지 기록한다.

이 논문에서 우리 프로젝트가 먼저 가져올 기능은 **현재 화면과 직전 행동을 함께 보고 기능을 발견한 뒤, 해당 기능에 필요한 행동만 하나의 검사 흐름으로 묶는 것**이다.
