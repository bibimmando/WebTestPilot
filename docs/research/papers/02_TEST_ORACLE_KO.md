# 2. 테스트 오라클 서베이: 기대 결과를 무엇으로 정할 것인가

[전체 가이드](../PAPERS_GUIDE_KO.md) · [논문 공개 PDF](https://discovery.ucl.ac.uk/id/eprint/1471263/1/06963470.pdf)

## 원문에서 확인한 주제

이 논문은 특정 실행 도구를 제안하는 연구가 아니라, **올바른 결과를 판단하는 방법과 그 한계를 정리한 서베이**다. 입력 자동 생성과 결과 판정은 별개이며, 전체 명세가 없으면 일부 경우만 판단하는 부분 오라클을 사용할 수 있다.

| 원문의 큰 분류 | 판정 근거 |
|---|---|
| 명세 기반 | 형식 명세, 모델, 조건·계약 |
| 유도한 오라클 | 다른 구현·버전, 실행 기록, 문서, 여러 실행의 관계 |
| 암묵적 오라클 | 비정상 종료 등 일반적으로 오류로 여기는 현상 |
| 자동 오라클이 없는 경우 | 사람의 확인과 그 비용을 줄이는 방법 |

문서·관찰에서 추론한 규칙과 실제 의도는 다를 수 있고, 정상처럼 반복되는 결함도 있을 수 있다. 이전 버전 역시 항상 정답은 아니다. 암묵적 오라클에도 적용 문맥이 있다. [§4–7](https://discovery.ucl.ac.uk/id/eprint/1471263/1/06963470.pdf)

이 연구의 흐름은 ‘판정 문제 정의 → 근거 종류 분류 → 각 접근의 가능성과 한계 → 명세·사람 확인 비용 논의’다. 2015년 연구이므로 LLM의 최신 성능을 평가한 논문은 아니다.

## 프로젝트를 위한 해설: 전화번호 폼을 검사한다면

아래는 직접 구성한 예시다. AI가 전화번호 입력칸을 발견하고 `010-1234-5678`을 넣었다. 화면이 이를 거부했다. 이 사실만으로 결함을 보고할 수 있을까?

먼저 서비스가 허용하는 형식을 알아야 한다. 숫자만 입력하라고 명시돼 있다면 하이픈 포함 값을 거부하는 것은 정상일 수 있다. 반대로 하이픈을 자동 제거한다고 요구사항에 적혀 있는데 저장을 거부한다면 해당 요구사항을 위반했을 수 있다.

검사 기록에서 다음 네 문장을 나눠야 한다.

| 구분 | 예시 |
|---|---|
| 사실 | 입력 후 오류 메시지가 표시됐다. |
| 기대 결과 | 숫자만 허용한다는 안내에 따라 하이픈 입력은 거부돼야 한다. |
| 기대의 근거 | 해당 필드 옆에 ‘숫자만 입력’ 안내가 있다. |
| 판정 | 공개 안내에 대한 입력 거부 검사에서는 기대와 일치했다. |

만약 안내·제약·요구사항이 없다면 ‘전화번호니까 이 형식을 받아야 한다’는 AI의 상식은 검사 아이디어가 될 수 있지만, 결함 확정의 충분한 근거는 아니다. 이 경우 입력을 시도하고 반응을 남기되 형식의 적절성 판정은 보류한다.

이렇게 기록하면 사용자는 ‘무엇을 기준으로 버그라고 했는가?’를 보고서에서 확인할 수 있다. AI가 높은 자신감을 표현했다는 정보만으로는 이 질문에 답할 수 없다.

## 중요하게 이해할 지점

### 공개 요구사항, 화면 안내, HTML 제약은 적용 범위가 다르다

HTML의 `required`를 확인했다면 브라우저 폼에서 필수 입력으로 선언됐다는 사실을 알 수 있다. 서버가 실제로 저장을 막는지, 서비스가 요구하는 업무 규칙이 무엇인지까지 자동으로 알 수는 없다.

폼의 `novalidate`, 사용한 제출 방식, 비동기 처리, 조건부 필수 여부를 함께 확인해야 한다. 클라이언트 검증과 서버 검증은 별도 검사로 설계한다. 또 정상적으로 오류 메시지를 보여주는 폼에서 오류 문구가 있다는 이유만으로 결함을 보고하면 오탐이 된다.

### 기준은 ‘근거’와 ‘가설’을 나눠야 한다

우리 검사 계획에서 다음처럼 구분하면 좋다. 아래 분류는 프로젝트용 제안이며 논문의 공식 우선순위 체계가 아니다.

| 검사 기준의 출처 | 사용할 때 확인할 것 |
|---|---|
| 팀이 제공한 요구사항 | 현재 버전·기능·사용자 조건에 적용되는가? |
| 화면 안내 | 해당 입력·행동을 설명하는 문구인가? |
| HTML 제약 | 현재 컨트롤과 폼 제출 방식에서 적용되는가? |
| 명시된 상태 관계 | 초기 데이터와 전제 조건을 확보했는가? |
| AI의 기능 추정 | 추가 근거가 필요한 검사 후보로 구분했는가? |

오라클을 항상 ‘하나의 정답 값’으로 생각할 필요는 없다. ‘허용 범위 안에 있다’, ‘선택한 자료 ID와 일치한다’, ‘명세에서 허용한 상태로 이동한다’도 판정 기준이다. 반대로 화면 전체를 이해할 수 없더라도 그중 확인 가능한 좁은 조건은 검사할 수 있다.

### 반복된 동작과 올바른 동작을 구분한다

모든 입력을 저장하지 않는 결함이 계속 반복될 수 있다. 이 현상이 세 번 재현됐다고 해서 정상 동작이라는 뜻은 아니다. 반복 실행은 현상의 안정성을 확인하고, 요구사항은 그 현상이 올바른지 판단하는 데 쓰인다.

두 AI 모델이 같은 판정을 해도 동일한 잘못된 가정을 공유했을 수 있다. 모델 수를 늘리기 전에 결과의 출처·전제·실제 관찰을 먼저 확인하는 방식이 우리 초기 개발에 적합하다.

## 현재 프로젝트에 연결하는 위치

현재 계획 초안에는 `expected_result`, `expectation_source`, `observe`가 있다. 기대 결과를 못 정하면 `expected_result`를 비워 두고, 확인할 질문과 관찰 목적을 남길 수 있다. 아래는 상세 결과에 저장할 내용의 예이며 확정된 새 JSON 스키마가 아니다.

| 상세 결과 내용 | 기록 목적 |
|---|---|
| 검사 목적과 범위 | 무엇을 확인한 결과인지 제한 |
| 기대 결과·출처·전제 | 판정 기준을 검토 가능하게 함 |
| 실제 관찰과 증거 ID | 결론이 실제 자료에 연결됨 |
| 판정 가능한 조건 | 확인한 부분과 확인 못 한 부분 분리 |
| 판정 보류 사유 | 정보 누락·명세 부족·도구 실패 구분 |

현재 콜백에서는 `passed`, `failed`, `not_run`을 사용한다. 일부 검사 결과가 판정 불가이고 확정 실패도 없다면 통합 계약에 맞춰 `not_run`을 반환하고 상세 사유를 별도로 저장한다. `passed`도 실행한 검사 범위의 통과다. [프로젝트 판정 계약](../../INTEGRATION_GUIDE.md)

새 enum이나 근거 출처 이름을 여러 팀이 따로 만들기보다는, 현재 초안 필드를 사용해 작은 사례를 먼저 연결하고 필요한 상세 형식을 합의하는 것이 좋다.

## 작은 적용 순서

1. 기존 AI 검사 후보마다 기대 결과가 있는지 확인한다.
2. 기대 결과의 출처와 적용 전제를 같이 적는다.
3. 코드·관찰로 판정 가능한 부분과 근거 부족 부분을 구분한다.
4. 동일한 반응이 정상일 수도 있는 사례를 벤치마크에 포함한다.
5. 보고서에 기대·실제·근거·불확실성이 함께 나오는지 확인한다.

## 검증할 사례

‘잘못된 입력을 거부함’, ‘존재하지 않는 페이지가 정상적인 404를 반환함’, ‘권한 없는 기능이 안내를 보여줌’처럼 정상적인 실패 응답을 포함한다. 검사 도구의 selector 오류나 테스트 서버 미실행도 별도 사례로 넣는다. 이때 서비스 결함으로 보고하지 않고 원인을 구분하는지가 중요한 평가 대상이다.

이 논문에서 우리 프로젝트가 가져올 가장 중요한 기능은 **버그 판정마다 ‘기대 결과를 정한 근거’를 남기는 것**이다. 원문 분류 이름을 모두 구현하는 것보다, 하나의 판정이 설명 가능하도록 만드는 데 우선 적용하면 된다.
