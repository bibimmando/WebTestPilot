# 1. WebTestPilot: 실행 결과를 근거 있는 조건으로 검사하기

[전체 가이드](../PAPERS_GUIDE_KO.md) · [논문 원문](https://arxiv.org/html/2602.11724v3) · [섹션별 직역·용어표](WEBTESTPILOT_FULL_TRANSLATION_KO.md)

## 원문에서 확인한 방법

이 논문의 중심 문제는 **AI가 실제 서비스 결함과 자신의 잘못된 해석을 구분하기 어렵다**는 것이다. 자연어 요구사항과 실행 이력을 사용해 검사 조건을 구체화한다.

```text
요구사항 → 조건·행동·기대 결과로 단계 분해
        → 이전 상태와의 데이터·시간·인과 관계 추론
        → 필요한 GUI 데이터를 이름·자료형이 있는 변수로 표현
        → 변수에 대한 사전·사후 검사 조건 생성
        → 사전 조건 확인 → 행동 실행 → 사후 조건 확인
```

변수의 틀에는 Pydantic을, 검사 표현에는 Python을 확장한 DSL을 사용한다. 검사 종류는 존재, 관계, 시간 순서, 원인·결과, 데이터 일치다. 과거 상태는 실행 이력에서 조회한다. 동일한 논리적 페이지의 재방문은 DOM 거리와 화면 비교로 식별한다. 행동 대상은 대략적 화면 위치를 찾은 뒤 해당 영역을 잘라 요소를 선택한다. [§4 방법](https://arxiv.org/html/2602.11724v3#S4)

자연어 요구사항이 완결돼 있다는 가정이 있다. 실패 시 조건 재생성·재시도나 후보 조건의 다수결도 논의하지만 실험 설정은 `n=1`이다. 따라서 우리 프로젝트의 별도 반복 재현 기준과 동일시하면 안 된다. [§4.3.3, §7](https://arxiv.org/html/2602.11724v3)

## 프로젝트를 위한 해설: 즐겨찾기 추가 검사

아래는 직접 구성한 로컬 벤치마크 사례다. 서비스 요구사항은 다음처럼 명시돼 있다고 가정한다.

> 상세 화면에서 자료를 즐겨찾기에 추가하면 해당 자료가 한 번 등록된다. 기존 즐겨찾기는 유지된다.

초기 즐겨찾기에는 `자료 A`, `자료 B`가 있다. 지금 상세 화면에 보이는 자료는 `자료 C`다. 추가 버튼을 누른 뒤 즐겨찾기 목록에 들어간다.

실행기에 남은 기록이 ‘클릭 성공’과 ‘목록 화면 표시’뿐이면, 실제로 어떤 자료가 추가됐는지 확인할 수 없다. 버튼이 동작하면서 `자료 D`를 잘못 등록해도 이 기록만으로는 통과처럼 보일 수 있다.

반면 다음 관찰값을 남기면 비교할 수 있다.

| 필요한 관찰 | 설명용 값 | 판정에 쓰는 이유 |
|---|---|---|
| 기존 목록 | A, B | 원래 자료가 사라지지 않았는지 확인 |
| 추가 대상 | C | 다른 자료를 추가한 오류를 구분 |
| 추가 후 목록 | A, B, C | 기대한 상태와 비교 |
| 관련 행동 | 상세의 ‘즐겨찾기 추가’ 클릭 | 어떤 행동 전후를 비교하는지 설명 |

비교는 ‘자료가 보이는가?’ 하나로 끝내지 않는다. C가 등록됐는지, A와 B가 유지됐는지, C가 중복됐는지를 각각 확인한다. 자료 제목이 중복될 수 있다면 제목만으로 같은 자료라고 확정하지 않고 화면에서 관찰 가능한 고유 식별 단서를 사용한다.

여기서 **사전 조건**은 ‘로그인 상태이고, C의 상세 화면이며, C가 아직 등록되지 않았다’이다. 이 조건을 확인하지 못했으면 추가 후 결과만 보고 결함이라고 단정하기 어렵다. 이미 등록된 C를 다시 누르는 버튼이 취소 기능일 수도 있기 때문이다.

**사후 조건**은 ‘C가 한 번 등록되고 기존 자료가 유지된다’이다. 화면을 이동해도 결과가 확인되는지까지 검사할지는 저장 지속성 요구사항과 테스트 목적에 따라 정한다.

이 사례에서는 ‘이전 상태의 값’과 ‘다음 상태의 값’을 먼저 잘 관찰해야 한다. 두 값을 비교하는 계산이 정확해도, 첫 화면에서 C를 D로 읽었다면 판정은 틀린다. AI 해석 단계와 값 비교 단계를 분리해 기록하는 이유가 여기에 있다.

## 중요하게 이해할 지점

### 필요한 값을 언제든 다시 확인할 수 있어야 한다

현재 상태의 긴 설명문만 넘기면 이전 목록의 A와 B가 요약에서 사라질 수 있다. 우리 프로젝트에는 snapshot ID가 있으므로 ‘비교에 사용한 값이 어느 상태에서 나왔는지’를 기록하는 방향이 적합하다.

하지만 snapshot ID가 있다고 필요한 값이 자동으로 추출되지는 않는다. 즐겨찾기 목록이 현재 요약의 본문 상한을 넘거나, 한 화면에 일부만 표시되면 별도 조회·수집이 필요하다. 이때는 비교를 완료하기 전까지 ‘전체 목록을 확인했다’고 표시하지 않는다.

### 이름을 붙여 구조화하면 검사 목적이 분명해진다

‘앞에서 본 자료가 제대로 추가됐는지 확인’이라는 설명만 보관하기보다, 실행 중 `추가할 자료`, `기존 목록`, `현재 목록`을 구분해 저장하면 비교 대상을 혼동할 가능성이 줄어든다. 처음부터 모든 서비스용 데이터 모델을 만들 필요는 없다. 먼저 로컬 벤치마크 한 기능에 필요한 항목만 정한다.

### 화면이 달라졌다는 사실과 기대한 결과는 다르다

클릭 후 토스트가 나타났다는 관찰은 피드백이 있었다는 증거다. 즐겨찾기가 실제로 저장됐다는 증거로 충분한지는 별도 문제다. UI 반응 확인과 업무 데이터 확인을 다른 검사로 기록하면 보고서도 명확해진다.

## 현재 프로젝트에 연결하는 위치

| 현재 기반 | 활용 방향 | 현재 자동으로 되지는 않는 것 |
|---|---|---|
| `initial_snapshot` | 시작 상태와 사전 조건의 근거 | 즐겨찾기 전체 데이터의 의미 추출 |
| `evidence.get_ai_input()` | 검사 목적·대상 선택 | 이전 업무 값의 영구 기억 |
| `controls[].key`와 상세 요소 | 최신 조작 대상 확인 | 같은 key가 항상 같은 업무 객체라는 보장 |
| `evidence.action()` | 조작 전후 snapshot과 이벤트 기록 | 기대 결과 자동 생성·판정 |
| `expected_result`, `expectation_source` | 계획 초안에서 기대 결과와 근거 기록 | 논문의 DSL 실행 |

AI 검사 콜백이 기대 결과, 실제 관찰값, 관련 action/snapshot ID를 상세 결과에 저장하도록 연결할 수 있다. 현재 크롤러는 임의의 `findings`·`report` 반환 필드를 자동 저장하지 않으므로 별도 저장 경로를 마련한다. [프로젝트 통합 계약](../../INTEGRATION_GUIDE.md)

논문의 DSL을 그대로 복제하는 대신, 초기에는 존재·동일 값·개수·범위 등 필요한 비교만 지원할 수 있다. AI는 검사를 제안하고, 실행기는 허용된 비교와 관찰값을 검증한다. 모델이 생성한 임의 Python을 실행하는 방식은 현재 프로젝트의 계획 검증 계약에 맞지 않는다.

## 작은 적용 순서

1. 로컬 즐겨찾기 페이지에 공개 요구사항과 정상·결함 모드를 준비한다.
2. 사전 조건과 필요한 관찰값을 정하고, 실제로 수집되는지 먼저 확인한다.
3. 하나의 추가 행동을 전후 증거로 감싸고 완료 조건까지 기다린다.
4. 비교 규칙별로 통과·실패·판정 불가와 근거를 저장한다.
5. 초기 데이터로 되돌린 후 같은 절차를 다시 실행한다.

## 검증할 사례

| 로컬 페이지 조건 | 기대되는 검사 결과 |
|---|---|
| 정상: C 한 번 추가, A·B 유지 | 설정한 검사 통과 |
| 결함: D가 추가됨 | 추가 대상 일치 검사 실패 |
| 결함: C 두 번 추가됨 | 중복 검사 실패 |
| 결함: B가 사라짐 | 기존 자료 유지 검사 실패 |
| 상태 수집 실패 또는 목록 일부만 수집 | 전체 목록 관계 판정 보류 |
| 사전 조건과 다른 자료 상세에 도달 | 준비·경로 문제 기록, 결함 여부 추가 확인 |

이 논문에서 우리 프로젝트가 먼저 가져올 기능은 **이전 상태의 필요한 값을 보관하고, 기대 결과와 실제 결과를 증거 ID로 연결해 비교하는 것**이다. 스크린샷 위치 모델이나 전체 DSL 도입은 이 작은 검사 흐름을 완성한 뒤 필요성을 판단할 수 있다.
