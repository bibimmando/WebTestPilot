## 아키텍처 v1 기반 새 엔진 모듈

Claude Opus가 생성한 코드를 별도 `engine_*` 모듈로 추가하고 인터페이스 연결과 안전 제한을 보완했다.
기존 크롤러 CLI와 출력 스키마는 유지한다.

- `engine_budget.py`: 프로필별 예산, 우선순위 frontier, 체크포인트
- `engine_safety.py`: 범위·robots·속도·위험 동작 제한
- `engine_explore.py`: P0–P3 탐색 조율, 비동기 조언, 검증 파이프라인 연결
- `engine_verify.py`: 근거 ID 검증, 중복 제거, 새 컨텍스트 재현 3/3 조건, 보고서

이 모듈들은 어댑터 기반 코어다. 실제 브라우저 어댑터, LLM Gateway, 인증·웹 서비스의 연결은
아직 완료되지 않았으며 기존 CLI가 새 엔진 전체를 실행하지 않는다. 43개 테스트는 기존 크롤러
통합 테스트와 새 코어의 단위 테스트를 포함하며 새 P0–P6 전체 시스템의 실사이트 검증을 뜻하지 않는다.

팀 협업용 루트 README, 개인 폴더 6개, PR 양식과 GitHub Actions CI를 추가했다.

## 현재 우선순위

2026-09-30 여섯 사이트 실측에서 확인한 아래 전처리·탐색 한계를 먼저 수정한 뒤 공통 평가를 진행한다.

- 차단 동작이 페이지당 동작 예산을 먼저 소모함: Books의 80개 결과가 모두 blocked여서 허용된 hover를 실행하지 못했다.
- 상품 title을 hover 기능으로 세는 과다 라우팅: Books 공통 신호 339개를 제거했지만 hover 339개가 남아 20페이지 모두 hybrid다.
- URL/데이터가 다른 동일 템플릿은 방문 생략 대상이 아님: Books에서 카테고리 20페이지를 재수집하고 큐 332개가 남았다.
- 실행 환경에서 차단한 통계/CSP 요청이 사이트 오류로 탐지됨: HackerRank·Tistory 결과에서 원인 분리 필요.
- 외부 리소스 DNS 실패, 의도된 401, 시간 초과를 기능 버그와 구분할 분류 단계 필요.
- 해시 라우트, 입력·Enter·select·checkbox·스크롤 기능이 없어 TodoMVC와 동적 기능 검사가 제한된다.

1. 팀 공통 정답셋과 탐지 `kind` 명세 확정 후 6개 프로토타입 실측
2. 전처리 적용 전·후 동일 조건 재벤치마크로 토큰 감소와 Recall 변화 확인
3. AI CLI 어댑터와 결과 스키마를 정한 뒤 `ai_results.jsonl` 연결
4. 결정적 탐지와 AI 결과를 합친 최종 버그 보고서 구현
5. 오류 후보 자동 재현과 재현 성공률 측정
6. 다중 viewport Responsive 검사 설계·구현

## 아직 구현하지 않은 핵심 기능

- 실제 AI API 호출 CLI와 `ai_results.jsonl`
- 결정적 탐지와 AI 결과를 합친 최종 버그 보고서
- 자동 재현과 재현 성공률 계산
- 인증 상태와 다중 사용자 상태 그래프
- 다중 viewport Responsive 검사
나머지는 다음 이유로 이번 AI 전처리 단계에서 제외했다.

- AI 호출·최종 병합: 사용할 로컬 CLI 명령, 출력 JSON 스키마와 모델이 아직 정해지지 않았다.
- 자동 재현: 재시도 횟수·동적 데이터 초기화 방식이 없으면 중복 실행이 상태를 오염시킬 수 있다.
- 인증/다중 사용자: 테스트 계정, 역할과 비밀값 주입 규칙이 필요하다.
- 다중 viewport: 대상 기기 폭과 동일 페이지 재방문을 페이지 예산에 포함할지 먼저 정해야 한다.

## 현재 전처리 제약

- 공통 UI는 오류 없는 페이지 3개 이상, 60% 이상에서 반복된 의미 시그니처로 판정한다. 페이지 수가
  적거나 같은 이름의 서로 다른 기능은 추가 검증이 필요하다.
- 근본 원인 병합은 정규화한 첫 오류 메시지·리소스 종류·호스트를 사용한다. 난독화된 스택이나
  메시지가 없는 실패는 과소/과다 병합될 수 있다.
- 읽기 중심 라벨을 허용해도 안전 모드의 네트워크 가드는 GET/HEAD/OPTIONS 외 요청을 계속 차단한다.
- 공통 평가는 모든 프로토타입이 `crawl_report.json`의 `findings` 또는 `root_causes` 구조로 내보내야
  한다. 다른 구조는 팀별 어댑터가 필요하다.

## 갱신 규칙

- 완료한 작업은 `구현 완료`로 옮기고 우선순위를 다시 정렬한다.
- 새 문제는 재현 근거와 관련 보고서 경로를 함께 기록한다.
- 실험 수치는 대상, 제한값과 토크나이저가 같을 때만 직접 비교한다.
- 단순 코드 변경 내역보다 설계 결정, 성능 변화와 다음 행동을 중심으로 기록한다.
- 긴 일지로 만들지 말고 완료·진행·다음 작업이 빠르게 보이도록 유지한다.
